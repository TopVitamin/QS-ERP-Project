# 需求调研与分析文档方法（通用模板）-V1

> 版本：V1
> 用途：给一个业务系统项目定义需求层写什么。现状调研怎么记，目标结论怎么给，写到什么程度算完。
> 用法：骨架和检查项可以直接沿用，把 [项目名]、[模块名] 换成自己的。
> 共用规则见《文档通用规则（通用模板）-V1》。本文只讲需求层独有的东西。

## 一、调研稿和分析稿分工

一个模块通常要写两份文档，职责不一样。

调研稿只还原现状：谁在做、在哪个系统或表格里做、怎么交接、证据在哪、碰到什么问题、用户原话是怎么说的。

分析稿只写目标结论：要解决什么、一期做什么、不做什么、拿什么验收、哪些还没定。

| 调研稿写 | 分析稿写 |
| --- | --- |
| 现在谁在哪个系统里做，怎么交接 | 目标上由谁、在哪一步做 |
| 现状带来的问题，有实例 | 一期解不解决、解决到什么程度 |
| 用户原话原意的诉求 | 诉求采纳了没有，不采纳的理由 |
| 资料缺口，证据去哪里找 | 待确认事项和最迟确认时点 |

自查办法：把调研稿里的“应该”换成“现在”再读一遍，把分析稿里的“现在”换成“目标上”再读一遍。哪句话读不通，哪句话就是串层了。

两条容易犯的错：

- 把本轮讨论确认的目标方案写进调研稿当成现状。目标规则要标明是设计确认的，它不是访谈、样表或接口证据。
- 拿演示数据当证据。原型和Mock只能说明流程走得通，说明不了真实接口、并发和生产行为已经验证过。

写到什么程度算完，只有一条判断标准：下游能不能据此决定做什么、不做什么，以及能不能验收。

## 二、这一层放哪些文件

- **项目级两篇总览**：需求调研总览、需求分析总览。只放项目级的问题和索引，不复制模块内容。
- **每个模块两篇**：`[模块名]需求调研.md`、`[模块名]需求分析.md`，固定成对，结构按本文，不另起章节。

两篇总览的骨架在下面。它们的定位是索引，每条结论都要能指到某个模块文档的编号；指不到，说明这条要么该下沉到模块，要么该补依据。

### 调研总览（四节）

1. **定位、范围与事实来源**：本文回答哪几个问题、不复制什么；一张表写清每类资料能用在哪、不能用在哪。
2. **模块地图与调研进度**：目标需求有没有形成、现状证据齐不齐，分两列记，不要合成一个进度。末尾用一句话收当前总体状态。
3. **统一记录与确认方法**：编号规则、追溯关系、结论状态词表、更新纪律。
4. **项目级待核实事项**：只升级跨模块的问题，写影响范围、需要补的证据、最迟确认时点。

### 分析总览（五节）

1. **项目级分析结论**：一段人话讲清系统定位和本期边界，不展开模块细节。
2. **模块职责与核心链路**：模块职责、文档索引、当前阶段一张表，另附一张主链图。
3. **一期范围与共同原则**：包含什么、明确不做什么。跨模块的共同原则逐条编号，当索引用，不替代模块里的适用条件和例外。
4. **跨模块待决策与后续确认**：事项、问题类别、影响与写在哪篇、确认时点。
5. **整体验收与阅读顺序**：需求体系的整体验收维度，加一份先读哪篇的次序。

## 三、调研稿写什么

**1. 调研范围与资料来源。** 覆盖哪些业务、不覆盖什么；每条结论出自哪里（访谈、样表、系统截图、上游背景文档、本轮讨论）。来源写不到具体资料的，这条结论不成立。

**2. 当前角色与系统分工。** 谁在做、在哪个系统或表格里做、产出交给谁。已经上了系统的写系统名和职责边界；没上系统的写清楚靠什么表格和线下沟通衔接。

**3. 核心场景与业务问题。** 场景和问题各自编号。一个场景写清现状做法、参与方、卡在哪。不编造频率、损失金额、效率数字。没有留存记录就不写，写了就要有出处。

**4. 原始业务诉求。** 用用户的原意记，不要提前翻译成方案，并标注它来自哪个场景。这一部分是分析稿的输入，不是结论。

**5. 需要重点确认的边界。** 把主链已经确认、细节还没确认的地方逐条点出来。上游背景文档里的旧说法如果本轮作废，在这里说明以哪份为准、从哪一条起不再沿用。

**6. 下一轮调研清单。** 调研对象、重点问题、需要对方提供的资料，三列。别人拿着这张表就能去要材料。

## 四、分析稿写什么

**1. 分析结论与业务边界。** 开头一段人话讲清这个系统做什么、不做什么、和谁交接。框架性的描述不算结论。

**2. 原始诉求处理。** 诉求、处理结论、理由三列，逐条覆盖调研稿里的全部诉求。不采纳也要写理由，只写暂不考虑不算。

**3. 需求追溯矩阵。** 场景与问题、业务需求、功能需求、验收标准，一张表，覆盖到验收编号。

**4. 功能需求。** 一条编号一段，标题就是结论。写规则、数量关系、边界和例外。只要出现部分、剩余、还能做多少这类关系，就用一个小例子把加减算一遍，并说明每个数落在哪个对象上。举例用的数字要说明是示例，别混进真实数据。引用上游编号的只链接不复制。

**5. 一期范围与模块依赖。** 包含和不包含分开写。依赖表逐行写依赖谁、依赖什么，外部系统也算依赖。

**6. 验收标准。** 写成“条件与操作 → 预期结果”，一条聚焦一个能判定的结果。标明这是业务验收示例，不是已经执行的测试记录。测试步骤和用例留在测试文档里。

**7. 待决策事项。** 事项、待确认内容、确认阶段、谁去确认、不确认的影响、最迟确认时点。只留会改变范围、数量、责任或算法的问题，细节问题留在正文对应位置，不上这个表。

## 五、编号与追溯

推荐五类编号：模块前缀 + 类型 + 序号。项目可以换前缀，类型不要混。

| 类型 | 记什么 | 放在哪 |
| --- | --- | --- |
| S场景 | 现状里真实发生过的一类情形 | 调研稿 |
| P问题 | 现状做法带来的问题 | 调研稿 |
| BR业务需求 | 目标上要满足什么 | 分析稿 |
| FR功能需求 | 系统要实现什么 | 分析稿 |
| AC验收 | 拿什么判断做到了 | 分析稿 |

追溯关系：

```plain
现状事实／目标设计确认
    → 场景 S 与问题 P
    → 业务需求 BR
    → 功能需求 FR
    → 验收标准 AC
```

几条约定：

- 每条BR至少挂一个FR，每条FR至少挂一条AC，跨模块引用的编号写全前缀。
- 新增或删除功能时，同步更新追溯矩阵、功能需求清单和验收表。只改正文等于没改。

## 六、逐条自查

- [ ] 调研稿没有出现目标方案；分析稿没有重抄现状
- [ ] 每条现状结论都标了来源，来源指向具体资料
- [ ] 场景和问题都编号了，能举出真实例子，没有编造的频率或损失数字
- [ ] 原始诉求与处理表逐条对应，没有遗漏；不采纳的写了理由
- [ ] 追溯矩阵覆盖到验收，每条FR都有AC，每条BR都有FR
- [ ] 功能需求标题就是结论；有数量关系的，用例子算过
- [ ] 一期包含与不包含都写了，依赖表逐行写清依赖什么
- [ ] 每条验收标准能对应功能需求，单看条件与预期即可判定；不以“正确”、“合理”代替具体结果
- [ ] 待确认事项都写了谁去确认、影响范围和最迟确认时点，项目级问题已升级到总览
- [ ] 全文引用的上游结论都能指到具体文档和编号

## 七、按模块类型定密度

不同类型分量不一样，但都得写到能交差。下面几种是常见类型，不是必须按这四类拆模块。

| 类型 | 常见适用 | 读者该记住的一条 |
| --- | --- | --- |
| 主链路 | 下单、履约、库存、工单这类核心 | 链路怎么走，数量怎么控制，异常怎么收，哪一步卡人工 |
| 基础资料 | 主数据、价格、配置等前置 | 没有它下游不能做什么；改了、禁用了，新单和老单分别怎么办 |
| 交接边界 | 财务交接、外部系统集成 | 谁负责执行、谁负责记账、谁负责交接；拿不到结果时谁确认 |
| 公共能力 | 权限、审核、导入等共用机制 | 共用机制的适用边界；不在这里重定义业务规则，只写谁去引用哪一条 |
