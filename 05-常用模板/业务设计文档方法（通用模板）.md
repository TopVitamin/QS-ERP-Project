# 业务设计文档方法（通用模板）

> 用途：给一个业务系统项目定义「业务设计层」写什么、写到什么程度算完。
> 用法：把方括号里的内容换成自己项目的实际情况；骨架、深度标准、自检清单、硬条件可以直接沿用。
> 来源：从 QS-ERP 项目的《业务设计和应用设计的边界》抽象出来，去掉了项目专有名词。

## 一、先分清业务设计和应用设计

**业务设计回答：业务应该怎样运转？** 谁在什么情况下做什么、产生什么结果、下一步交给谁。

**应用设计回答：系统怎样支撑这些业务？** 单据关系、状态机、字段、权限、页面和交互。

| 业务设计 | 应用设计 |
| --- | --- |
| 一次采购允许分批收货 | 系统如何组织订单、通知与结果的关联 |
| 剩余履约可以终止，已安排的交付怎么处理 | 关闭按钮、操作条件、状态和校验怎么设计 |
| 什么实际结果引起库存变化 | 系统如何接收、校验并记录 |
| 谁有权确认或更正结果 | 对应页面、操作和接口怎么落实权限 |

业务设计可以出现单据名和业务阶段（生效、履约、结束），出现这些不等于越界；但状态枚举、按钮、字段、页面文案和执行标识不进这一层，需要时只引用应用设计文档。

## 二、这一层放哪些文件

- **一篇总览**：业务域地图、参与方与域的关系、链路与交接清单、公共术语、收口事项。
- **每个业务域一篇**：默认一域一文，内容复杂再拆。
- 编号发出后不改号，新增业务域追加编号；不预建空文件。
- 过程物（待确认清单、评审记录、讨论稿）不放交付目录——它们会和正文重复，还会过期。
- 总览里单独写一份阅读顺序，并注明「文件号不是阅读序」。

## 三、每篇的骨架（七部分）

1. 业务定位与范围。
2. 参与角色。
3. 核心业务场景。
4. 核心业务流程。
5. 业务对象及关系。
6. 核心业务规则。
7. 特殊与异常场景。

文首一句话说明用途，并注明输入来源与确认状态；文末按处理阶段列出待确认事项。

## 四、深度标准

判断只有一条：**下游据此能不能决定「做什么、不做什么」。**

1. **定位与范围**：解决什么问题、服务谁、和谁交接、一期明确不做什么；边界要指到上游文档和编号。
2. **参与角色**：做成矩阵——负责什么／在哪些单据上做什么／必须交出什么；未定岗位显式标「待确认」；权限只引用公共规则，不在这里设计权限矩阵。
3. **业务场景**：覆盖主场景、分支场景、辅助场景、异常场景四类；每个场景写触发、前置、参与方、主要步骤、分支与判断点、业务结果、后续环节。只写「允许分批」这类结论句不算场景。
4. **业务流程**：分主流程、分支流程、辅助流程、异常流程；写「谁在什么条件下做什么、产生什么结果、交给谁」；关键交接点唯一可指认；不写页面跳转和接口调用。
5. **业务对象及关系**：对象清单（含义、如何识别、业务阶段、阶段结束时的结果）＋关系表（基数、可选性、追溯路径）＋数量流向（每个量落在哪个对象上、怎么累计、回补、释放，不重不漏）。
6. **业务规则**：写成判断句（条件→结果），写清适用范围和例外；本域特有规则写全，引用上游的只链接不复制；每条规则要能反推出验收。
7. **特殊与异常场景**：四要素——触发条件、业务后果、责任方、能否恢复及恢复方式；明确一期不处理的情形。

## 五、自检清单（防漏章节）

- [ ] 四类场景齐全，且都能举出本域的真实例子
- [ ] 每个场景都有触发、前置、参与方、步骤、分支、结果、后续环节
- [ ] 角色表覆盖全部参与方，未定岗位已显式标注
- [ ] 对象关系有基数和可选性，数量沿对象链条能对上
- [ ] 关键交接点唯一：上游给什么、本域交给下游什么
- [ ] 规则可判定，没有「视情况」「按需」这类说法
- [ ] 系统机制（状态枚举、按钮、字段、执行标识、页面显示）没有写进本层，需要时只引用
- [ ] 待确认事项只留会改数量、责任或算法的问题，并标注处理阶段
- [ ] 全文引用的外部结论都能指到具体文档和编号

## 六、六条硬条件（防糊弄）

自检清单防的是漏章节，这六条防的是「章节齐了但内容糊弄」。缺一条就不算写完。

1. **开篇一句人话 + 一张交接表。** 上游给什么、本域交出什么，列名全项目统一。
2. **第三节只做场景目录。** 只写触发和后续环节；步骤进第四节，后果进第七节，不要回潮。
3. **第四节必须有一条时间序走查。** 一个故事按时间往下走，分支标成「分支」，不接在主链后面装成下一步；走查要拆开本域最容易混的那组量。
4. **第六节的规则标题就是结论**（例如「收货进度不等于终止」），能反推出验收；依据只点上游编号，不抄上游。
5. **一篇一个权威位置。** 关闭和取消的业务含义只在第四节，公式只在第六节，异常四要素只在第七节。
6. **文末待确认只留会改数量、责任或算法的事。** 「待确认事项怎么读」的解释只放在总览一处，各业务域不重复贴。

## 七、按域类型定密度

不同域的职责不同，密度也不一样，但都要能交差：

| 类型 | 适用 | 读者三分钟内要带走什么 |
| --- | --- | --- |
| 总览 | 全局 | 域怎么接、先读哪篇、哪些词全项目同义、哪些还没收口 |
| 履约 | 主链路域 | 约定／安排／实际怎么分开，终止怎么走，一条带数量的时间线 |
| 准备 | 基础资料、价格等前置域 | 没有这些就不能建单；改了、禁用了，新单和老单分别怎么办 |
| 边界 | 财务交接、外部集成等 | 谁负责执行、谁负责记账、谁负责交接；拿不到结果时谁确认 |

## 八、写完怎么评

- 自检清单防漏章节，独立评审防「章节齐了内容糊弄」。
- 独立评审分三线，各自只读、不改文件：**事实核对**（结论能不能指到上游编号，有没有无依据的断言、与上游冲突的口径、编号错误）、**完整性**（按骨架和自检清单逐条打钩）、**语言**（AI 味、长句、内部术语、引用简写）。
- 固定输出格式：文件 + 行号 + 原文摘录 + 问题类型 + 依据 + 严重度 + 建议。
- 评审意见的处理：先逐条对原文（外部评审常见三类偏差——引用旧版本、与正文重复、把行业惯例当成本项目规则），再分「会影响对错」（必须改）和「文档卫生」（按收益改）；不采纳的要写明理由。

## 九、写作纪律

- **一条结论只有一个权威位置。** 上游规则写在上游，本域只写特有规则；重复内容改成引用。同一规则写三遍，改一处必漏两处。
- 引用写完整文件名，不写编号简称（如「01/4」「采购分析」）。需求编号可以保留，但要能看出属于哪份文档。
- 去 AI 味：不用「触发：…。前置：…」这类电报式标签；不堆砌「本域／本稿／口径／承接／闭环」；把长句拆开。
- 系统内部说法不进业务设计层：「下推」「回写」「状态枚举」「执行标识」换成业务说法。
- 更新或查阅文档时顺带润色：删冗余、拆长句、统一术语、简写换全称。
