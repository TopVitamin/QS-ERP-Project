# 应用设计四篇骨架（通用模板）-V1

> 版本：V1
> 用途：给一个多模块业务系统定义应用设计层要回答哪几件事、写到什么程度可以交给研发和测试。字段清单不在这一层，它是单独一份产物。
> 用法：四件事都要回答；拆成几篇按系统形态定，见第二节。标了「示例」的对象类型、数量名、单据分层，是某类系统的一种拆法，不要当目标项目的结论抄走。
> 共用规则见《文档通用规则（通用模板）-V1》。本文只讲应用设计层独有的东西。

## 一、这一层解决什么

业务设计回答业务应该怎样运转，技术设计回答用什么库、什么框架、怎么部署。这一层夹在中间，回答系统怎样支撑业务。

| 这一层回答 | 不属于这一层 |
| --- | --- |
| 有哪些系统和模块，各自能做什么 | 为什么做这件事、责任归谁（业务设计的活） |
| 每条链路里谁发起、经过哪些单据、状态怎么变 | 页面怎么画、按钮放哪、交互怎么反馈（原型和设计稿的活） |
| 有哪些对象、谁引用谁、数量怎么流动 | 字段名、字段类型、必填性、取值（字段清单的活） |
| 每类单据的状态、操作、条件、校验、联动 | 数据库、索引、事务、部署（技术设计的活） |

写到位的标志：研发照着能定对象、关系和状态，以及接口的时序和校验；测试照着能设计用例；产品交接时不用再口述一遍系统怎么跑。但还不能直接建表，字段名、类型、必填另出一份字段清单。

## 二、怎么拆篇

要回答的是四件事：系统边界、链路交互、对象与数量、单据状态。拆成几篇按系统形态定，不是所有项目都写成四篇。

| 系统形态 | 建议拆法 | 读者该记住的一条 |
| --- | --- | --- |
| 业务中枢（衔接多个外部系统） | 四篇：地图、流程、对象、状态 | 谁负责执行、谁负责记账、数据在系统之间怎么走 |
| 单体内业务系统 | 地图可以很短；流程和状态可合并 | 一笔业务从建单到结束经过哪些状态，数量怎么算 |
| 集成或中间层 | 地图加流程（异常写全）；对象和状态从简 | 交换什么、失败了谁看得见、重试和去重怎么办 |
| 配置或基础层 | 地图加对象；流程和状态只写影响下游的部分 | 谁引用它、改了以后新老数据分别怎么办 |

若采用四篇，阅读和写作顺序都是地图、流程、对象、状态。先有系统边界，才谈得上链路；先有链路，才谈得上对象；先有对象，才谈得上状态。改动时反过来检查：改了状态要回头核对对象关系和流程表，改了模块职责要回头核对地图和依赖。

下面第三到第六节按四篇拆法给骨架。合并篇章时，把对应骨架收进同一篇，深度要求不要降低。

## 三、《系统与模块地图》

### 写哪几节

1. **系统分工**：本系统扮演什么角色，外部系统各自定位，与谁交换什么。一张关系图加一张表（系统／定位／交换什么）。
2. **模块与功能清单**：模块分层图；每个模块一行，写解决什么问题，以及一级、二级功能点。
3. **模块依赖**：谁依赖谁、依赖什么。依赖方向应当单向，出现反向依赖要单独说明。
4. **资料流**：资料、创建、审核、分发、使用五列。只回答谁建、谁审、谁用，规则细节链接到对应文档。没有审核环节的资料，审核列写「无」。
5. **本期范围**：做哪些、不做哪些，各写一段。
6. **文档索引与权威声明**：本套文档各回答什么，冲突时以哪一份为准、怎么判断。

### 写到什么程度

- 没参与过项目的人读完，能说出这个系统管什么、不管什么、和外部交换什么数据。
- 功能清单是划范围用的，不是页面清单，也不是排期表。一个功能点对应一件用户能感知的事。
- 外部系统的定位要写到它负责什么、交给本系统什么、从本系统拿什么，不能只写对接第三方。

### 常见漏项

- 只画了系统图，没写交换的具体内容，导致后面链路文档各说各的。
- 功能清单写成菜单名，研发看不出边界。
- 没写不做的部分，范围争议留到开发阶段。

## 四、《系统流程与单据交互》

### 写哪几节

按链路分节，一节一条链路，每节固定三段：

1. **一句话说明**：这条链路做什么，业务上一句话讲清。
2. **流程图**：图上每个矩形写角色或系统、动作、单据；箭头上标触发方式。自动动作和人工动作要能一眼分开。
3. **步骤表**：谁／动作与单据／状态变化／触发与校验／异常与处理，五列。

最后单独留一节给跨链路的准备和人工补充：资料准备到什么程度才能建单；接口拿不到结果时谁来人工确认、走什么校验。没有外部接口的系统，这一节写内部补录即可。

### 写到什么程度

- **谁**：写角色或系统，不写具体人名；系统动的写系统。
- **状态变化**：写从什么到什么，中间态（处理中、取消中）也要写。
- **触发与校验**：写清是自动还是人工、触发条件和拦下来的校验。
- **异常与处理**：每行都要有落点，不能留这里后续再说。按本系统实际写，超时、失败、重复、人工补救这四类至少要想到。
- 研发照着能做接口时序和状态流转，测试照着能设计用例。

### 常见漏项

- 图里画了人工动作，表里没说是谁触发的，研发当成自动。
- 正常流程写得很细，异常只写一句按异常处理。
- 多条链路各写一遍同一张单的推送或回传规则，改的时候漏掉两处。共用规则应该只写一处，其他位置引用。

## 五、《实体对象关系》

### 写哪几节

1. **对象清单**：对象、类型、识别方法（怎么保证唯一）、业务阶段。类型列由本系统自己定义，不要照搬别的项目的分类。
2. **主数据与组织（或分区）的关系**：有组织、仓库、账套这类硬边界时必写，没有就并进对象清单。
3. **单据之间如何生成**：安排如何变成执行、执行如何变成结果；哪些关联是可选的；一次外部回传对应几张结果单。没有多层单据的系统，写清主单和下游单的基数即可。
4. **数量在对象之间怎么流动**：数量、落在哪个对象、怎么产生、怎么变。有数量的系统，这一节是全篇重头。
5. **单据引用哪些主数据**：单据、引用、归属或分区。
6. **追溯路径**：从哪里能追溯到哪里。
7. **一致性约束**：系统必须守住的不变量。
8. **对象的形态**：几条容易混的区分，逐条一两句话点破。

### 写到什么程度

- 数量一节要覆盖本系统的全部数量，不要照抄别的项目的量名。每个数量说清落在哪个对象上、由什么动作产生、什么时候被消耗或释放。
- 一致性约束写成可判定的判断句：不超过上界、最多一对一、不能为负、未结束的一直占用。写不出判定方式的，就不是约束，是一句愿望。
- 对象的形态专门处理同名不同义。示例：草稿还不是正式单据；价目表当前价不是本单成交价；结果单才是记账依据，外部单据只是证据。换成目标项目里最容易被追问的那几条。

### 常见漏项

- 只列了对象，没写数量。到用的时候才发现，还能执行多少到底减哪些数没人说得清。
- 结果单和上游单的基数写错：一对多还是一对一没核实就定了。
- 没有一致性约束，负库存、超量、重复记账这类问题在实现阶段才暴露。

**对象类型示例**（单据分层的履约系统常用，其他系统自行定义）：主数据、业务安排、执行指令、实际结果、数量状态。

**数量示例**（同一类系统常见，按本系统清单为准）：订购、占用、可执行、累计实际、缺量、预占、可用、在途、冻结、可退额度。

## 六、《单据与状态流转》

### 写哪几节

1. **单据总表**：单据、所属模块、在链路里的角色、状态字段、来源、下游。
2. **按本系统的单据分类写状态**：每类给状态图和状态与操作的对照表。有多状态字段的主单，每个状态字段单独一张图。分类按本系统来，不要预设必须有指令单、结果单。
3. **数量怎么算**：把所有公式收在一处，每条公式一行，写清适用范围。
4. **回写或回传规则**（若有）：结果回来之后改什么、什么时候改，方向是不是单向。
5. **权限怎么处理**：明确这一篇不约定岗位和权限矩阵，只说明权限不替代业务校验。
6. **跨单据联动要点**：额度、占用、零数量、结束与终止、主单完结、记账来源唯一，有哪项写哪项。

状态与操作对照表用四列：状态、可执行操作、前置条件与校验、结果与联动。

**分类示例**（单据分层系统可按这四类分节，其他系统按自己的单据分）：带审核与业务两套状态的主单；一个状态字段串起发送和执行的指令单；审核与推送分开记的结果单；安排和执行写在同一张单上的单据。

### 写到什么程度

- 状态枚举是闭集，写进文档的取值就是全部取值。每个状态都要能答出能做什么、不能做什么、下一步去哪。
- 状态图上的每条箭头都能指出触发者：哪个人、哪个系统、哪个条件。
- 前置条件写具体：数量大于几、单价非空非负、上游是否启用、是否需要确认。
- 结果与联动写清改了什么、生成了什么、推了什么。
- 公式只在数量一节写全，其他位置引用；权限只在权限一节出现。

### 常见漏项

- 状态字段之间互相覆盖（把审核状态和业务状态挤在一个字段里），后面加分支就要推倒重来。
- 只写了成功路径的操作表，取消、退回、失败重试、超时没有入口。
- 状态图和操作表对不上：图上有箭头，表里找不到对应操作，或者反过来。
- 数量公式散落在多条规则里，同一件事在不同章节算法不一致。

## 七、四篇共用的写法约定

- **每篇头注写清三件事**：用途（给谁看、用来干什么）、定位（和业务设计、字段清单、原型各是什么关系）、不写什么。
- **规则集中在一处**：同一条规则只在最合适的一篇里写完整，其他位置引用篇名和小节号。状态只在状态篇写全，对象关系只在对象篇写全，系统边界只在地图篇写全。
- **图与表不重复**：图给结构和顺序，表给条件和异常。图里能看懂的不再抄一遍文字。
- **枚举与命名统一**：单据名、状态名、字段名在这一层里保持同一套叫法，换个说法就要重新对一遍。
- **区分模型说明和正式结论**：项目如果另有一篇模型说明（例如单据怎么分层），头注里要说清楚，模型说明里的枚举和流程属于示例，实际怎么算以应用设计为准。没有模型说明的，不必生造这一层。

权威归属按《文档通用规则（通用模板）-V1》第一节处理。

## 八、怎么维护

- 新增一条链路：先在地图里确认模块职责没变，再写流程，再补对象和数量，最后补状态。相关篇章一起改，不要只改一篇。
- 改一个状态：回头核对对象数量、关联的操作表和流程步骤。改一个数量公式：回头核对引用它的每条规则。
- 状态、字段或枚举调整如果和需求结论冲突，先改需求，再改业务设计，最后改应用设计，不要反过来。
- 这一层是交付物不是过程物。待确认清单、评审记录、讨论稿放在别处，写完不回填进来。

## 九、逐条自查

- [ ] 每篇的头注都写了用途、定位和不写什么
- [ ] 模块清单覆盖全部模块，每个模块写了解决什么问题和功能点
- [ ] 每条链路都有流程和步骤表，异常列每行有落点
- [ ] 对象清单里有识别方法和业务阶段；有数量的，数量一节覆盖全部数量
- [ ] 一致性约束都是可判定的判断句
- [ ] 状态枚举是闭集，状态图上每条箭头都有触发者，操作表与状态图对得上
- [ ] 数量公式集中在一处，其他位置只引用
- [ ] 权限、字段、页面没有混进这一层
- [ ] 篇章之间引用的篇名和小节号都能对上，没有同一规则写两遍
- [ ] 若有模型说明，它和正式结论分别以谁为准，在头注里标清楚了

## 十、容易糊弄的地方

**1. 每篇说不清自己回答什么。** 用一句话概括不出来，说明这篇在凑内容，拆掉或者合并进别的篇。

**2. 图和表各说各的。** 图讲结构和顺序，表讲条件和异常，两边要对得上。只有图没有表，研发问不出什么时候不行；只有表没有图，评审看不出全局。

**3. 状态和数量对不上。** 每个状态下的数量算法都要成立，每个数量在状态图里都找得到产生和释放的位置。这一条对不上，实现阶段一定返工。没有数量的系统，检查状态和对象关系即可。

**4. 异常没人负责。** 每类异常写清谁发现、谁处理、处理不完怎么办，不能停在系统提示异常。

**5. 没写明这一层不写什么。** 每篇要明确排除字段、权限矩阵、页面交互和技术实现，并指明它们各自在哪。边界不写清，这一层会慢慢长成第二个需求文档。
