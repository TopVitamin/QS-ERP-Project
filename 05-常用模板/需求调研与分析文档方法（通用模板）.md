# 需求调研与分析文档方法（通用模板）

> 用途：给一个业务系统项目定义「需求层」写什么——现状调研怎么记录、目标结论怎么给、写到什么程度算完。
> 用法：把方括号里的内容换成自己项目的实际情况；骨架、编号规则、自检清单、硬条件可以直接沿用。
> 来源：从 QS-ERP 项目的《需求调研与分析写作须知》和十个模块的调研／分析稿抽象出来，去掉了项目专有名词。

## 一、先分清调研与分析

**调研稿只还原现状。** 谁在做、在哪个系统或表格里做、怎么交接、证据在哪、遇到什么问题、用户原话说了什么。

**分析稿只写目标结论。** 要解决什么、一期做什么、不做什么、拿什么验收、哪些还没定。

| 调研稿写 | 分析稿写 |
| --- | --- |
| 现在谁在哪个系统里做，怎么交接 | 目标上由谁、在哪一步做 |
| 现状带来的问题，有实例 | 一期解不解决、解决到什么程度 |
| 用户原话原意的诉求 | 诉求的采纳、不采纳结论和理由 |
| 资料缺口，证据去哪里找 | 待确认事项和最迟确认时点 |

自查办法：把调研稿里的「应该」逐个换成「现在」，把分析稿里的「现在」逐个换成「目标上」，哪句话读不通，哪句话就串层了。

两条容易犯的错：

- 把本轮讨论确认的目标方案写成现状。目标规则要标明「本轮设计确认」，它不是访谈、样表或接口证据。
- 拿演示数据当证据。原型和 Mock 只能说明流程走得通，不能说明真实接口、并发和生产行为已验证。

## 二、这一层放哪些文件

- **项目级两篇总览**：需求调研总览、需求分析总览。只放项目级的问题与索引，不复制模块内容。
- **每个模块两篇**：`XX需求调研.md`、`XX需求分析.md`，固定成对，结构按本文骨架，不另起章节。
- 编号发出后不改号；新增模块追加编号；不预建空文件。
- 过程物（访谈记录、讨论稿、评审意见稿）不放交付目录，它们会和正文重复，还会过期。

### 调研总览的骨架（四节）

1. 定位、范围与事实来源：本文回答哪几个问题、不复制什么；一张表写清每类资料的作用和使用边界（能用在哪、不能用在哪）。
2. 模块地图与调研进度：**「目标需求是否形成」和「现状证据是否齐备」分两列记**，不要合成一个进度；末尾用一句话收当前总体状态。
3. 统一记录与确认方法：编号规则、追溯关系、结论状态词表、更新纪律。
4. 项目级待核实事项：跨模块的问题才升级到这里，写影响范围、需要补的证据、最迟确认时点。

### 分析总览的骨架（五节）

1. 项目级分析结论：一段人话讲清系统定位和本期边界，不展开模块细节。
2. 模块职责与核心链路：模块职责 + 文档索引 + 当前阶段一张表；另附一张主链图。
3. 一期范围与共同原则：包含什么、明确不做什么；跨模块共同原则逐条编号，作为索引，不替代模块里的适用条件和例外。
4. 跨模块待决策与后续确认：事项、问题类别、影响与承接位置、确认时点。
5. 整体验收与建议阅读顺序：需求体系的整体验收维度，加一份「先读哪篇」的次序。

总览里的话要能当索引使：每条结论都能指到某个模块文档的编号，指不到就说明它要么该下沉到模块，要么该补依据。

## 三、模块调研稿的骨架（六节）

1. 调研范围与资料来源。
2. 当前角色与系统分工。
3. 核心场景与业务问题。
4. 原始业务诉求。
5. 需要重点确认的边界。
6. 下一轮调研清单。

## 四、模块分析稿的骨架（七节）

1. 分析结论与业务边界。
2. 原始诉求处理。
3. 需求追溯矩阵。
4. 功能需求。
5. 一期范围与模块依赖。
6. 验收标准。
7. 待决策事项。

## 五、深度标准

判断只有一条：**下游能不能据此判断「做什么、不做什么」，以及能不能验收。**

### 调研稿

1. **范围与来源**：覆盖哪些业务、不覆盖什么；每类结论出自哪里（访谈、样表、系统截图、上游背景文档、本轮讨论）。来源写不到具体资料的，这条结论不成立。
2. **角色与系统分工**：谁在做、在哪个系统或表格里做、产出交给谁；已上系统的写系统名和职责边界，没上系统的写清楚靠什么表格和线下沟通衔接。
3. **场景与问题**：场景和问题各自编号，一个场景写清现状做法、参与方、卡在哪。**不编造频率、损失金额、效率数字**——没有留存记录就不写，写了就要有出处。
4. **原始诉求**：用用户的原意记，不提前翻译成方案，并标注来自哪个场景。这一节是分析稿的输入，不是结论。
5. **重点确认的边界**：把「主链已确认但细节没确认」的地方逐条点出来；上游背景里的旧说法如果本轮作废，在这里说明以哪份为准、从哪一条起不再沿用。
6. **下一轮调研清单**：调研对象、重点问题、需要对方提供的资料三列。别人拿着这张表就能去要材料。

### 分析稿

1. **结论与边界**：开头一段人话讲清系统做什么、不做什么、和谁交接。框架性描述不算结论。
2. **原始诉求处理**：诉求、处理结论、理由三列，**逐条覆盖调研稿里的全部诉求**。不采纳也要写理由，只写「暂不考虑」不算。
3. **追溯矩阵**：场景与问题 → 业务需求 → 功能需求 → 验收标准一张表，覆盖到验收编号。
4. **功能需求**：一条编号一段，**标题就是结论**；写规则、数量关系、边界和例外；数量关系用一个小例子算一遍；引用上游编号的，只链接不复制。
5. **一期范围与模块依赖**：包含、不包含分开写；依赖表逐行写「依赖谁、依赖什么」，外部系统也算依赖。
6. **验收标准**：写成「条件与操作 → 预期结果」，一条聚焦一个可判定的结果。**标明这是业务验收示例，不是已执行的测试记录**；测试步骤和用例留在测试文档里。
7. **待决策事项**：事项、待确认内容、确认阶段三列，只留会改变范围、数量、责任或算法的问题；细节问题留在正文对应位置，不上这个表。

### 数据与事实

- 现状结论标来源；引用上游文档写完整文件名，不写「01」「背景那篇」这类简写。
- 没有依据的写「待确认」，不留空、不填假设。**空着的模板内容不算结论，任何人不得引用。**
- 举例用的数字说明清楚是示例，别混进真实口径。

## 六、编号与追溯

模块前缀 + 类型 + 序号，五类编号：

| 类型 | 记什么 | 放在哪 |
| --- | --- | --- |
| S 场景 | 现状里真实发生过的一类情形 | 调研稿 |
| P 问题 | 现状做法带来的问题 | 调研稿 |
| BR 业务需求 | 目标上要满足什么 | 分析稿 |
| FR 功能需求 | 系统要实现什么 | 分析稿 |
| AC 验收 | 拿什么判断做到了 | 分析稿 |

追溯关系：

```plain
现状事实／目标设计确认
    → 场景 S 与问题 P
    → 业务需求 BR
    → 功能需求 FR
    → 验收标准 AC
```

约定：

- 编号发出后不复用、不改号；新增追加，删除留空不补位。
- 每条 BR 至少挂一个 FR；每条 FR 至少挂一条 AC；跨模块引用的编号写全前缀。
- 新增或删除功能时，同步更新追溯矩阵、功能清单和验收表，只改正文等于没改。

## 七、结论状态与待确认分级

| 状态 | 含义 | 写到哪 |
| --- | --- | --- |
| 已核实的现状事实 | 有背景文档、样表、系统资料或其他可定位证据 | 调研稿，标来源 |
| 目标设计确认 | 本轮讨论确认的目标方案 | 分析稿；引用时说明它不是现状 |
| 待核实现状 | 缺访谈、样表、接口或操作证据 | 调研稿保留问题和所需资料，不用经验补全 |
| 待决策规则 | 会影响范围、业务结果或责任归属，现有资料未定义 | 分析稿待决策表，写明确认阶段 |
| 后续设计事项 | 字段、页面、接口技术和实施细节 | 交给对应设计阶段，不在需求层展开 |

待确认事项按影响范围分两级：

- 模块内部细节（某个参数、某个字段、某个岗位）留在模块文档，不升级。
- 同时影响多个模块或项目范围的问题，升级到总览，写清影响范围、需要补什么、最迟什么时候定。

两个纪律：**不问「以后再说」的问题**——每条待确认都要有一个最迟确认时点；**确认结果要回填到有权威的那一份**，其他位置改成引用。

## 八、自检清单（防漏章节）

- [ ] 调研稿没有出现目标方案；分析稿没有重抄现状
- [ ] 每条现状结论都标了来源，来源指向具体资料
- [ ] 场景和问题都编号了，能举出真实例子，没有编造的频率或损失数字
- [ ] 原始诉求逐条有处理结论，不采纳的写了理由
- [ ] 追溯矩阵覆盖到验收，每条 FR 都有 AC，每条 BR 都有 FR
- [ ] 功能需求标题就是结论，数量关系有例子算过
- [ ] 一期包含与不包含都写了，依赖表逐行写清依赖什么
- [ ] 验收标准能判定，没有「基本正确」「大致符合」这类说法
- [ ] 待确认事项都有影响范围和最迟确认时点，项目级问题已升级到总览
- [ ] 全文引用的上游结论都能指到具体文档和编号

## 九、六条硬条件（防糊弄）

自检清单防的是漏章节，这六条防的是「章节齐了但内容糊弄」。缺一条就不算写完。

1. **两篇互不越界。** 调研稿找不到按钮、状态机、字段和方案；分析稿找不到重抄一段现状再补一句「目标改为……」。边界用「换词读一遍」自查。
2. **每条诉求有下文。** 调研稿收进来的诉求，分析稿必须逐条给出采纳、不采纳或后置，并写理由；「收进来没下文」是最常见的漏。
3. **数字关系要算。** 只要出现「部分」「剩余」「可下推」「可退」这类词，就用一个小例子把加减算一遍，并说明每个数落在哪个对象上。
4. **验收贴着功能。** 每条 AC 挂得上一条 FR，读者只看 AC 就能判断这件事做没做到；不写测试步骤，也不用「正确」「合理」收尾。
5. **一处一权威。** 同一条结论只在一份文档里完整维护，其他位置用编号引用；跨模块共用的结论写在负责那个模块的文档里。
6. **待确认写清代价。** 每条待确认写：不确认会影响什么、谁去确认、最迟什么时候。写不出影响范围的，说明它其实不是待确认，是没想清楚。

## 十、按模块类型定密度

不同模块在需求层的分量不一样，但都要能交差：

| 类型 | 适用 | 读者三分钟内要带走什么 |
| --- | --- | --- |
| 主链路模块 | 下单、履约、库存这类核心 | 链路怎么走、数量怎么控制、异常怎么收、哪一步卡人工 |
| 基础资料模块 | 主数据、组织、价格等前置 | 没有它下游不能做什么；改了、禁用了，新单和老单分别怎么办 |
| 交接边界模块 | 财务交接、外部系统集成 | 谁负责执行、谁负责记账、谁负责交接；拿不到结果时谁确认 |
| 公共能力模块 | 权限、审核、导入等共用机制 | 共用机制的适用边界；不在这里重定义业务规则，只写「谁去引用哪一条」 |

## 十一、写完怎么评

- 自检清单防漏章节，独立评审防「章节齐了但内容糊弄」。
- 独立评审分三线，各自只读、不改文件：**事实核对**（结论能不能指到来源、有没有无依据的断言、有没有和上游冲突）、**完整性**（按骨架和自检清单逐条打钩）、**语言**（术语是否统一、有没有内部说法和长句）。
- 固定输出格式：文件＋行号＋原文摘录＋问题类型＋依据＋严重度＋建议。
- 评审意见先逐条对原文再采纳（常见偏差：引用旧版本、与正文重复、把行业惯例当成本项目规则），分「会影响对错」和「文档卫生」处理，不采纳的写明理由。同一套办法见《业务设计文档方法（通用模板）》第八节。

## 十二、写作纪律

- 用中文写清楚，先给结论再讲理由；不堆术语，不写「触发：…。前置：…」这类电报式标签。
- 引用写完整文件名（如《采购业务管理需求分析》），不写「采购分析」「02/2」这类简写；编号可以保留，但要能看出属于哪份文档。
- 一条结论只有一个权威位置；重复出现的改引用。同一规则写三遍，改一处必漏两处。
- 头部保留版本表（版本 / 本次变化 / 状态），每次改动补一行；正文里不写变更过程。
- 改结论时同步三处：版本表、追溯矩阵与验收项、引用了这条结论的其他文档。
