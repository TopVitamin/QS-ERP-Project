# 应用设计四篇骨架（通用模板）

> 用途：给一个多模块业务系统定义「应用设计层」的骨架——业务规则已经写完，系统这边要回答哪几个问题、每个问题写在哪一篇、写到什么程度可以交给研发和测试。
> 用法：四篇的职责和骨架可以沿用；模块名、单据名、状态枚举换成自己项目的。字段清单不在这四篇里，它是单独一份产物。
> 来源：从 QS-ERP 项目的《系统与模块地图》《系统流程与单据交互》《实体对象关系》《单据与状态流转》四篇抽象出来，去掉了项目专有名词。

## 一、这四篇解决什么、不解决什么

业务设计回答「业务应该怎样运转」，技术设计回答「用什么库、什么框架、怎么部署」。四篇夹在中间，回答**系统怎样支撑业务**：

| 四篇回答 | 不在四篇里 |
| --- | --- |
| 有哪些系统和模块，各自能做什么 | 为什么做这件事、责任归谁（业务设计的活） |
| 每条链路里谁发起、经过哪些单据、状态怎么变 | 页面怎么画、按钮放哪、交互怎么反馈（原型和设计稿的活） |
| 有哪些对象、谁引用谁、数量怎么流动 | 字段名、字段类型、必填性、取值（字段清单的活） |
| 每类单据的状态、操作、条件、校验、联动 | 数据库、索引、事务、部署（技术设计的活） |

四篇写得好的标志：**研发照着能建表、能做接口；测试照着能设计用例；产品交接时不用再口述一遍系统怎么跑。**

## 二、四篇的分工与阅读顺序

| 篇目 | 回答什么 | 谁来看 |
| --- | --- | --- |
| 系统与模块地图 | 有什么系统、哪些模块、每个模块能做什么、资料谁建谁审谁用 | 所有人；新加入项目的人从这里入门 |
| 系统流程与单据交互 | 每条链路里系统之间怎么交互、单据状态怎么变、出问题怎么收 | 研发、测试 |
| 实体对象关系 | 流程里的对象是什么、谁引用谁、数量怎么流动、有什么不变量 | 研发、数据 |
| 单据与状态流转 | 每类单据的状态、可执行操作、前置条件、校验和联动 | 研发、测试、产品 |

写作和维护按这个顺序：**地图 → 流程 → 对象 → 状态**。先有系统边界，才谈得上链路；先有链路，才谈得上对象；先有对象，才谈得上状态。改动时反过来检查：改了状态要回头核对对象关系和流程表，改了模块职责要回头核对地图和依赖。

## 三、《系统与模块地图》

### 骨架（六节）

1. **系统分工**：本系统在其中扮演什么角色，外部系统各自定位，与谁交换什么。一张关系图加一张表（系统 / 定位 / 交换什么）。
2. **模块与功能清单**：模块分层图；每个模块一行，写「解决什么问题」和一级、二级功能点。
3. **模块依赖**：谁依赖谁、依赖什么。依赖方向应当单向，出现反向依赖要单独说明。
4. **资料流**：资料 / 创建 / 审核 / 分发 / 使用，五列。只回答「谁建、谁审、谁用」，规则细节链接到对应文档。
5. **本期范围**：做哪些、不做哪些，各写一段。
6. **文档索引与权威声明**：本套文档各回答什么，冲突时以哪一份为准、怎么判断。

### 深度标准

- 没参与过项目的人读完，能说出这个系统管什么、不管什么、和外部交换什么数据。
- 功能清单是**划范围**用的，不是页面清单，也不是排期表；一个功能点对应一件用户能感知的事。
- 外部系统的定位要写到「它负责什么、交给本系统什么、从本系统拿什么」，不写「对接第三方」。

### 常见漏项

- 只画了系统图，没写交换的具体内容，导致后面链路文档各说各的。
- 功能清单写成菜单名，研发看不出边界。
- 没写「不做」的部分，范围争议留到开发阶段。

## 四、《系统流程与单据交互》

### 骨架

按链路分节，一节一条链路，每节固定三段：

1. **一句话说明**：这条链路做什么，业务上一句话讲清。
2. **流程图**：图上每个矩形写「角色或系统 + 动作 + 单据」，箭头上标触发方式；自动动作和人工动作要能一眼分开。
3. **步骤表**：谁 / 动作与单据 / 状态变化 / 触发与校验 / 异常与处理，五列。

最后单独留一节给**跨链路的准备链和人工补充**：资料准备到什么程度才能建单；接口拿不到结果时谁来人工确认、走什么校验。

### 深度标准

- **谁**写角色或系统，不写具体人名；系统动的写「系统」。
- **状态变化**写「从什么 → 到什么」，中间态（推送中、取消中）也要写。
- **触发与校验**写清是自动还是人工、触发条件和拦下来的校验。
- **异常与处理**每行都要有落点，不能留「这里后续再说」。拿不到结果、回传校验失败、重复回传、推送失败，这四类至少各有一条。
- 研发照着能做接口和状态流转，测试照着能设计用例。

### 常见漏项

- 图里画了人工动作，表里没说是谁触发的，研发当成自动。
- 正常流程写得很细，异常只写一句「按异常处理」。
- 多个链路各写一遍通知单的推送规则，改的时候漏掉两处。共用规则应该只写一处，其他位置引用。

## 五、《实体对象关系》

### 骨架（八节）

1. **对象清单**：对象 / 类型（主数据、业务安排、执行指令、实际结果、数量状态）/ 识别口径（唯一性）/ 业务阶段。
2. **主数据与组织的关系**：关系图加说明，重点写归属不可变、分区不可跨这类硬约束。
3. **单据与结果的关系**：关系图加读法。至少写清三件事：安排生成指令、指令生成结果；**一次回传最多生成一张结果单**，零数量不生成；哪些关联是可选的。
4. **数量在对象之间怎么流动**：数量 / 落在哪个对象 / 怎么产生、怎么变。这一节是全篇重头。
5. **单据引用哪些主数据**：单据 / 引用 / 组织归属。
6. **追溯路径**：从哪里能追溯到哪里。
7. **一致性约束**：系统必须守住的不变量。
8. **对象的形态**：几条容易混的区分，逐条一两句话点破。

### 深度标准

- 数量一节要覆盖**全部**数量：订购、占用、可下推、累计实际、缺量、预占、可用、在途、冻结、退回额度，一个不落。每个数量说清落在哪个对象上、由什么动作产生、什么时候被消耗或释放。
- 一致性约束写成可判定的判断句：不超过上界、最多一对一、不能为负、未结束的一直占用。写不出判定方式的，就不是约束，是愿望。
- 「对象的形态」这一节专门处理同名不同义：草稿不是正式单据、当前价不是本单成交价、结果单才是唯一记账依据、外部单据是证据不是安排、数量状态不单独成单据。这些区分在需求评审里最容易被追问。

### 常见漏项

- 只列了对象，没写数量；结果到用的时候才发现「可下推」到底减哪些数没人说得清。
- 结果单和指令单的关系写成一比多，实际是一次回传只能对应一张结果单。
- 没有一致性约束，负库存、超量、重复记账这类问题在实现阶段才暴露。

## 六、《单据与状态流转》

### 骨架（九节）

1. **单据总表**：单据 / 所属模块 / 层级角色 / 状态字段 / 来源 / 下游。
2. **多状态字段的主单**（如审核状态 + 业务状态 + 计算列）：每个状态字段画一张状态图，再给「状态 × 操作」表。
3. **执行指令单**：单状态字段怎么串起发送和执行，同样给状态图和操作表。
4. **结果单**：审核与推送状态分别记录，推送失败不回滚业务。
5. **合并了安排与执行的单据**：一个状态字段怎么表达两层含义。
6. **数量口径**：把所有公式收在一处，每条公式一行，写清适用范围。
7. **回写规则**：结果单回写什么、什么时候回写；回写是单向的。
8. **权限怎么处理**：明确本篇不约定岗位和权限矩阵，只说明「权限不替代业务校验」。
9. **跨单据联动要点**：额度、占用、零数量怎么处理、结束与终止的分工、主单完结、唯一记账口径。

「状态 × 操作」表的四列：状态 / 可执行操作 / 前置条件与校验 / 结果与联动。

### 深度标准

- **状态枚举是闭集**，写进文档的取值就是全部取值；每个状态都要能答出「能做什么、不能做什么、下一步去哪」。
- 状态图上的每条箭头都能指出触发者：哪个人、哪个系统、哪个条件。
- 前置条件写具体：数量大于几、单价非空非负、上游是否启用、是否需要确认。
- 结果与联动写清「改了什么、生成了什么、推了什么」。
- 一篇里只写一遍的规则：**公式只在数量口径一节写全，其他位置引用**；权限只在权限一节出现。

### 常见漏项

- 状态字段之间互相覆盖（把审核状态和业务状态挤在一个字段里），后面加分支就要推倒重来。
- 只写了成功路径的操作表，取消、退回、失败重试、超时没有入口。
- 状态图和操作表对不上：图上有箭头，表里找不到对应操作，或者反过来。
- 数量公式散落在多条规则里，同一件事在不同章节算法不一致。

## 七、四篇共用的写法约定

- **每篇头注写清三件事**：用途（给谁看、用来干什么）、定位（和业务设计、字段清单、原型各是什么关系）、不写什么。
- **权威声明**：同一件事越靠近实现越有解释权。业务规则看业务设计，系统表达看四篇和模块需求文档，字段与枚举取值看字段清单，页面行为看原型。两边写得不一样时，先判断是「业务规则变了」还是「系统表达写错了」，再改对应的一份。
- **图与表不重复**：图给结构和顺序，表给条件和异常。图里能看懂的不再抄一遍文字。
- **枚举与命名统一**：单据名、状态名、字段名在四篇里保持同一套叫法；四篇是同一批人要读的，换个说法就要重新对一遍。
- **一处一权威**：同一条规则只在最合适的一篇里写完整，其他位置引用篇名和小节号。
- 用的是模型说明还是落地口径，要在头注里说清楚：**模型说明里的枚举和流程属于示例，落地口径以应用设计为准。**

## 八、自检清单（防漏章节）

- [ ] 四篇的头注都写了用途、定位和不写什么
- [ ] 模块清单覆盖全部模块，每个模块写了「解决什么问题」和功能点
- [ ] 每条链路都有流程和步骤表，异常列每行有落点
- [ ] 对象清单里有识别口径和业务阶段，数量一节覆盖全部数量
- [ ] 一致性约束都是可判定的判断句
- [ ] 状态枚举是闭集，状态图上每条箭头都有触发者，操作表与状态图对得上
- [ ] 数量公式集中在一处，其他位置只引用
- [ ] 权限、字段、页面没有混进这四篇
- [ ] 四篇之间引用的篇名和小节号都能对上，没有同一规则写两遍
- [ ] 「模型说明」和「落地口径」的身份在头注里标清楚了

## 九、六条硬条件（防糊弄）

自检清单防的是漏章节，这六条防的是「章节齐了但内容糊弄」。缺一条就不算写完。

1. **每篇能用一句话说明它回答什么。** 说不出来的，说明这篇在凑内容，拆掉或者合并。
2. **图和表说的是一件事。** 图讲结构和顺序，表讲条件和异常，两边对得上；只有图没有表，研发问不出「什么时候不行」，只有表没有图，评审看不出全局。
3. **状态和数量互不打架。** 每个状态下的数量算法都成立，每个数量在状态图里找得到产生和释放的位置。这一条对不上，实现阶段一定返工。
4. **异常有主。** 每类异常写清「谁发现、谁处理、处理不完怎么办」，不能停在「系统提示异常」。
5. **一处一权威。** 状态只在状态篇写全，对象关系只在对象篇写全，系统边界只在地图篇写全，其他位置引用。同一件事写三遍，改一处必漏两处。
6. **写明不写什么。** 每篇明确排除字段、权限矩阵、页面交互和技术实现，并指明它们各自在哪。边界不写清，四篇会慢慢长成第二个需求文档。

## 十、按系统角色定密度

不同系统的四篇分量不一样，但都要能交差：

| 系统角色 | 重点在 | 读者三分钟内要带走什么 |
| --- | --- | --- |
| 业务中枢（衔接多个外部系统） | 系统分工、链路交互 | 谁负责执行、谁负责记账、数据在系统之间怎么走 |
| 单体内业务系统 | 单据状态、数量口径 | 一笔业务从建单到结束会经过哪些状态，数量怎么算 |
| 集成或中间层 | 地图、异常处理 | 交换什么、失败了谁看得见、重试和去重怎么办 |
| 配置或基础层 | 对象关系、依赖 | 谁引用它、改了以后新老数据分别怎么办 |

## 十一、写完怎么评

- 自检清单防漏章节，独立评审防「章节齐了但内容糊弄」。
- 独立评审分三线，各自只读、不改文件：**事实核对**（系统表达能不能指到需求编号、有没有无依据的断言、有没有和业务设计冲突）、**完整性**（按骨架和自检清单逐条打钩）、**语言**（术语是否统一、图和表能不能对上）。
- 固定输出格式：文件＋行号＋原文摘录＋问题类型＋依据＋严重度＋建议。
- 评审意见先逐条对原文再采纳，分「会影响对错」和「文档卫生」处理，不采纳的写明理由。同一套办法见《业务设计文档方法（通用模板）》第八节。

## 十二、怎么维护

- 新增一条链路：先在地图里确认模块职责没变，再写流程，再补对象和数量，最后补状态；四篇一起改，不要只改一篇。
- 改一个状态：回头核对对象数量、关联的操作表和流程步骤；改一个数量公式：回头核对引用它的每条规则。
- 状态、字段或枚举调整如果和需求结论冲突，**先改需求，再改业务设计，最后改应用设计**，不要反过来。
- 四篇是交付物不是过程物：待确认清单、评审记录、讨论稿放在别处，写完不回填进这四篇。
