# 业务设计文档方法（通用模板）-V1

> 版本：V1
> 用途：给一个业务系统项目定义业务设计层写什么、写到什么程度算完。
> 用法：把 [项目名]、[业务域] 换成自己的；骨架和检查项可以直接沿用。七部分是推荐骨架，域很薄时可以合并，不要为了凑章节而凑章节。
> 共用规则见《文档通用规则（通用模板）-V1》。本文只讲业务设计层独有的东西。

## 一、业务设计和应用设计的分工

业务设计回答业务应该怎样运转：谁在什么情况下做什么，产生什么结果，下一步交给谁。

应用设计回答系统怎样支撑这些业务：单据关系、状态机、字段、权限、页面和交互。

| 这类问题属于业务设计 | 这类问题属于应用设计 |
| --- | --- |
| 一笔约定允许分多次执行 | 系统怎么组织主单、执行单与结果单的关系 |
| 剩余部分可以终止，已经安排出去的怎么处理 | 关闭操作的条件、状态和校验怎么设计 |
| 什么实际结果引起库存或账务变化 | 系统怎么接收、校验并记录 |
| 谁有权确认或更正结果 | 对应页面、操作和接口怎么落实权限 |

业务设计里出现单据名和业务阶段（生效、履约、结束）不算越界。但状态枚举、按钮、字段、页面文案和系统内部标识不进这一层，需要时引用应用设计文档。下推、回写、执行标识这类系统内部说法，要换成业务上听得懂的说法。

一条链路确认了就可以进入应用设计，不必等所有业务域都写完。草图和原型可以拿来讨论，不能当作业务依据。

## 二、这一层放哪些文件

- **一篇总览**：业务域地图、参与方与域的关系、链路与交接清单、公共术语、还需要收口的事项。
- **每个业务域一篇**：默认一域一文，内容复杂再拆。
- 编号发出后不改号，新增业务域追加编号，不预建空文件。
- 过程物（待确认清单、评审记录、讨论稿）不放交付目录。它们会和正文重复，也会过期。
- 总览里单独写一份阅读顺序，并注明文件号不是阅读顺序。

## 三、每个业务域写什么

写到什么程度算完，判断只有一条：下游据此能不能决定做什么、不做什么。

每个业务域写七部分。总览不套这七部分，但要覆盖域地图、参与方、链路与交接、公共术语、还需要收口的事项这几项。

**1. 业务定位与范围。** 解决什么问题、服务谁、和谁交接、一期明确不做什么。边界要指到上游文档和编号。

**2. 参与角色。** 做成矩阵：负责什么、在哪些对象上做什么、必须交出什么。还没定的岗位显式标出来。权限只引用公共规则，不在这里设计权限矩阵。

**3. 核心业务场景。** 覆盖主场景、分支场景、辅助场景、异常场景四类。每个场景写触发、前置、参与方、主要步骤、分支与判断点、业务结果、后续环节。只写「允许分次执行」这类结论句不算场景。

**4. 核心业务流程。** 分主流程、分支流程、辅助流程、异常流程。写清谁在什么条件下做什么、产生什么结果、交给谁。关键交接点要唯一可指认。不写页面跳转和接口调用。

**5. 业务对象及关系。** 对象清单写含义、如何识别、业务阶段、阶段结束时的结果。关系表写基数、可选性、追溯路径。数量流向要写清每个量落在哪个对象上，怎么累计、怎么回补、怎么释放，不重不漏。没有数量流动的域，写对象关系就行。

**6. 核心业务规则。** 写成判断句，条件到结果要说通。写清适用范围和例外。这个域特有的规则写全，引用上游的只链接不复制。每条规则要能反推出验收。

**7. 特殊与异常场景。** 写四件事：触发条件、业务后果、责任方、能不能恢复以及怎么恢复。明确一期不处理的情形。

另外两件放在固定位置：文首一句话说明用途，并注明输入来源和确认状态；文末按处理阶段列出待确认事项。

场景和流程容易互相抄。场景一节写触发和后续环节，当目录用；步骤放流程，后果放异常。域很薄、场景只有一两条时，可以把场景并进流程，不要空着第三节充数。

## 四、逐条自查

- [ ] 四类场景齐全，都能举出这个域的真实例子（域很薄、已经并掉场景一节的，在流程里仍能指认这四类）
- [ ] 每个场景都有触发、前置、参与方、步骤、分支、结果、后续环节
- [ ] 角色表覆盖全部参与方，没定的岗位已经显式标注
- [ ] 对象关系有基数和可选性；有数量的，沿对象链条能对上
- [ ] 关键交接点唯一：上游给什么，这个域交给下游什么
- [ ] 规则可判定，没有视情况、按需这类说法
- [ ] 系统机制（状态枚举、按钮、字段、页面显示）没有写进这一层，需要时只引用
- [ ] 待确认事项只留会改数量、责任或算法的问题，并标注处理阶段
- [ ] 全文引用的外部结论都能指到具体文档和编号

## 五、容易糊弄的地方

上面的清单防的是漏章节，下面这几处防的是章节齐了但内容糊弄。

**1. 开篇缺一句人话和一张交接表。** 上游给什么、这个域交出什么，两份都要列全，列名全项目统一；开篇还要一句话说明这个域是干什么的。

**2. 场景和流程互相抄。** 同一段话在场景、流程、异常三节各写一遍。场景写触发和后续环节，步骤进流程，后果进异常。

**3. 同一件事在多处写全。** 结束和取消的业务含义只在流程里写，公式只在规则里写，异常四要素只在异常一节写。其他地方引用，不要重抄。

**4. 有数量流动却没做时间序走查。** 一个故事按时间往下走，分支要标成分支，不能接在主链后面装成下一步。走查要专门拆开这个域最容易混的那组量。没有数量的域，走查交接点即可。

**5. 规则标题不是结论。** 标题要写成能一眼看出结论的判断句，比如「进度达到上限不等于终止」。写成「数量校验规则」这种，读者看完不知道结论是什么，也没法反推验收。

**6. 待确认表里混进了别的东西。** 只留会改数量、责任或算法的事。待确认事项怎么读、怎么升级，解释只放在总览一处，各业务域不要重复贴。

## 六、按域类型定密度

不同类型分量不一样，但都得写到能交差。下面几种是常见类型，不是必须按这四类拆域。

| 类型 | 常见适用 | 读者该记住的一条 |
| --- | --- | --- |
| 总览 | 全局 | 域怎么接，先读哪篇，哪些词全项目同义，哪些还没收口 |
| 履约 | 有约定、安排、实际结果的主链路域 | 这三层怎么分开，终止怎么走，一条带数量的时间线 |
| 准备 | 基础资料、价格、配置等前置域 | 没有这些就不能建单；改了、禁用了，新单和老单分别怎么办 |
| 边界 | 财务交接、外部集成等 | 谁负责执行、谁负责记账、谁负责交接；拿不到结果时谁确认 |
