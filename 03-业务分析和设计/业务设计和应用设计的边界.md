# 业务设计和应用设计的边界

## 方法来源与取舍

本项目的思路来源于《大话软件工程》，借鉴其中业务设计与应用设计的分层思想，并结合 QS-ERP 的业务场景和产品经理的维护方式，做了大量精简与调整。

本文是本项目采用的工作方法，不是原书内容的复述。我们保留“先理解和设计业务，再确定系统如何支撑”的核心思路，将应用设计统一放在 `04-产品设计方案` 中，不再单独增加一层文档；业务设计按业务域组织，默认一域一文，复杂后再拆。

## 业务设计与应用设计

**业务设计回答：业务应该怎样运转？**

说明业务目标、范围、参与角色、业务流程、对象关系、关键规则和异常处理。重点是：谁在什么情况下做什么，产生什么结果，下一步交给谁。

**应用设计回答：系统怎样支撑这些业务？**

将业务要求落实为系统功能、单据关系、状态机、字段、权限、页面和交互。接口与数据的业务要求在此明确，数据库、索引、事务等具体实现由技术设计承接。

| 业务设计 | 应用设计 |
| --- | --- |
| 一次采购允许分批收货 | 系统如何组织订单、通知与入库结果的关联 |
| 剩余履约可以终止，已安排的交付如何处理 | 关闭按钮、操作条件、状态和校验如何设计 |
| 什么实际业务结果引起库存变化 | 系统如何接收、校验并记录该结果 |
| 谁有权确认或更正业务结果 | 对应页面、操作和接口如何落实权限 |

以上是边界示例，具体规则以本项目已确认需求为准。

业务设计可以出现采购订单等业务凭证，也可以说明生效、履约、结束等业务阶段；不因出现单据或状态名称就归为应用设计。业务层解释其含义与后果，应用层决定如何用系统表达和控制。

业务蓝图不展开系统功能，但应说明范围外的业务交接，例如将实际结果交给财务处理。已有系统分工作为约束引用，不在这里重做系统架构。

业务正文按实际内容维护，不预建空文件。不另设 README、参考资料和讨论稿。

公共术语先放在业务蓝图中，业务域特有概念放在各自正文中。已存在的全局规则和模块规则直接引用，不另建重复的公共规则文件。价格等主题是否独立成文，按实际内容决定，不机械复制需求目录的全部模块。

每份业务域设计默认包含七部分：

1. 业务定位与范围。
2. 参与角色。
3. 核心业务场景。
4. 核心业务流程。
5. 业务对象及关系。
6. 核心业务规则。
7. 特殊与异常场景。

文首用一句话说明用途，并注明输入来源与确认状态；文末按处理阶段列出待确认事项。影响数量、责任或处理结果的业务问题，应在对应功能方案定稿前确认；页面、接口与技术细节随后承接。业务阶段和跨域交接放在相应章节，不为分类额外拆文件。

## 如何推进与维护

输入来自 `01-全局背景信息` 和 `02-需求调研和分析`。03 将已确认结论串成可以完整阅读和按场景走查的目标业务设计，不重复现状调研，也不把待确认事项写成既定规则。

先形成一版业务蓝图，再用采购业务设计做样板，确认结构够用后扩展销售与库存。蓝图讲全局关系，业务域正文讲具体运行；未覆盖结算付款的链路，应明确范围，不称为完整交易闭环。

正文保留理解业务所需的解释，详细规则链接已有权威位置，避免整段重复维护。发现缺口时集中列出；新的业务决定确认后，同步相关需求依据，不让不同目录各有一套结论。

一条业务链路确认后即可进入应用设计，无须等全部业务域写完。草图和原型可以辅助讨论，但不能替代业务依据。后续发现影响业务结果、责任或口径的问题，回到业务设计确认；系统表达与实现问题在应用设计和技术设计中处理。
