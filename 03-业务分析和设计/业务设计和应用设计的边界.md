# 业务设计和应用设计的边界

> 版本：V0.4｜更新日期：2026-09-15｜状态：方法说明，随本目录推进更新。
> 本版同步主数据准备文档改名，以及组织退场后的业务域清单。业务结论仍以各业务域正文为准，本文不重复。

## 方法来源与取舍

本项目的思路来源于《大话软件工程》，借鉴其中业务设计与应用设计的分层思想，并结合QS-ERP的业务场景和产品经理的维护方式，做了大量精简与调整。

本文是本项目采用的工作方法，不是原书内容的复述。我们保留“先理解和设计业务，再确定系统如何支撑”的核心思路，将应用设计统一放在 `04-产品设计方案` 中，不再单独增加一层文档；业务设计按业务域组织，默认一域一文，复杂后再拆。

## 业务设计与应用设计

**业务设计回答：业务应该怎样运转？**

说明业务目标、范围、参与角色、业务流程、对象关系、关键规则和异常处理。重点是：谁在什么情况下做什么，产生什么结果，下一步交给谁。

**应用设计回答：系统怎样支撑这些业务？**

将业务要求落实为系统功能、单据关系、状态机、字段、权限、页面和交互。接口与数据的业务要求在此明确，数据库、索引、事务等具体实现由技术设计负责。

| 业务设计 | 应用设计 |
| --- | --- |
| 一次采购允许分批收货 | 系统如何组织订单、通知与入库结果的关联 |
| 剩余履约可以终止，已安排的交付如何处理 | 关闭按钮、操作条件、状态和校验如何设计 |
| 什么实际业务结果引起库存变化 | 系统如何接收、校验并记录该结果 |
| 谁有权确认或更正业务结果 | 对应页面、操作和接口如何落实权限 |

以上是边界示例，具体规则以本项目已确认需求为准。

业务设计可以出现采购订单等业务凭证，也可以说明生效、履约、结束等业务阶段；不因出现单据或状态名称就归为应用设计。业务层解释其含义与后果，应用层决定如何用系统表达和控制。

业务蓝图不展开系统功能，但应说明范围外的业务交接，例如将实际结果交给财务处理。已有系统分工作为约束引用，不在这里重做系统架构。

## 每篇怎么写：七部分的深度标准

业务域设计默认包含七部分。下面是每一部分“挖到什么程度算够”的标准，判断依据只有一条：**产品设计阶段据此能决定哪些要做、哪些不做。**

### 1. 业务定位与范围

- 回答：这个业务域解决什么问题、服务哪些使用方、与哪些域有交接、一期明确不做什么。
- 范围边界要指到具体来源文档和编号（例如《采购业务管理需求分析》PUR-FR01），不自行扩大或缩小。

### 2. 参与角色

- 列出全部参与角色。每个角色写清：负责什么、对哪些对象做哪些业务动作、交出什么结果。
- 未确认的岗位、责任人、审核人显式标注“待确认”，不省略、不假设。
- 权限只引用公共规则（[强盛ERP全局业务规则与约束](../01-全局背景信息/4.强盛ERP全局业务规则与约束.md) §五、COM-FR01、COM-FR02），不在这里设计角色权限矩阵。

### 3. 核心业务场景

- 场景覆盖四类：主场景、分支场景、辅助场景、异常场景，每类至少能举出这个业务域的真实例子。
- 每个场景写：触发事件、前置条件、参与方、主要步骤、分支与判断点、业务结果、后续环节交给谁。
- 只写“允许分批”、“可以取消”这类结论句不算场景，那是规则或结果。

### 4. 核心业务流程

- 主流程：端到端步骤表，写“谁在什么条件下做什么、产生什么业务结果、交给谁”。
- 分支流程：同一主流程下的不同走法（分批、少收、超量、拒收、延期、终止等）分别说明。
- 辅助流程：让主流程跑得起来的准备与跟进动作（资料准备、跟单、通知创建、期限维护等）。
- 异常流程：失败、差异、超时、重复发生时业务如何处理，与第7部分的分工保持一致。
- 关键交接点唯一可指认：哪张单、哪个数量、由谁确认、交给哪个角色或哪个系统。
- 不写页面跳转、按钮和接口调用；流程的表述单位是“业务动作与结果”，不是“操作与响应”。

### 5. 业务对象及关系

- 对象清单：每个对象的业务含义、如何唯一识别（业务识别方式，不是编码规则）、业务阶段。
- 对象关系：一对多／多对一／可选关联／是否可变，以及跨对象追溯路径（例如退货能追到哪一次出库）。
- 数量和每个量怎么变：订购量、通知量、实际量、额度、可用量分别落在哪个对象上，如何累计、回补、释放，确保不重不漏。
- 状态只写业务阶段及其后果；系统枚举、字段和状态机在应用设计中定义。

### 6. 核心业务规则

- 每条规则可判定：条件 → 结果，并写清适用范围和例外。
- 区分两类：这个业务域特有的规则写全；引用全局或模块的规则只链接，不复述。
- 规则要能反推出验收场景，不用“视情况”、“按需”这类无法验收的表述。

### 7. 特殊与异常场景

- 每条写四要素：触发条件、业务后果、责任方、能否恢复及恢复方式。
- 明确一期不处理的情形，避免读者误以为遗漏。

文首用一句话说明用途，并注明输入来源与确认状态。文末按处理阶段列出待确认事项（事项／影响的数量、责任或算法／来源／处理阶段），与《强盛科技一期业务蓝图》§七 的收口要求一致，不重复列出已确认结论。业务阶段和跨域交接放在相应章节，不为分类额外拆文件。

00-业务蓝图不套用七部分，但应覆盖：业务域地图、参与方与业务域的关系、链路与交接清单、公共术语，以及当前仍需收口的事项。

## 写完一篇的自检清单

- [ ] 四类场景都有，且都能举出该业务域的真实例子（主／分支／辅助／异常）
- [ ] 每个场景都有触发、前置、参与方、步骤、分支、结果、后续环节
- [ ] 角色表覆盖全部参与方，未定岗位已显式标注
- [ ] 对象关系有基数和可选性；数量沿对象链条能对上，不重不漏
- [ ] 关键交接点唯一：上游给什么、这个业务域交给下游什么，文中都能指到
- [ ] 每条规则可判定（条件 → 结果），没有不可验收的表述
- [ ] 系统机制（状态枚举、按钮、字段、执行标识、页面显示）没有写进本层，需要时只做引用
- [ ] 待确认事项只保留真正会改变数量、责任或算法的问题，并标注处理阶段
- [ ] 全文引用的外部结论都能指到具体文档与编号

清单不通过时先补正文，不用“待确认”掩盖缺口。

## 一篇算写完的六条硬条件

自检清单防的是漏章节，这六条防的是“章节齐了但内容糊弄”。缺一条就不算写完。

1. **开篇一句人话 + 一张交接表。** 上游给什么、这个业务域交出什么，列名全目录统一。
2. **第三节只做场景目录。** 只写触发和后续环节；步骤进第四节，后果进第七节，不要回潮。
3. **第四节必须有一条时间序走查。** 一个故事按时间往下走，分支标成“分支”，不接在主链后面装成下一步；走查要拆开这个业务域最容易混的那组量。
4. **第六节的规则必须是判断句。** 标题就是结论（如“收货进度不等于终止”），能反推出验收；依据只点02的编号，不抄02。
5. **一篇一个权威位置。** 关闭和取消的业务含义只在第四节，公式只在第六节，异常四要素只在第七节。
6. **文末待确认只留会改数量、责任或算法的。** “业务先确认”的解释只放在《强盛科技一期业务蓝图》§七，各业务域不重复贴。

不同域的职责不同，密度也不一样，但都要能交差：

| 类型 | 适用 | 读者三分钟内要带走什么 |
| --- | --- | --- |
| 总览 | 业务蓝图 | 域怎么接、先读哪篇、哪些词全项目同义、哪些还没收口 |
| 履约 | 采购、销售与履约、库存与仓储 | 约定、安排、实际怎么分开，终止怎么走，一条带数量的时间线 |
| 准备 | 价格、主数据 | 没有这些就不能建单；改了、禁用了，新单和老单分别怎么办 |
| 边界 | 结算与业财、集成协作 | 谁负责执行、谁负责记账、谁负责交接；拿不到结果时谁确认 |

## 如何推进与维护

输入来自 `01-全局背景信息` 和 `02-需求调研和分析` 两个目录。业务设计把已经确认的结论串成可以完整阅读、能按场景走查的目标业务，既不重抄现状调研，也不把待确认事项写成既定规则。

七个业务域都已成文：采购、销售与履约、库存与仓储是主链，价格和主数据是前置准备，结算与业财、集成协作收尾。蓝图讲全局关系，业务域正文讲具体运行。新增业务域或者大幅改版时，沿用同一套深度标准和自检清单。

**同一件事尽量只有一个权威位置，但不禁止副本。** 全局跨模块规则在《强盛ERP全局业务规则与约束》；单据分层模型在《强盛ERP的单据分层设计》（模型说明，枚举和流程属示例）；模块规则与验收在02-需求调研和分析；系统表达（状态、操作、校验）在 `04-产品设计方案` 的系统架构与流程和PRD。本目录只写业务过程和各业务域特有的规则。

为了说明、沟通和补充，允许同一事实出现在多份文档里，但要满足三条：指明谁是owner；副本标注“说明／示例”；按事项归属写明权威位置，冲突处理遵循根AGENTS.md。满足不了这三条，就变成了两个真相源，改一处必漏一处。

**改结论要同步。** 本目录内部改口后，同步[强盛科技一期业务蓝图](00-业务蓝图.md) §六、关联业务域的交叉引用，以及需求分析的对应依据；需求分析里还没确认的，在待确认事项里写明，不用业务设计单方面定案。

发现缺口时集中列出；新的业务决定确认后，同步相关需求依据，不让不同目录各有一套结论。

一条业务链路确认后即可进入应用设计，无须等全部业务域写完。草图和原型可以辅助讨论，但不能替代业务依据。后续发现影响业务结果、责任或算法的问题，回到业务设计确认；系统表达与实现问题在应用设计和技术设计中处理。
