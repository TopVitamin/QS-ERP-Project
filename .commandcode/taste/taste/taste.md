# Taste
- 用中文沟通：用户以中文提出需求，期望中文回复。Confidence: 0.6
- 希望 agent 先区分"可直接执行的机械修复"和"需要用户拍板的事项"，对有判断/口径争议的改动先问清再动手，而不是默认全改。Confidence: 0.75
- git 提交必须由用户明确授权，agent 不自行 commit（改完留待用户决定提交时机与拆分）。Confidence: 0.75
- 触及线上部署链路的改动（如 CI / deploy.yml）需单独确认后才执行。Confidence: 0.6
- 遇到"局部文档与全局权威规则冲突"时，倾向选推荐方案即按全局口径统一，而不是维持现状走过场。Confidence: 0.65
- 偏保守最小改动：能用改措辞/留待确认解决的就不删文件、不动既有素材（如保留草稿图、退役模板只留 git 历史）。Confidence: 0.55
- 期望"先诊断、后修改"的两阶段流程：默认只做只读的全量分析与诊断报告，未收到用户确认前不删除 / 移动 / 合并文件，也不做大规模修改。Confidence: 0.8
- 需要用户决策的问题必须整理成选择题（选择题/多选项形式，说明各方案影响）逐条拍板，明确禁止用开放式问题让用户自由回复（用户曾明确纠正「给我一些选择题，不要用这样一个问题让我回复」）；明确、低风险的项允许批量处理。Confidence: 0.9
- 诊断 / 评审报告要有固定分类结构（保留为核心上下文 / 归档为历史资料 / 建议删除 / 重复可合并 / 错误与冲突 / 治理建议 / 可直接修复 / 待确认），并给出下一步建议。Confidence: 0.6
- 关心 AI 上下文治理：希望文件标明有效性与是否为历史资料，并规定冲突时的可信来源优先级，以减少 AI 理解歧义；历史/草稿素材要显式标注「AI 不主动读取、不作为依据」。Confidence: 0.65
- 会主动授权 agent 先干「可自行处理」的低风险/机械修复，不必逐项等确认；期望 agent 自己先分清「可自行处理」与「需用户确认」两类清单再开工。Confidence: 0.75
- 删除文件（及其他不可逆操作）必须先列清单、经用户确认后才执行，即使处于「可自行处理」模式也不例外。Confidence: 0.8
- 文档去重遵循「单一事实来源」：同一结论只在唯一权威处维护（如全局蓝图 §七），其他文档用互指代替复制；各域文档文末待确认表只列本域真正未决项，已确认的结论不重复。Confidence: 0.65
- 新模块的业务口径向已有同类模块对齐，保持对称/一致（如销售退货与采购退货同口径），而不是各写一套。Confidence: 0.6
- 示例与 Demo 数据要求算术自洽：明细、关联单据与汇总数字之间前后一致，不出现自相矛盾的占位数字。Confidence: 0.6
- 通用模板（方法文档/模板）保持跨项目可复用，不在其中写死项目专属内容；项目落地差异用一句互指指向项目内权威文档。Confidence: 0.55
- 对 agent 已给出「推荐默认值」的事项，用户常直接答复「处理一下 A1–A6」式的简短授权，不再复述选择、也接受 agent 按默认推荐执行（如命名统一取推荐写法）。Confidence: 0.6
- 要求全项目术语/角色命名收敛为单一写法，不允许两套叫法并存；统一时选与多数文档一致、更短的那个。Confidence: 0.6
- 交付/阶段性完成后，期望 agent 主动列出「需要用户拍板的分叉」与「发现的上游不一致」两类遗留问题供确认，而不是只汇报已完成；上游文件的问题不擅自修改，标注出处交由评审定夺。Confidence: 0.65
- 常用基础能力（草稿删除、列表正式导入等）要求一期就提供并写成正式功能，不接受「本期不提供 + 待确认」的推迟写法；确认后需同步规则、状态矩阵、页面骨架、Demo 与验收全链路。Confidence: 0.8
- 对不确定的行话/自造术语（如「全部退足」）会直接要求先解释再决定：回复决策时应先用平实语言解释术语含义，再落结论。Confidence: 0.7
