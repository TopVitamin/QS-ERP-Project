## 一、项目级分析结论

强盛科技自研ERP一期定位为后台业务中枢，不替换领星、聚水潭、第三方WMS或金蝶。系统统一维护或引用业务基础资料，处理采购、销售、价格和库存业务，接收仓库及外部SaaS的实际结果，维护逻辑仓库存，并把七类已审核结果单逐单推送金蝶。

本期重点是把基础资料、业务单据、仓储执行结果、库存记账和业财传递串成一条主链，不只建几套采购或库存页面。详细定位、系统分工和一期范围见[强盛科技ERP项目的背景信息](../../01-全局背景信息/2.强盛科技ERP项目的背景信息.md)；跨模块强约束见[强盛ERP全局业务规则与约束](../../01-全局背景信息/4.强盛ERP全局业务规则与约束.md)。

当前九个模块均已形成需求分析稿。采购、库存、销售、价格、业财、系统集成和公共能力等主要业务边界已经形成，可以继续支撑业务设计和产品设计；部分字段、状态、权限、金额、接口和实施事项仍需在对应阶段确认。本文不把这些后续事项描述为已经定稿，也不把Mock或原型视为真实接口和生产行为验证。

### 2.2 项目核心链路

```plain
商品、供应商、仓库、客户、物流与辅助资料就绪
    ＋ 采购价、销售价准备
        ↓
采购／销售／退货／其他出入库／仓间调拨
        ↓
通知单，或直接承担执行指令的订单、申请单
        ↓
仓库、WMS 或 SaaS 执行并返回实际结果
        ↓
ERP 生成或接收结果单 → 对应逻辑仓库存记账
        ↓
七类已审核结果单逐单推送金蝶
```

领星、聚水潭负责的外部ToC不重新走ERP的履约主链。ERP保留原始订单与实际结果的关联，校验通过后记录结果、变更对应逻辑仓库存并推送金蝶。Shopify独立站订单直接进入ERP，由人工选仓、选物流和审核，审核后自动推送仓库执行。

各链路采用三层、两层或一层单据，取决于业务是否需要分别记录安排、执行和实际结果；不能强制所有业务使用相同层数。完整分层及状态联动见[强盛ERP的单据分层设计](../../01-全局背景信息/5.强盛ERP的单据分层设计.md)。

## 三、一期范围与共同原则

### 3.1 一期范围

一期包含九个模块：商品与主数据、采购、库存、销售、结算与业财、价格、系统集成、公共能力、辅助资料。一期按单主体建设，不建组织档案；多主体之间的购销属于后续需求。系统集成和业财推送随各业务链路同步建设，不等全部业务页面完成后再统一补做。

一期明确不建设生产制造、自研WMS、自研SRM、中央OMS、全渠道统一调度、多主体之间的购销与调拨、ERP财务核算台账和完整自动履约等能力。切换、并行运行、期初初始化与历史迁移另行制定实施方案，但不表示上线可以没有库存起点。完整纳入和排除范围以[项目背景第三、四章](../../01-全局背景信息/2.强盛科技ERP项目的背景信息.md)为准。

### 3.2 跨模块共同原则

1. **业务对象统一。** 商品只管理成品SKU；五类ERP主数据由主数据模块统一维护。业务模块引用统一档案，不重复建立同类主数据。
2. **库存按实际结果记账。** 订单、申请和通知本身不改变即时库存；实际入库增加、实际出库减少。预占和冻结只限制可用数量，不直接改变即时库存；不允许负库存。
3. **安排、执行和结果分层。** 不同业务按需要采用三层、两层或一层单据。执行指令由系统自动发送仓库，不要求业务人员逐单点击推送；实际结果由结果单记录。
4. **价格保留交易快照。** 商品建档初始化采购价和销售基准价，后续通过价格调整单变价；已保存业务单据保留自身价格和税率，后续调价不追溯历史成交。
5. **外部ToC不重复履约。** 领星、聚水潭继续抓单和履约，ERP归集原订单和实际结果；匹配或库存校验失败时不记库存、不推金蝶，修复后继续原记录。
6. **金蝶继续承担财务核算。** ERP只推送七类已审核结果单，不建设应收应付、收付款、核销、凭证、总账或存货成本核算；推送失败不回滚已生效ERP业务和库存。
7. **权限不能绕过业务校验。** 一期采用RBAC，允许本人审核本人创建的数据；导入仍遵循对象原有的提交审核规则，不能绕过库存、金额和状态校验。

以上是项目级索引，不替代对应模块的适用条件、例外和待决策事项。文档之间出现冲突时，按各自的职责判断：背景看[强盛科技ERP项目的背景信息](../../01-全局背景信息/2.强盛科技ERP项目的背景信息.md)，模块规则看各模块需求分析稿，业务设计看 `03-业务分析和设计`，字段与PRD看 `04-产品设计方案`，页面行为以 `09-产品原型` 为准。

| 性能、可用性、技术安全、容量和接口服务指标 | 系统级未定义 | 当前需求资料没有给出可核验数值，不在本总览编造；应由产品与技术在研发和测试交接前形成非功能要求 | 技术方案及研发测试交接前 |

## 五、整体验收与下游使用

### 5.1 需求阶段整体验收原则

本节定义需求体系的整体验收依据，不表示当前已经通过真实接口或生产验收。具体功能仍按各模块 `AC` 验收。

| 验收维度 | 通过条件 |
| --- | --- |
| 范围完整 | 九个模块均有调研稿和分析稿，纳入与排除范围能够回到项目背景和模块文档定位 |
| 职责清楚 | ERP、领星、聚水潭、Shopify、WMS、仓库和金蝶的业务边界不互相替代，不把SaaS履约、仓内作业或财务核算错误归入ERP |
| 主链完整 | 基础资料和价格能够支撑业务建单；执行结果能够形成结果单和库存变化；七类已审核结果单能够进入金蝶推送范围 |
| 数量与金额一致 | 预占、实际库存、分批和缺量按各模块规则处理；业务单据价格快照和外部ToC来源金额不被后续调价错误覆盖 |
| 需求可追溯 | 模块场景与问题能够追溯到业务需求、功能需求和验收标准；新增或删除功能时同步更新矩阵和验收 |
| 未决项可控 | 未确认的业务、字段、接口和实施事项写明影响及确认阶段，不把Mock、原型或经验当成已验证结论 |

### 5.2 建议阅读顺序

1. 先读[项目背景](../../01-全局背景信息/2.强盛科技ERP项目的背景信息.md)和[系统定义与上下游链路](../../01-全局背景信息/3.强盛ERP的定义和上下游链路.md)，理解为什么建设及各系统分工。
2. 再读本总览，确认模块职责、核心链路、一期范围和跨模块待确认项。
3. 进入上表对应的模块需求分析稿查看目标规则、功能、依赖和验收；需要核实现状时返回对应调研稿。
4. 业务设计继续进入 `03-业务分析和设计`，字段与PRD进入 `04-产品设计方案`，页面表现进入 `09-产品原型`；下游资料不得反向创造或改写尚未确认的需求规则。
