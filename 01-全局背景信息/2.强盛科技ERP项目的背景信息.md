## 一、为什么做

### 1.1 触发点

2020年下半年，强盛先把前台渠道SaaS升级为**领星**（Amazon / 跨境）和**聚水潭**（天猫 / 京东），各自渠道内的运营和履约问题解决了。

但跑了几个月后，后台主链条仍然断在财务ERP、领星、聚水潭和多个仓储节点之间。公司需要的不是再买一个垂直SaaS，而是**一个自己能掌控的后台业务中枢**，把主数据、采购、销售、库存和业财编排收回来，同时衔接领星、聚水潭和财务ERP。

### 1.2 立项要解决的五个缺口

| 缺口 | 立项时的表现 | 一期要对准什么 |
| --- | --- | --- |
| 采购主链条分散 | 财务ERP有基础PO和入库，但深圳仓无专业WMS，实物收发靠财务ERP简易模块和现场纸单；跟单靠微信，入库账实易脱节 | 自研ERP收口采购主链条，**一期引入第三方WMS** 承接国内仓实物作业，ERP下发采购收货通知并接收实际结果 |
| 库存视图分散 | 领星、聚水潭、财务ERP、各仓各记各账；国内仓采购入库后，B2B侧看不到可靠可用量 | ERP维护自营及第三方仓对应的逻辑仓库存，包含ToC实际出入库记账；提供仓间调拨及库存比对，不扩展全量库存双向同步 |
| B2B业务灵活多变 | 临时改量改价、分批发货、现场提车、账期结算各异；当时财务ERP的开单方式未覆盖这些场景 | 建设专门的B2B销售模块，承接灵活订单与发货 / 出库单据 |
| ToC与后台割裂 | 订单和履约在领星 / 聚水潭，采购备货和财务看不到完整链路 | ToC继续在外部履约，ERP保留原始订单与实际结果关联，并完成库存记账及业财推送 |
| 主数据与业财口径不一 | 多系统SKU编码各异，月结靠Excel拼表 | 五类业务主数据在ERP维护；已审核结果单逐单推送财务ERP |

### 1.3 为什么自研，而不是再买一套或继续补财务ERP

| 方案 | 项目中的用途 | 本项目的取舍 |
| --- | --- | --- |
| 领星 / 聚水潭 | 各自渠道运营和履约 | 保留前台执行及仓储中转，跨系统采购、库存与业财主链由ERP承接 |
| 金蝶云·星空 | 财务核算、基础进销存 | 保留财务核算底座，采购、销售业务入口逐步迁入ERP |
| 再采购一套ERP | 候选建设方式 | 本项目已选择自研后台中枢；不据此判断市场上不存在适用产品 |

因此一期策略是：**前台渠道继续分治，财务ERP继续做财务底座，中间缺的后台主链条从零自研。**

### 1.4 立项时各系统分工（现状）

自研ERP **尚未建设**，深圳主仓也**还没有专业WMS**。当时各系统分工如下：

```plain
领星 / 聚水潭  →  各自渠道 ToC 抓单与履约
财务ERP           →  B2B / 采购基础进销存 + 财务核算；深圳仓简易仓储记账
深圳主仓现场   →  收货、拣货、装柜；无 WMS，与财务ERP、前台系统库存不联动
独立站         →  未接入现有系统
自研 ERP       →  不存在
```

### 1.5 从现状到一期目标

立项时的断点，和一期要建成的能力，不是同一件事。读后面章节时，注意下面两个关键变化：

| 维度 | 立项时（现状） | 一期建成后（目标） |
| --- | --- | --- |
| 国内仓实物作业 | 财务ERP简易仓储 + 现场纸单，无专业WMS | **引入第三方WMS** 执行收货 / 上架 / 拣货；ERP下发指令、接收回写（不是自建WMS项目） |
| 库存视图 | 领星、聚水潭、财务ERP、各仓各记各账 | ERP按逻辑仓维护自营及第三方仓库存，包含ToC实际结果；支持预占冻结、仓间调拨、其他出入库和库存比对 |

一期通过自研后台中枢与仓储系统衔接，贯通采购、销售、退货、库存变动和财务ERP结果推送，并归集外部ToC实际结果。

## 二、这个项目是什么

| 项 | 说明 |
| --- | --- |
| 项目名称 | 强盛科技自研ERP建设项目（一期） |
| 建设方式 | 从零新建，不是升级旧ERP，也不替换领星、聚水潭或财务ERP |
| 核心定位 | **后台业务中枢**：统一主数据，承接采购 / 销售业务单据，维护逻辑库存，将已审核结果单逐单推送财务ERP |
| 与前台关系 | 领星、聚水潭继续承担ToC订单与履约；自研ERP保留原订单及实际结果关联，不接管前台履约 |
| 与财务关系 | 财务ERP继续做财务核算底座；业务单据由自研ERP推送，财务ERP不做采购 / 销售业务入口 |
| 与仓储关系 | 立项时深圳主仓无专业WMS；一期**引入第三方WMS** 承接国内仓实物作业，自营仓直连，第三方仓可经SaaS中转，ERP下发通知、接收实际结果并维护对应逻辑仓库存 |
| 与财务ERP迁移 | B2B、采购等业务逐步从财务ERP迁到自研ERP；切换与并行方案后续单独确认 |

## 三、一期建设范围

一期按 **主数据 → 业务模块 → 系统集成** 三层搭建后台能力，目标是跑通一条能自我闭环的后台主链条。

### 3.1 能力结构

```plain
基础资料：商品 · 供应商 · 仓库 · 客户 · 物流 · 辅助资料
                       ↓
业务模块：价格管理 · 采购 · 销售 · 库存 · 结算与业财
                       ↓
系统集成：领星 · 聚水潭 · Shopify · 第三方 WMS · 财务ERP

公共能力贯穿各层：RBAC、提交审核、导入原则、技术配置参数
```

### 3.2 主数据

商品、供应商、仓库、客户、物流在ERP内统一维护。辅助资料提供分类、品牌、单位、币别及收付款条件等预置类型下的资料值。

| 主数据域 | 一期要做什么 | 谁维护 | 主要给谁用 |
| --- | --- | --- | --- |
| 商品（成品SKU） | 编码、名称、分类、单位、条码、初始供应商与价格及管理配置 | 主数据模块 | 采购、销售、库存、结算 |
| 供应商 | 基础信息、结算方式、联系人等 | 主数据模块 | 采购、结算 |
| 仓库 | 实体仓及其下自主划分的逻辑仓 | 主数据模块 | 采购入库、销售出库、库存查询 |
| 客户 | 代理商、国内及跨境2B、通用2C档案；等级、结算方式及收款条件 | 主数据模块 | B2B销售、结算 |
| 物流 | 物流商及物流服务产品；支持由仓库指定或自提，不含跨境头程 | 主数据模块 | 销售发货 |

外部分发原则：商品SKU异步分发至财务ERP和第三方WMS；领星 / 聚水潭一期通过SKU编码或确认后的对应关系匹配，不做全量资料推送。供应商通过邮件、微信等线下沟通，采购人员代录ERP；一期不建在线协同门户或商品供货关系。

### 3.3 业务模块

| 模块 | 一期要做什么 | 主要单据或对象 |
| --- | --- | --- |
| 采购 | 成品采购与采购退货，通知仓库并接收实际结果 | 采购订单、采购收货通知单、采购入库单；采购退货单、采退发货通知单、采退出库单 |
| 销售 | B2B与独立站正向及退货链路；外部ToC原订单与实际结果归集 | 销售订单、销售发货通知单、销售出库单；销售退货单、销退收货通知单、销退入库单 |
| 库存 | 逻辑仓库存、预占冻结、仓间调拨、其他出入库与库存比对 | 其他出入库申请单及结果单；直接调拨单、分步式调拨单及调出／调入通知单 |
| 价格管理 | 采购价、销售价及调整；业务单据保存成交价格快照 | 采购／销售价目表、采购／销售价格调整单 |
| 结算与业财 | 定义七类已审核结果单逐单推送及财务ERP核算边界 | 采购入库、采退出库、销售出库、销退入库、其他入库、其他出库、直接调拨 |

B2B在ERP建单并支持分批通知、自提等场景，已审核订单不改量改价；外部ToC由SaaS履约。Shopify直连ERP，一期人工批量选仓、选物流及审核，审核通过后由系统自动推送仓库，整单履约。

| 订单类型 | 订单来源 | 履约执行 | ERP一期做什么 |
| --- | --- | --- | --- |
| 外部电商ToC | 平台订单，由领星／聚水潭承接 | SaaS及对应仓库 | 保留原始订单与实际结果关联，记库存、推财务ERP |
| B2B | ERP人工建单 | 仓库 | 审核占库、分批通知、实际出入库与退货 |
| Shopify独立站 | ERP自研接口拉取已付款订单 | 深圳仓或海外仓 | 人工选仓、选物流与审核占库，审核后自动推送仓库，整单发货及结果回写 |

### 3.4 系统集成

| 外部系统 | 一期定位 | 与ERP怎么接 |
| --- | --- | --- |
| 领星／聚水潭 | 跨境／国内ToC运营与履约，第三方仓储中转 | 返回原订单及实际结果；中转采购与仓储通知和结果，具体来源单据需映射 |
| Shopify | 独立站订单来源 | 拉取已付款订单，回写履约及运单等结果；接口未覆盖订单支持人工导入 |
| 第三方WMS | 仓内实物执行 | 自营仓直连，接收通知或直接推送的订单、申请单，回传实际出入库、物流及适用库存信息 |
| 金蝶云·星空 | 财务核算底座 | 接收七类已审核结果单 |
| 东莞电商仓 | 国内电商仓内作业 | 一期经聚水潭间接衔接 |
| FBA／第三方海外仓 | 跨境履约节点 | 实际结果纳入对应逻辑仓库存；具体对接路径及能力按来源核验 |

外部映射、推送失败及必要处理记录由系统集成承接；映射随基础资料维护（商品映射在商品资料独立页面按「平台＋店铺」维护，仓库映射与货主标识随实体仓）；无法自动取得仓库实际结果时支持人工确认，入口在对应业务单据详情页（2026-09-24调整）。人工补充仍须遵守业务校验及适用的审核流程，Mock不代表真实接口已验证。

### 3.5 公共能力与需求依据

一期采用RBAC，有相应权限即可提交、审核，允许本人审核本人创建的数据。导入不绕过适用的提交审核流程；业务参数暂由技术支持／运维通过代码配置文件维护。

模块范围及详细规则见：[主数据](../02-需求调研和分析/01-商品与主数据/商品与主数据需求分析.md)、[采购](../02-需求调研和分析/02-采购业务管理/采购业务管理需求分析.md)、[库存](../02-需求调研和分析/03-库存与仓储/库存与仓储需求分析.md)、[销售](../02-需求调研和分析/04-销售与履约/销售与履约需求分析.md)、[业财](../02-需求调研和分析/05-结算与业财/结算与业财需求分析.md)、[价格](../02-需求调研和分析/06-价格管理/价格管理需求分析.md)、[集成](../02-需求调研和分析/07-系统集成/系统集成需求分析.md)、[公共能力](../02-需求调研和分析/08-公共能力与系统管理/公共能力与系统管理需求分析.md)、[辅助资料](../02-需求调研和分析/09-辅助资料/辅助资料需求分析.md)。

## 四、一期不做什么

| 类别 | 不做什么 |
| --- | --- |
| 生产制造 | 原材料、BOM、物料计划、MRP、车间排产 |
| 后续自研系统 | 自研WMS、自研SRM、中央OMS、POS、区域仓网、BI |
| 采购扩展 | 采购申请、自动补货、采购计划模型、供应商在线协同、商品供货关系 |
| 库存扩展 | 全量库存双向同步、跨渠道配额及统一调度、多主体之间的购销与调拨、ERP盘点单、仓内作业接管 |
| 销售扩展 | 外部ToC抓单及履约接管、B2B已审核改量改价、独立站拆单缺量发货、完整自动履约、ERP执行退款 |
| 财务替代 | 应收应付、收付款、预收预付、核销、凭证、总账、存货成本核算及平台账单费用回款对账 |
| 公共能力后置 | 完整操作日志不列为一期必做；待办、消息提醒及业务参数配置页面后置，保留必要集成记录 |
| 实施类另行安排 | 切换、并行运行、期初初始化与历史迁移；不表示上线无需库存起点 |

销售退货、仓间调拨和盘盈盘亏结果接收已纳入本期，不能与仓内盘点或全渠道调度混为一谈。完整状态、字段及接口仍在后续设计中细化。

## 五、建设优先级与交付目标

### 5.1 一期要建什么（均属本期，不是分期项目）

主数据、辅助资料、价格、采购、库存、销售、结算与业财、系统集成和公共能力共同构成本期范围。具体能力见 §三，落地先后不改变范围。

### 5.2 建议落地顺序

1. 基础资料与公共权限，支撑后续业务建单。
2. 价格初始化及调整、采购正向和退货，与仓库结果及库存记账同步闭环。
3. B2B、外部ToC、独立站销售及退货，分别落实占库、执行和结果归集。
4. 其他出入库、仓间调拨、在途及库存比对，补齐库存业务。

系统集成与七类结果单推送随各业务同步建设，不放到全部业务结束后才处理。以上为建议顺序，不是已确认排期。

### 5.3 一期交付目标

一期应覆盖以下业务闭环，而不只完成采购入库与B2B出库：

```plain
基础资料与价格就绪
    → 采购／销售及退货 → 通知仓库 → 实际出入库 → 逻辑仓库存记账
    → 外部 ToC 原订单及实际结果归集 → 对应逻辑仓库存记账
    → 其他出入库／仓间调拨 → 实际结果与在途记录
    → 七类已审核结果单逐单推送财务ERP

库存比对发现差异；接口失败保留记录并按确认边界处理
```

实际外部接口、库存初始化与上线切换需另行核验和实施；需求与演示阶段可用Mock验证流程表达，不能据此宣称已完成真实业务联调。

## 六、项目协同

| 部门 | 一期诉求 |
| --- | --- |
| 供应链中心 / 采购 | 采购主链条收口；入库后库存可查 |
| 产品中心 | 成品SKU统一维护，支撑采购建单 |
| 仓储物流 | 实际出入库与仓储结果对齐；通过库存比对发现账实差异 |
| B2B渠道 / 营销中心 | 灵活B2B订单能系统留痕，不必先微信谈妥再事后补单 |
| 财务中心 | 实际结果单逐单推送财务ERP；平台账单、费用与回款继续由财务线下处理 |
| 数字化中心 | 明确ERP与领星、聚水潭、财务ERP、WMS的边界 |

组织架构用于理解业务参与方，不直接映射ERP角色、权限或审批配置。
