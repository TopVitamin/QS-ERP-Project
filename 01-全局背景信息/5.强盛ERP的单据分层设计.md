# 强盛ERP的单据分层设计

> **更新日期**：2026-09-13。依据本轮单据分层设计讨论确认；系统分工与链路见 [3.强盛ERP的定义和上下游链路](3.强盛ERP的定义和上下游链路.md)，跨模块强约束见 [4.强盛ERP全局业务规则与约束](4.强盛ERP全局业务规则与约束.md)。
>
> 本文说明 ERP 业务单据的统一分层模型：为什么分层、三个角色各是什么、每条链路用几层、层数怎么判断，以及跨模块共用的一次回传、数量控制和结果单审核口径。
>
> **怎么使用本文**：设计或评审一类新单据时，按 §三 判断层数，按 §五 设计单据关系、状态与联动；改动任何模块的单据链路时，同步更新 §四 的链路表。三层是完整形态，不是强制模板——有的链路只有两层或一层。
>
> 文中时间、规模与数据均为课程演练设计的虚拟内容，不代表真实企业运行记录。

## 一、为什么要把单据分层

一笔业务在现实中通常包含三件不同的事：先谈好"要做什么"，再安排仓库"这一次怎么做"，最后记录"实际做成了什么"。这三件事由不同的人在不同时间完成，还可能反复发生：供应商分批发货、客户取消某一次发货、仓库实际只收到一部分。

如果把这些压在一张单据上，会出现三类问题：

- **契约和执行互相牵制**：分批发货、单独取消某一次执行，没有地方安放；
- **计划被当成事实**：订单数量、通知数量直接进库存，造成账实不符；
- **历史被覆盖**：仓库回传直接改写已审核的业务约定，追溯断链。

分成三层之后：

1. **执行可以分批、可以独立跟踪**：一张订单对应多张通知单，每张通知单有自己的数量、状态和取消流程；
2. **约定保持稳定**：实际结果只回写到对应层级，差额按各模块规则回补额度或另建单据，不篡改原约定；
3. **记账口径唯一**：库存只按实际结果变化；订单、通知和申请本身不增加或扣减即时库存（销售、采购退货等审核时的预占只锁定可用量）。

## 二、三个角色（层）是什么

| 层级 | 角色 | 回答什么 | 本质 | 典型单据 |
| --- | --- | --- | --- | --- |
| 第一层 | 业务安排 | 我要做什么 | 与供应商、客户或内部确认的业务约定 | 采购订单、采购退货单、销售订单、销售退货单、其他入库申请单、其他出库申请单、分步式调拨单 |
| 第二层 | 执行指令 | 这一次让仓库做什么 | 一次具体执行的指令，可以分批下发 | 采购收货通知单、采退发货通知单、销售发货通知单、销退收货通知单、调出通知单、调入通知单；也可由订单、申请单直接承担 |
| 第三层 | 实际结果 | 实际发生了什么 | 实际发生的事实，库存记账和业财推送的唯一依据 | 采购入库单、采退出库单、销售出库单、销退入库单、其他入库单、其他出库单、直接调拨单 |

两个必须记住的认识：

- **角色 ≠ 单据**。一个角色可以由一张单据承担，多个角色也可以合并到同一张单据上，用状态变化区分（例如同一张单从"已审核、待执行"走到"已完成"，先后承担指令和结果）。
- **结果单的定义**。结果单记录实际发生的事情：由仓库或下游回传自动生成，或由人工确认实际结果后形成。订单和通知的数量不能当作库存事实——这正是"库存只按实际结果记账、只把结果推给金蝶"能成立的原因。

以采购为例：采购订单审核后（第一层），采购按供应商线下发货反馈代录采购收货通知单并下推仓库（第二层）；仓库回传一次实际收货结果（允许缺量），系统更新通知单及采购订单累计收货数量，并生成采购入库单（第三层，自动审核）；采购入库单再逐单推送金蝶。

## 三、层数怎么定（判断口径）

设计或评审单据时，不要先问"它应该是几层"，按顺序回答四个问题：

1. **有没有独立的业务需求或交易约定？** 有（客户买了什么、向供应商采购什么、内部要领用什么），才建第一层。没有就不要为了形式制造一张"订单"。
2. **约定和某一次执行会不会不同、是否需要独立的生命周期？** 只要出现任一情况——分批、分仓、多次下推、部分履约、单独取消或重试、单独调整执行仓或物流、一张约定对应多个执行任务——第二层就有独立价值。如果约定天然就是"一次、一个仓、一次完成"，第一层本身就是执行指令，可以省略独立指令层。
3. **实际会不会和计划不同、是否需要独立记录库存事实？** 只要实际可能少于或多于计划，或者库存事实需要独立保存并推送金蝶，就必须保留第三层。无论前面怎么裁剪，第三层都不能省——它是记账依据。
4. **两个角色是否真的需要两张单？** 即使角色独立存在，如果"指令数量≈实际数量、一单一次完成、生命周期一致"，也可以合并成一张单，用状态承担多个角色。

一句话口径：**有独立业务需求才建安排层，有独立执行编排才建指令层，要记录实际库存事实必须有结果层。**

三个形态对应的场景：

| 形态 | 什么时候用 | 本项目链路 |
| --- | --- | --- |
| 3 层（安排→指令→结果） | 会分批，或执行需要单独取消、重试、跟踪 | 采购、B2B 销售、退货、分步式调拨 |
| 2 层（安排→结果） | 一次执行、一个仓，业务单据本身就能指挥仓库 | 独立站正向、其他出入库 |
| 1 层（只有结果） | 不经过仓库的调整，或仓库已经完成、ERP 只登记事实 | 一步式直接调拨、仓库主动回传、外部 ToC |

**规则跟着角色走，不跟着单据名走**：一次回传、允许缺量、不允许超量，约束的是"承担执行指令角色的单据"（可能是通知单，也可能是直接推送的订单或申请单）与其回传之间；结果单的自动审核和金蝶推送，针对的是第三层。

**什么时候改用另一种**：本项目复杂主链（采购、B2B、退货、分步式调拨）会分批或需要单独取消，所以保留独立指令层；独立站、其他出入库一期明确规定"一单一仓、不分批、一次执行"，就主动裁剪掉指令层。反过来，如果哪天独立站开放拆单发货、其他出入库开放分批执行，应该重新评估加回指令层，而不是把分批硬塞进订单或申请单。

## 四、各业务链路的分层

| 业务链路 | 层数 | 结构 | 为什么这么定 |
| --- | --- | --- | --- |
| 采购入库 | 3 | 采购订单 → 采购收货通知单 → 采购入库单 | 供应商分批发货，每批一次通知、一次回传；PUR-FR01～FR03 |
| 采购退货 | 3 | 采购退货单 → 采退发货通知单 → 采退出库单 | 支持分批出库、缺量回补；PUR-FR04、FR05 |
| B2B 销售 | 3 | 销售订单 → 销售发货通知单 → 销售出库单 | 分批通知、可自提、取消需等仓库确认；SAL-FR02、FR03 |
| 销售退货 | 3 | 销售退货单 → 销退收货通知单 → 销退入库单 | 支持分批收货、按额度控制；SAL-FR05、FR06 |
| 分步式调拨 | 3 | 分步式调拨单 → 调出通知单（按实际调出生成调入通知单）→ 直接调拨单×2 | 两端执行，第二段指令按实出量生成；INV-FR03 |
| 独立站正向 | 2 | 销售订单（审核后直接推送仓库）→ 销售出库单 | 一单一仓、整单履约、不分批，订单即执行指令；SAL-FR07、FR08 |
| 其他入库 | 2 | 其他入库申请单（审核后直接推送仓库）→ 其他入库单 | 一期不分批、一次执行，申请即指令；INV-FR06 |
| 其他出库 | 2 | 其他出库申请单（审核后直接推送仓库）→ 其他出库单 | 同上；出库申请审核时预占；INV-FR06 |
| 一步式直接调拨 | 1 | 直接调拨单 | ERP 内部转库存、不推送仓库或外部执行系统，审核后直接记一减一增；INV-FR07 |
| 仓库主动回传 | 1 | 其他入库单、其他出库单、直接调拨单 | 仓库已经完成，ERP 只接收结果，不补造安排与指令；INV-FR04、INV-FR07 |
| 外部 ToC 正/反向 | 1 | 销售出库单、销退入库单 | 履约在 SaaS 完成；平台原订单仅作来源追溯，不驱动履约；SAL-FR09 |

## 五、跨层的对象关系与状态口径

本节把各模块已确认的数量与流转规则抽象成一套通用口径，回答三个问题：单据之间是什么关系（1:N 还是 1:1）、状态放在单头还是行、上下层怎么联动。状态命名和完整枚举仍留各模块详细设计，本节只写能从已确认规则中抽象出来的部分。

### 5.1 对象关系：上一级可以分多张，指令与结果一一对应

| 关系 | 基数 | 说明与依据 |
| --- | --- | --- |
| 业务安排 → 执行指令 | 分批链路 1:N；安排单直接兼作指令时 1:1 | 一张订单可生成多张通知单（PUR-FR02、SAL-FR02）；独立站、其他出入库审核后直接推送，不再生成指令单 |
| 执行指令 → 实际结果 | 1:1 | 承担指令角色的单据只接受一次回传，回传即结束、生成一张结果单；要再执行就另建单据（见「一次回传」） |
| 业务安排 → 实际结果 | 1:N | 多次执行产生多张结果单，按行累计回写到安排单 |
| 分步式调拨（特例） | 主单 1:2 端，每端指令与结果 1:1 | 调出、调入各生成一张直接调拨单，中间经过虚拟在途仓（INV-FR03） |
| 外部 ToC（特例） | 平台原订单 1:N 结果 | 同一平台订单可能形成多次实际出入库结果；原订单只作追溯，不驱动履约（SAL-AC15） |
| 结果单 → 来源单据 | 多对一，逐级可溯 | 结果单保留来源指令（乃至安排单）关联，用于库存归属、追溯与差异处理 |

一句话：**上一层可以分多张往下走，但指令与结果永远一对一；跨层累计靠回写，不靠一张单反复回传。**

### 5.2 状态划分：动作状态在单头，数量状态在行

一期不强行统一一套全模块的状态枚举，而是统一动作语义：审核、关闭、取消、结束的含义跨模块一致（见 [4.强盛ERP全局业务规则与约束](4.强盛ERP全局业务规则与约束.md) §三），状态命名和数量留各模块详细设计。在这个前提下：

- **单头管动作和生命周期**：提交、审核、关闭、取消，以及是否已下发/已推送，都是单头状态，决定这张单还能做什么——例如关闭后不再新增下推，但已经下发的指令继续执行。
- **行管数量和额度**：需求数量、已生成指令数量、已执行数量、可下推数量/剩余额度，都按商品明细行维护；不同商品行不能互相抵用。
- **一份通用数量公式**（适用于支持分批的三层链路：采购、采购退货、B2B 销售、销售退货）：

  可下推数量 = 安排数量 − 已结束指令的实际执行数量 − 未结束有效指令的指令数量

  已取消的指令不占额度（已确认于 B2B 销售、销售退货；其他链路的取消规则按各模块）；下推时占用额度，指令结束后少收/少出部分回补。两层链路没有"下推"概念：一次执行结束（其他出入库）或整单履约（独立站），按实际结果一次了结。
- **行是否需要独立的状态枚举，一期未确认**：现有结论只要求行上的数量能对账（累计执行、未结束指令占用、额度回补）；单头结束的自动判定、状态命名留详细设计（见销售、库存的待决策事项）。

三层各自的生命周期阶段（示意，名称以详细设计为准）：

| 层 | 生命周期阶段 |
| --- | --- |
| 业务安排 | 草稿 → 已审核（可下推）→ 执行中 → 结束 / 关闭（不可反关单） |
| 执行指令 | 待下发 / 已推送 → 仓库执行中 → 已结束（回传）或已取消（需仓库确认） |
| 实际结果 | 回传自动生成（自动审核）或人工形成（提交审核）→ 已审核 → 已推送金蝶 / 推送失败 |

### 5.3 跨层联动：生成、回传、回补、占库、外部确认、业财

```plain
                生成/下推（按行占用可下推数量）
  业务安排 ──────────────────────────────► 执行指令
      ▲                                        │
      │  回写累计执行数量、少收少出回补额度       │ 一次回传
      └────────────────────────────────────────┤
                                               ▼
                                    实际结果（自动审核 → 推送金蝶）
```

1. **生成（下推）**：安排层审核后生成指令单，或由安排单直接推送仓库；每次生成受行上"可下推数量"约束，支持分批；取消或关闭后不再新增。
2. **回传（结果形成）**：指令单据一次回传后，系统自动生成结果单并自动审核，同时把实收/实出数量回写到指令单与安排单的行上。
3. **回补**：指令结束后，少收/少出部分回补可下推数量（采购、销售、退货支持；其他出入库不回补、一次结束）；补发要新建指令或订单。
4. **占库联动**：需要出库的主动业务在安排层审核时预占；下发指令不重复占库；结果记账时扣减即时库存并消耗对应预占；关闭或取消经外部确认后，释放未执行部分的预占。
5. **终态与外部确认**：关闭不等于取消，ERP 关闭不撤销已下发的指令；取消指令是"申请—仓库确认—落地"的异步流程；已结束的结果单不接受第二次回传或被直接改写。
6. **业财联动**：只有结果层推送金蝶（FIN-FR01）；安排、指令和分步式调拨主单不推送。

## 六、各层共用规则（按角色表述）

### 6.1 一次回传

承担执行指令角色的单据只接受一次回传，回传即结束；仓库内部如何分批作业、拆分成多少任务，不进入系统口径。结束后需要补发、补收的，另建单据。

### 6.2 缺量与超量

- 允许缺量：回传数量少于指令数量时按实际结果记账；少收、少发部分是否回补下推数量按各模块规则（采购、销售支持回补，其他出入库不回补原单余量）。
- 不允许超量：回传数量超过指令数量时，系统直接拒绝本次回传并报错。需要接收超出部分时，按各模块规则另建单据（采购超出通知仍在原订单可下推额度内另建通知单，超过订单数量另建采购订单），不改变回传层面的拒绝规则。

### 6.3 结果单与审核

- 由仓库或下游回传、系统自动生成的结果单，默认自动审核，不经人工审核。
- 人工形成的结果单（人工确认实际结果、人工创建的直接调拨单），按提交审核流程处理。
- 结果单在 ERP 已生成且已审核后逐单推送金蝶；订单、申请、通知和分步式调拨主单不推送。推送范围与失败处理沿用 FIN-FR01～FIN-FR03。
- 结果单推送金蝶后由金蝶按其核算规则处理；金蝶内部的暂估应付、应付、付款及凭证流程不属于 ERP，也不在本文范围。

### 6.4 执行回执

执行指令层只有结果回传会生成结果单。申请取消后的仓库确认或拒绝等回执，只更新指令单据状态，不生成单据、不改变库存；目前该能力见 SAL-FR04。

### 6.5 结果单的完结与更正

结果单记录实际发生，不接受第二次回传，也不跟随来源直接改写已完结结果。回传后发现少收、错收等差异，不设计常规业务更正流程，由技术介入修数据，或按双方线下约定处理；外部 ToC 的完结保护继续沿用 SAL-FR12。

业务上一次回传与接口去重是两件事：来源重复回传、幂等标识及部分成功恢复仍属接口设计待确认项，不因本模型视为已解决。

### 6.6 不设换货单、补发单

换货按"销售退货链 + 新建销售订单"处理；补发在销售按原订单另建单据或新订单，采购超出部分按 6.2 的补救规则处理。不新增换货单、补发单。

## 七、边界场景

以下情况明确不进单据分层模型：

- 拒收：仓库现场拒收按缺量回传处理；入库后的不合格品走采购退货链，不新增单据。
- 自提：B2B 现场提车仍需订单与通知单，只是不选物流，层数不变。
- 在途差异：分步式调拨少收差异保留在途，后续通过再次调拨或其他出库清理，不自动抹平（INV-FR03）。
- 库存比对差异：只展示与比较，不自动改账、不生成单据（INV-FR08）。
- 库存初始化：由上线切换方案安排，不属于日常单据链（INV-FR02）。
- 跨组织调拨：属于买卖，方案另行确认，不并入同组织调拨链路。
- FBA、海外仓等外部来源的丢件、破损与平台调整：一期接口能力待核验，不预设单据链路。
