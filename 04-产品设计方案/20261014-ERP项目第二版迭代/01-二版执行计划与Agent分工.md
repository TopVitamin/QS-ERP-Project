## 一、最终目的与完成定义

**最终目的**：贴合第二版需求，把相关文档改动输出到位——在二版目录内形成"二版文档集"：一版未变的文件继续引用一版；有变动的按"重建"落地；一版没有的对象与文档新建；全部改动可在《二版交付清单》（B6）中追溯到任务号与一版对应文件。

完成判定（全部满足才算收口）：

1. 00 §三 各任务达到各自「完成标准」，勾选并补「完成记录：日期＋版本位置」；
2. 二版目录内交付物与 01–03 修订后口径一致；全文无「外部原始订单／外部电商／外部ToC」对象名残留；
3. 新建、重建文件均带版本行注明变化；B6 把一版受影响文件全部登记（取代／增量／勘误／未变引用）；
4. C 组：`npm run build` 通过＋浏览器走查记录；`待改项.md` 条目核销或登记新差异；
5. 完整交付后做一轮独立只读评审（事实依据、完整性、语言），影响对错的问题处理完毕。

## 二、执行原则

1. **先能做的就做完**：不依赖你拍板、不依赖其他批次的先做完。批次0 可立即执行；批次1 内各任务相互独立，可并行。
2. **需确认、检查的后置**：凡任务要求「与用户确认」或会改变产出的决定（见 §五 确认单），未收口前不动手；收口后连续执行，不再逐件请示。批次完成后你可抽检（可选检查点）。
3. **冲突与待确认处理**：发现与 01–03 或已确认设计的冲突，停下记录、不自行改设计；接口字段、渠道产品名等未定值写「待确认」，不阻塞任务。
4. **只读纪律**：一版目录（`20260812-…`）默认只读；唯一例外是 B6 登记过的显式勘误（先登记、后修改、版本记录注明）。不擅自 git 提交，提交节奏由你决定。
5. **版本与追溯**：每处修改按所在目录格式加版本行，能追溯到任务号；同一结论只在一处维护，其余引用。
6. **交付深度基线**：所有二版交付物按「能让 AI 直接消费、产出 PRD 与原型」的标准写——结构化表达，字段/状态/规则/异常齐全，待确认明确标注，不依赖口头补充。

## 三、能否一步到位（评估）

**结论：不能一次全做完，也不建议硬凑一步。** 展开看：

| 判断维度 | 情况 |
| --- | --- |
| 体量 | 剩余任务约 70–90 个文件级动作（B3/B4/B5/B7 为大头），一次派工承载不了 |
| 确认闸门 | 3 项需你拍板（二版目录组织、B1 形式、B2 形式），按原则2 必须后置 |
| 依赖链 | A4→B2；B3→C1/C3；B4/B5→C1/C2；B8→C4；B1–B8→B6；B6→B10③ |
| 并行风险 | 同批 Agent 若共写同一文件或口径不一致，返工成本高 |

**可行的是「一次确认＋三个波次」**：确认收口后，批次1（文档主体，8 个 Agent 并行）→ 批次2（原型，4 个 Agent）→ 批次3（收尾评审，2–3 个 Agent）。中途无需你逐件审批（出现新决策除外）。

## 六、文档处理规则（重建与新增的落地方式）

每个任务动手前，把涉及文件逐一判为四类，判定结果记入批次报告、供 B6 汇总：

1. **未变动（规则a）**：不复制、不重建；B6 登记为「未变-引用一版」，路径指向一版文件。
2. **变动（规则b）**：在二版目录对应位置**重新创建**修订文件——以一版原文件为底稿，只应用本次改动；头部版本表加行注明「二版重建（任务号）：新增/调整了什么」；相对链接按二版目录调整。命名沿用原名，以目录区分版本（B1 增量文按 00 命名）。
3. **新增**：一版没有的对象/文档直接新建；B6 登记为「新增」，并汇总「本次新增的文档结构」清单（如：集成映射分册、结果处理规则、用户与权限套件、订单对象三件套、5 份模块交付清单、3 份评审报告等）。
4. **勘误**：唯一可动一版目录的例外——先登记 B6，再修改，版本记录注明「显式勘误」，不重复维护第二份。

「本次新加了哪些内容、哪些结构」的落点（不另造重复说明文件）：①每个新建/重建文件的版本行；②B6 的「本次变化摘要」「新增结构说明」列；③批次报告。

判定示例：独立站订单无旧套件→新增；采购收货通知单主PRD/骨架/Demo 受中转与人工确认影响→重建，其 TSV 若无新字段→不重建、继续引用一版；价格管理四对象二版不动→不重建，只出评审报告；一版模块地图「库存比对（另行批次交付）」字样→勘误。

B6 表建议列：一版文件｜二版去向（取代／增量／勘误／未变-引用／新增）｜二版文件或引用路径｜本次新增内容摘要｜任务号。

## 八、风险与防错

1. **术语残留**：批次末统一检索「外部原始订单」「外部电商」「外部ToC」「external_toc」，命中即修（文档与原型）。
2. **口径漂移**：来源标识统一「来源系统＋来源单号（＋执行标识）」；结果关联统一「分两张」；订单编号 GNDS/KJDS 已定（2026-10-15）。以 00 §二与 `01/6` §1.3 为准。
3. **并行冲突**：批次1 各 Agent 文件集已按对象分工、互不重叠；批次2 共享文件由主控统一登记。
4. **一版污染**：批次结束用 `git status/diff` 复核，一版目录只允许登记过的勘误。
5. **范围克制**：本轮暂缓项（商品外部映射与 SKU 分发、结算与业财套件、FBA 只读入口、个人中心升级）不得顺手做。
6. **验证边界**：build 通过 ≠ 接口/交互验证；Mock 边界注明，只报告实际完成的验证。
7. **工作区现状**：当前工作区已有未提交改动（含 A 组首轮修订与其他在办改动）；开工前由你决定提交或保留，Agent 只报告自身改动范围、不擅自整理他人改动。
