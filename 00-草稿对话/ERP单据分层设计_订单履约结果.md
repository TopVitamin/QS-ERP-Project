# ERP 单据分层设计：订单、履约指令与执行结果

## 一、讨论起点：所谓“三层单据”是什么

在 ERP、供应链、库存与仓储协同场景中，可以把业务单据抽象为三个角色：

| 层级 | 核心含义 | 回答的问题 | 典型单据 |
|---|---|---|---|
| 订单层（Order） | 业务需求、交易约定、业务意图 | 我要做什么？ | 采购订单、销售订单、调拨订单、退货订单 |
| 履约层（Execution / Fulfillment） | 一次具体的履约或作业指令 | 这一次具体怎么执行？ | 收货通知、发货通知、调拨通知 |
| 结果层（Result / Transaction） | 实际发生的业务与库存事实 | 最终实际发生了什么？ | 采购入库、销售出库、调拨出入库、盘盈盘亏 |

最典型的三层链路：

```text
采购订单 → 收货通知 → 采购入库
销售订单 → 发货通知 → 销售出库
```

例如采购 100 件，并不代表一次全部到货：

```text
采购订单：100件
    ↓
收货通知01：计划收60件
    ↓
采购入库01：实际收58件

收货通知02：计划收42件
    ↓
采购入库02：实际收42件
```

订单表达的是总体业务需求，通知表达的是某一次具体履约安排，结果单记录的是最终实际发生的库存事实。

---

## 二、三层单据不是强制模板

最重要的结论是：

> “订单 → 通知 → 结果”应该理解为完整的业务角色模型，而不是所有业务都必须固定生成三张单据。

判断一条业务链路需要几层，不应该看“系统是否统一”，而应该看三个角色是否真的具有独立业务价值。

更准确的三个角色是：

```text
业务意图（Order）
        ↓
履约指令（Execution）
        ↓
执行结果（Result）
```

这三个角色可以分别存在，也可以根据业务复杂度合并或省略。

因此系统中可以合理存在：

```text
三层：Order → Execution → Result
两层：Order → Result
两层：Execution → Result
一层：Execution + Result
一层：Result
```

---

## 三、什么时候业务单据和履约指令需要独立

业务单据和履约指令是否需要拆开，核心不是“要不要推给 WMS”，而是：

> 业务需求和一次具体履约是否可能不同，是否需要拥有独立生命周期。

### 1. 不需要独立的情况

例如一张 B2C 销售订单：

```text
销售订单 SO001
SKU A × 2
履约仓：广州仓
收货地址：已确定
物流要求：已确定
```

如果这张订单天然就是：

- 一个订单对应一次履约；
- 不会拆成多次发货；
- 不会拆多个仓；
- 不会改单独某一次履约；
- 不会多次下推；
- ERP 不承担复杂履约编排；

那么销售订单本身就已经足够作为 WMS 的履约指令。

链路可以直接是：

```text
销售订单
   ↓
直接推送 WMS
   ↓
WMS 履约
   ↓
销售出库单
```

此时如果再增加一张发货通知：

```text
销售订单 → 发货通知 → WMS
```

发货通知很可能只是把订单里的 SKU、数量、仓库、地址、物流信息复制一遍，没有新增业务含义。

这种情况下通知层就是冗余的。

---

### 2. 需要独立的情况

如果订单和某一次履约开始出现差异，就需要考虑独立履约层。

例如：

```text
销售订单 SO001：A × 100
```

第一次只履约 60：

```text
SO001：A × 100
    ↓
发货通知 DN001：A × 60，广州仓
```

剩余 40 后续再次履约：

```text
SO001：A × 100
    ├─ DN001：60，已完成
    └─ DN002：40，上海仓，待发货
```

甚至 DN002 因仓库异常取消：

```text
SO001：保持不变

DN002：取消
   ↓
重新分配仓库
   ↓
DN003：40，深圳仓
```

这时订单和履约指令已经具有不同生命周期：

- 订单管理的是客户总体业务需求；
- 通知管理的是每一次具体履约任务；
- 某次履约可以创建、取消、重试，但订单本身不一定变化。

### 3. 常见的独立信号

| 场景 | 是否建议独立履约层 |
|---|---|
| 一个订单拆多次发货 | 是 |
| 一个订单拆多个仓 | 是 |
| 本次只履约订单中的部分数量 | 是 |
| 同一订单允许多次下推 | 是 |
| 某次履约可以单独取消、重推 | 是 |
| 订单不变，但履约仓、物流方式等可以变化 | 是 |
| 一个订单对应多个 WMS 履约任务 | 是 |
| 订单与履约长期稳定 1:1 | 通常不需要 |
| 订单内容本身已经足够指导仓库作业 | 通常不需要 |

最核心的判断可以收敛成一句话：

> 如果一个业务单据可能产生 N 次独立履约，就应该考虑把履约层独立出来。

## 四、“需要推 WMS”不等于“必须有通知单”

这是整个讨论中一个很重要的纠偏。

最开始容易产生一种直觉：

```text
只要 ERP 要推送 WMS
→ 就需要一张通知单
```

但这并不成立。

推 WMS 只代表“需要一个可执行指令”，这个指令完全可能由订单本身承担。

例如 B2C：

```text
平台订单
   ↓
ERP 销售订单
   ↓
WMS
   ↓
销售出库
```

此时销售订单既是业务订单，也是仓库履约的输入。

所以真正的判断应该是：

> 是否需要把履约指令从原业务单据中独立出来管理，而不是是否需要通知仓库。

---

## 五、订单直接到结果单的场景

在新零售 ERP 中，“订单 → 结果”并不少见，尤其是在业务流程简单、履约高度确定的场景。

| 场景 | 推荐链路 | 原因 |
|---|---|---|
| B2C 电商订单 | 销售订单 → 销售出库 | 通常一次履约，平台或 OMS 已确定履约信息 |
| POS 门店销售 | 销售订单/小票 → 销售出库 | 交易与库存扣减高度同步 |
| 门店自提 | 销售订单 → 销售出库 | 门店直接完成交付 |
| 简单采购 | 采购订单 → 采购入库 | 不做复杂预约、分批编排 |
| 简单调拨 | 调拨单 → 调拨出库/入库 | 调拨单本身已明确调出调入信息 |
| 简单销售退货 | 退货单 → 销售退货入库 | 一次退货直接完成收货 |
| 简单采购退货 | 采购退货单 → 采购退货出库 | 退货单本身即可指导仓库执行 |

一个规律是：

> 越靠近零售即时交易，越容易采用两层；越靠近 B2B、供应链计划和复杂履约，三层价值越高。

例如：

```text
简单 B2C
销售订单 → 销售出库
```

而复杂 B2B：

```text
销售订单
   ↓
多个发货通知
   ↓
多个销售出库
```

---

## 六、没有订单，但需要仓库作业：Execution → Result

还有一类场景没有真正的交易订单，但仍需要 ERP 发起一次仓库作业。

例如其他出库：

```text
其他出库通知
    ↓
WMS 作业
    ↓
其他出库单
```

这时可以理解为：

```text
履约指令 → 执行结果
```

没有必要为了形式完整，再额外创造一个“其他出库订单”。

例如：

```text
其他出库订单
    ↓
其他出库通知
    ↓
其他出库单
```

如果前两张单只是重复描述“样品领用 A × 10”，那就没有意义。

因此：

> 有交易、计划或总体业务需求时才需要订单层；没有订单需求但需要仓库执行，可以直接从履约层开始。

---

## 七、其他出入库到底用一层还是两层

其他出入库需要根据业务复杂度选择。

### 方案 A：两层

```text
其他出库通知
    ↓
WMS
    ↓
其他出库单
```

适用于：

- 作业指令与实际结果可能不同；
- 经常存在部分完成；
- 需要保留原始要求数量和实际执行数量；
- 履约过程需要独立状态；
- 对 WMS 的作业需要单独取消、重试或追踪。

例如：

```text
要求出库：100
实际出库：97
```

通知保留“要求 100”，结果单记录“实际 97”。

### 方案 B：一层合一

```text
其他出库单
草稿 → 已审核 → 待出库 → 作业中 → 已出库
```

这张单在生命周期不同阶段承担不同角色：

| 状态 | 单据角色 |
|---|---|
| 草稿 | 业务申请 |
| 已审核 / 待出库 | 已生效作业指令 |
| 作业中 | 履约中 |
| 已出库 | 已完成库存事实 |

这种模式适用于：

- 要求数量和实际数量通常一致；
- 一张单一次完成；
- 不需要同时保留两套独立生命周期；
- 不存在复杂分批、改单、重试。

因此，“其他出入库”没有唯一答案。

核心仍然是：

> 指令和结果是否需要分别管理。

---

## 八、只有结果单的场景

有些业务甚至不需要订单，也不需要履约指令，只需要记录“已经发生的事实”。

典型场景：

- 盘盈；
- 盘亏；
- 库存初始化；
- 期初库存导入；
- 系统库存纠错；
- 某些库存属性调整后的库存事务。

例如盘点：

```text
账面库存：100
实盘库存：98
差异：-2
```

盘点差异已经确认后，系统生成：

```text
盘亏单：A × 2
```

这张单不是在告诉仓库“请去盘亏 2 件”，而是在记录：

> 经过确认，库存实际少了 2 件。

所以它更接近纯粹的库存事实：

```text
Result
```

## 九、指令、履约、结果可以合并成一张单

单据角色不等于必须对应一张物理单据。

一个单据完全可以在不同状态下承担不同角色。

例如：

```text
其他出库单
```

它可以经历：

```text
草稿
  ↓
已审核
  ↓
待出库
  ↓
作业中
  ↓
已出库
```

其中：

- 草稿阶段是申请；
- 审核后是执行指令；
- 作业中是履约载体；
- 完成后是库存结果。

也就是说：

```text
Execution + Result
```

可以被一张单据承载。

是否拆开，取决于独立管理价值，而不是架构洁癖。

## 十、最终形成的统一模型

经过前面的讨论，可以把 ERP 单据设计从“固定三层”升级成“业务角色模型”。

### 完整形态：三层

```text
Order → Execution → Result
```

适用于复杂采购、复杂销售、复杂调拨等。

例如：

```text
采购订单 → 收货通知 → 采购入库
```

---

### 省略履约层：两层

```text
Order → Result
```

适用于订单本身已经能够直接指导履约。

例如：

```text
B2C 销售订单 → 销售出库
简单采购订单 → 采购入库
```

---

### 省略订单层：两层

```text
Execution → Result
```

适用于没有交易订单，但需要发起一次仓库作业。

例如：

```text
其他出库通知 → 其他出库
其他入库通知 → 其他入库
```

---

### 指令与结果合一：一层

```text
Execution + Result
```

适用于简单、一次性、结果高度确定的库存作业。

例如：

```text
其他出库单
报损单
简单领料单
```

单据通过状态变化完成从指令到结果的转换。

---

### 纯结果：一层

```text
Result
```

适用于没有后续履约动作，只需要记录库存事实的业务。

例如：

```text
盘盈单
盘亏单
库存初始化
库存调整
```

---

## 十一、建议形成一套判断顺序

以后设计某类单据时，不要先问：

> “它应该是一层、两层还是三层？”

而应该按下面的顺序判断。

### 1. 是否存在独立业务需求或交易约定？

如果有，考虑 Order。

例如：

- 客户购买了什么；
- 向供应商采购什么；
- 从哪个组织调拨什么。

如果没有，就不需要为了形式制造订单层。

### 2. 是否存在需要独立管理的一次履约？

如果存在以下情况，考虑 Execution：

- 分批；
- 分仓；
- 多次下推；
- 部分履约；
- 单独取消；
- 单独重试；
- 单独调整履约仓、物流方式；
- 一个业务单据对应多个执行任务。

如果原业务单据天然就是一次执行指令，则可以省略独立通知层。

### 3. 是否需要独立记录实际发生的库存事实？

只要实际执行可能与计划不同，或者库存事务需要作为独立事实保存，就应该保留 Result。

例如：

```text
计划100
实际97
```

结果必须能独立记录 97。

### 4. 两个角色是否真的需要两张单？

即使业务上有两个角色，也不一定必须拆成两张单。

如果：

```text
指令数量 ≈ 实际数量
生命周期一致
一单一次完成
```

可以考虑由一张单据通过状态机承担多个角色。

---

## 十二、最终设计原则

可以把整套方法收敛成几句话：

> **有独立业务需求，才建订单。**

> **有独立履约编排，才建通知。**

> **需要记录实际库存事实，才建结果。**

> **一个角色是否独立存在，与是否必须独立成一张单据，是两个不同的问题。**

> **三层是完整模型，两层、一层不是阉割，而是业务复杂度降低后的正常裁剪。**

因此，ERP 单据设计真正要解决的不是“所有业务如何统一成三层”，而是：

```text
哪些角色真的存在？
哪些角色需要独立生命周期？
哪些角色可以由同一张单据承担？
```

这比机械规定所有采购、销售、调拨、其他出入库都必须遵循相同单据层级，更适合作为 ERP 产品设计的通用方法。
