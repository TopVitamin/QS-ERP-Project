## 1. 课程背景

第3讲我们讲完了采购链路。

采购订单审核、收货通知下发、WMS收货上架、采购入库单审核，这套流程走完之后，货真正进入库存。

如果是在进销存系统里，系统通常只需要回答一句话：

```text
某个仓库里，某个商品还剩多少？
```

但在强盛科技阶段4，这个问题开始变复杂。

阿兰打开ERP查“USB-C 65W黑色充电器”的库存，系统返回一个数字：

```text
库存合计：3287个
```

这个数字看起来很明确，但业务同事马上会继续问：

| 角色 | 追问 |
| --- | --- |
| 国内电商运营 | 这3287个里面，我现在能卖多少？ |
| 门店运营 | 南山门店还有多少？总部有没有给门店预留？ |
| 跨境团队 | 有多少已经准备发往FBA？还能不能被国内渠道占用？ |
| 仓库主管 | 这些货真实在哪个实体仓？深圳总仓还是东莞仓？ |
| 采购计划 | 供应商已经发货但还没到仓的数量算不算？ |
| 财务 | 这批货归哪个货主、哪个结算主体？ |

如果系统只能返回一个“库存合计”，这些问题都答不上来。

问题不是系统算错了数，而是库存模型太简单。

进销存时代，一个“仓库”字段通常够用；到了ERP阶段，同一批货会分布在多个地点、处于不同状态、服务不同业务用途、归属不同经营主体。

所以这一讲要解决的问题是：

> 为什么一个“仓库”不够用了？ERP如何用实体仓、逻辑仓和多维库存口径，回答“货在哪、什么状态、归谁管、能不能卖”？

这不是否定进销存的设计。

进销存的库存模型在简单场景下是合理的。只是在阶段4之后，强盛科技进入多仓、多渠道、多组织、多系统协同的阶段，以前合在一起的口径必须拆开。

本讲不讲批次/FIFO，不讲盘点，也不讲具体调拨单设计。

本讲只讲库存模型：学完之后，大家要能看懂一个ERP库存查询页、仓库档案页、库存汇总表背后的设计逻辑。

## 3. 课程内容

### 3.1 进销存库存 vs ERP库存：差异到底在哪里

先把两类系统的库存问题拆开。

进销存库存管理回答的核心问题是：

```text
仓库里还剩多少？
```

ERP库存管理要回答的问题要多得多：

1. 这批货在哪个真实仓库？
2. 这批货属于哪个货主或组织？
3. 这批货现在处于什么业务状态？
4. 这批货按什么业务口径统计？
5. 这批货现在能不能被销售、分配或承诺？

| 对比维度 | 进销存库存 | ERP库存 |
| --- | --- | --- |
| 核心问题 | 还剩多少 | 在哪、归谁、什么口径、能不能用 |
| 仓储维度 | 单仓或少量仓库 | 多实体仓 + 多逻辑仓 |
| 库存状态 | 多数只看账面库存/可用库存 | 可售、锁定、在途、待检、退货、残品、渠道预留 |
| 业务口径 | 通常不区分 | 按用途、渠道、质量、过程状态、组织区分 |
| 时间维度 | 主要看当前 | 还要看在途、预计到货、已发未收 |
| 系统协同 | 通常在一个系统闭环 | 要和WMS、OMS/POS、渠道系统、金蝶协同 |

可以概括成一句话：

> 进销存管的是仓库里还剩多少货，ERP管的是这批货在集团经营视角下属于哪个仓、什么状态、哪个口径、能不能被承诺。

#### 数据推演：同一批库存，进销存怎么记

假设强盛科技现在有一款商品：

```text
SKU：QC100
商品：氮化镓充电头
```

如果用进销存式库存表，大概会这样记录：

| 仓库 | SKU | 库存数量 |
| --- | --- | ---: |
| 深圳总仓 | QC100 | 1200 |
| 东莞仓 | QC100 | 2150 |
| 南山门店 | QC100 | 800 |
| 供应商在途 | QC100 | 2500 |
| **合计** | - | **6650** |

这张表能回答：

```text
每个仓库大概有多少货？
```

但它回答不了：

| 想问的问题 | 能不能回答 | 原因 |
| --- | --- | --- |
| 东莞仓2150个里，能卖的有几个？ | 不能 | 仓库字段只记录位置，不记录业务状态 |
| 南山门店800个是不是全都能卖？ | 不能 | 里面可能有残品、样机、锁定品 |
| 供应商在途2500个预计什么时候到？ | 不能 | “在途”被硬塞进仓库列，没有过程信息 |
| 哪些货已经准备发FBA？ | 不能 | 没有业务用途口径 |
| 哪些货已经给天猫活动预留？ | 不能 | 没有渠道预留口径 |

这不是进销存设计错了。

在单仓、少渠道、库存状态简单的阶段，这样记录够用。

但到了ERP阶段，库存表不能只回答“有多少”，还要回答“这批货能不能被谁使用”。

### 3.2 ERP库存 vs WMS库存：经营视角和实物视角

讲ERP库存时，还要先和WMS库存区分开。

WMS管仓库内部作业：

- 货在哪个库区？
- 货在哪个库位？
- 有没有扫码上架？
- 能不能拣出来？
- 出库有没有复核？

ERP管库存的经营属性：

- 这批货能不能卖？
- 这批货归谁？
- 这批货属于哪个业务用途？
- 这批货是不是在途、待检、预留、锁定？
- 这批货能不能参与全渠道可售计算？

| 对比维度 | ERP库存视角 | WMS/仓库库存视角 |
| --- | --- | --- |
| 管什么 | 库存的经营属性 | 库存的实物操作 |
| 核心关心 | 能不能卖、归谁管、什么口径 | 在哪个库位、能不能拣、数量对不对 |
| 管理维度 | 实体仓 + 逻辑仓 + 货主/组织 | 实体仓 + 库区 + 库位 + 作业状态 |
| 与订单关系 | 决定能不能承诺 | 决定能不能实际拣货出库 |
| 与财务关系 | 影响成本、归属、结算 | 提供实收实发依据 |

一句话：

> WMS问的是“货在哪个货架”，ERP问的是“这批货处于什么业务状态、归谁管、能不能用”。

本讲站在ERP视角讲库存模型，不展开WMS里的库位、波次、PDA和拣货路径。

ERP与WMS的接口和一致性问题，会放到第8讲。

### 3.3 实体仓和逻辑仓：先分清两个层级

ERP库存模型里，最核心的两个概念是实体仓和逻辑仓。

| 概念 | 回答的问题 | 例子 |
| --- | --- | --- |
| 实体仓 | 货真实放在哪个仓库节点 | 深圳总仓、东莞仓、南山门店仓、FBA仓 |
| 逻辑仓 | ERP按什么业务口径统计和管理库存 | 国内电商仓、门店仓、FBA备货仓、正常品仓、在途仓 |

实体仓是物理位置。

逻辑仓是业务统计口径。

用一个例子说明。

东莞实体仓里有10000个QC100充电头。

如果没有逻辑仓，库存记录只能这样写：

| 实体仓 | SKU | 数量 |
| --- | --- | ---: |
| 东莞仓 | QC100 | 10000 |

系统只能回答：

```text
东莞仓有10000个QC100。
```

但它答不了：

- 多少给国内电商卖？
- 多少给门店卖？
- 多少要发FBA？
- 多少是残品？

加上逻辑仓之后，同样10000个货可以这样表达：

| 实体仓 | 逻辑仓 | 拆分口径 | SKU | 数量 |
| --- | --- | --- | --- | ---: |
| 东莞仓 | 国内电商可售仓 | 业务用途 | QC100 | 5000 |
| 东莞仓 | 门店可售仓 | 业务用途 | QC100 | 3000 |
| 东莞仓 | 残品待处理仓 | 质量状态 | QC100 | 2000 |
| **合计** | - | - | - | **10000** |

现在系统能回答：

```text
东莞仓总共有10000个。
其中国内电商可售5000个。
门店可售3000个。
残品待处理2000个。
```

这就是逻辑仓的价值：

> 它不是多造一个真实仓库，而是给同一个实体仓里的货贴上不同的业务标签。

课堂演示时，可以打开仓库档案或库存查询页，让学员观察两个字段：

| 页面字段 | 看什么 |
| --- | --- |
| 实体仓/仓库 | 它对应真实仓库节点 |
| 逻辑仓/库存口径/库存类型 | 它对应业务统计口径 |

### 3.4 没有逻辑仓时，ERP怎么“硬撑”

只讲“逻辑仓是什么”还不够。

要让学员理解为什么需要逻辑仓，最好先看没有逻辑仓时，系统会怎么难受。

假设深圳总仓有1000个QC100。

最简单的库存表是：

| SKU | 实体仓 | 总库存 |
| --- | --- | ---: |
| QC100 | 深圳总仓 | 1000 |

后来业务要求区分国内电商、门店、跨境FBA、批发。

如果没有逻辑仓，系统常见做法是硬加一个“业务部门”字段：

| SKU | 实体仓 | 业务部门 | 库存数量 |
| --- | --- | --- | ---: |
| QC100 | 深圳总仓 | 国内电商部 | 400 |
| QC100 | 深圳总仓 | 门店事业部 | 250 |
| QC100 | 深圳总仓 | 跨境电商部 | 200 |
| QC100 | 深圳总仓 | 批发业务部 | 150 |
| **合计** | **深圳总仓** | - | **1000** |

看起来能用了。

但“业务部门”不是库存管理口径，它只是组织结构。

比如新增采购入库300个，这次采购需求只来自国内电商和门店：

| 需求来源 | 需求数量 |
| --- | ---: |
| 国内电商部 | 180 |
| 门店事业部 | 120 |
| 跨境电商部 | 0 |
| 批发业务部 | 0 |
| **合计** | **300** |

如果系统只能按历史固定比例分配库存：

| 部门 | 固定分配比例 |
| --- | ---: |
| 国内电商部 | 40% |
| 跨境电商部 | 20% |
| 门店事业部 | 30% |
| 批发业务部 | 10% |

系统分配结果会变成：

| 部门 | 真实需求 | 固定比例分配结果 | 差异 |
| --- | ---: | ---: | ---: |
| 国内电商部 | 180 | 120 | -60 |
| 门店事业部 | 120 | 90 | -30 |
| 跨境电商部 | 0 | 60 | +60 |
| 批发业务部 | 0 | 30 | +30 |
| **合计** | **300** | **300** | **0** |

总数没错，业务分配错了。

这就是“没有逻辑仓”时的典型问题：

> 总库存看起来是对的，但每个业务口径下的库存是错的。

业务再复杂一点，系统可能继续加字段：

| SKU | 实体仓 | 业务部门 | 是否残品 | 是否在途 | 是否活动预留 | 数量 |
| --- | --- | --- | --- | --- | --- | ---: |
| QC100 | 深圳总仓 | 国内电商部 | 否 | 否 | 是 | 100 |
| QC100 | 深圳总仓 | 国内电商部 | 否 | 否 | 否 | 300 |
| QC100 | 深圳总仓 | 门店事业部 | 否 | 是 | 否 | 120 |
| QC100 | 深圳总仓 | 跨境电商部 | 否 | 是 | 否 | 200 |
| QC100 | 深圳总仓 | 批发业务部 | 是 | 否 | 否 | 20 |

这张表已经很难用了：

- 部门、质量状态、过程状态、活动预留混在一起；
- 每新增一种业务口径，就可能新增字段或枚举；
- 查询“国内电商可售库存”时，要排除残品、在途、活动预留；
- 查询“全公司在途库存”时，又要跨部门汇总；
- 对接WMS时，WMS不一定理解这些ERP业务字段。

所以，逻辑仓不是为了多造一个字段。

它解决的是ERP库存表达能力的问题。

### 3.5 有了逻辑仓之后，库存怎么表达

引入逻辑仓之后，ERP不再把用途、质量、过程状态都硬塞进不同字段，而是统一放到“逻辑仓”这个维度上。

库存表可以变成：

```text
货主/组织 + SKU + 实体仓 + 逻辑仓 + 数量
```

还是同样1000个库存，可以这样表达：

| 货主/组织 | SKU | 实体仓 | 逻辑仓 | 逻辑仓口径 | 库存数量 |
| --- | --- | --- | --- | --- | ---: |
| 强盛总部 | QC100 | 深圳总仓 | 国内电商销售仓 | 业务用途 | 400 |
| 强盛总部 | QC100 | 深圳总仓 | 门店备货仓 | 业务用途 | 250 |
| 强盛跨境事业部 | QC100 | 深圳总仓 | 跨境FBA备货仓 | 业务用途 | 200 |
| 强盛总部 | QC100 | 深圳总仓 | 批发业务仓 | 业务用途 | 150 |
| **合计** | - | **深圳总仓** | - | - | **1000** |

现在系统可以直接回答：

| 问题 | 查询方式 | 结果 |
| --- | --- | ---: |
| 深圳总仓总库存是多少 | 按实体仓汇总 | 1000 |
| 国内电商能用多少 | 查国内电商销售仓 | 400 |
| 门店备货有多少 | 查门店备货仓 | 250 |
| 跨境FBA准备发多少 | 查跨境FBA备货仓 | 200 |
| 批发业务还能用多少 | 查批发业务仓 | 150 |

再看刚才那次采购入库300个。

有逻辑仓之后，不需要按固定比例分配，直接入到对应逻辑仓：

| 入库节点 | 逻辑仓 | 入库前 | 本次入库 | 入库后 |
| --- | --- | ---: | ---: | ---: |
| 采购入库 | 国内电商销售仓 | 400 | 180 | 580 |
| 采购入库 | 门店备货仓 | 250 | 120 | 370 |
| 采购入库 | 跨境FBA备货仓 | 200 | 0 | 200 |
| 采购入库 | 批发业务仓 | 150 | 0 | 150 |
| **合计** | - | **1000** | **300** | **1300** |

库存不仅总数正确，业务归属也正确。

再看客退待检。

国内电商退回50个，仓库收到后还没检测。

如果没有逻辑仓，系统可能直接加回深圳总仓总库存：

| SKU | 实体仓 | 总库存 |
| --- | --- | ---: |
| QC100 | 深圳总仓 | 1350 |

总库存增加了，但系统没说清楚这50个能不能卖。

有逻辑仓之后，这50个进入退货待检仓：

| 逻辑仓 | 退货前库存 | 本次变化 | 退货后库存 | 是否可用于常规销售 |
| --- | ---: | ---: | ---: | --- |
| 国内电商销售仓 | 580 | 0 | 580 | 是 |
| 退货待检仓 | 0 | +50 | 50 | 否 |
| 深圳总仓合计 | 1300 | +50 | 1350 | - |

这时系统能同时表达两件事：

```text
深圳总仓总库存：1350
国内电商可销售：580
退货待检：50
```

这才是ERP库存模型要解决的问题。

### 3.6 逻辑仓可以按哪些口径拆

逻辑仓不是固定类型，而是一种分析方法。

不要让学员死记“可售仓、残品仓、在途仓”这些名字。

真正要掌握的是：每次拆逻辑仓时，先问自己：

```text
我按什么口径在拆？
```

常见有五类：

| 拆分口径 | 逻辑仓例子 | 解决什么问题 |
| --- | --- | --- |
| 按业务用途 | 国内电商仓、门店销售仓、跨境FBA备货仓、批发业务仓 | 不同业务团队各有库存池，避免互相抢货 |
| 按商品质量状态 | 正常品仓、残品仓、退货待检仓、二手品仓 | 区分能不能正常销售、是否需要处理 |
| 按过程状态 | 采购在途仓、门店在途仓、委外加工仓 | 记录货物不在当前实体仓、但还没进入目标仓的中间状态 |
| 按渠道/活动预留 | 天猫活动仓、京东预留仓、门店开业备货仓 | 给特定渠道或活动保留库存 |
| 按组织/货主 | A事业部仓、B事业部仓、子公司库存仓 | 区分库存归属、结算主体和经营责任 |

以前有些资料会把“在途仓、冻结仓、渠道预留仓”称为“虚拟仓”。

本讲不把虚拟仓作为和实体仓、逻辑仓并列的第三类仓库。

在本课程里：

> 虚拟仓只是逻辑仓的一种叫法，本质仍然是逻辑仓。它通常不对应真实存储区域，而是用来承接过程状态或规则分配。

### 3.7 进销存里的“仓库”到底是什么

回到一个基础问题：

进销存里的“仓库”，到底是实体仓还是逻辑仓？

答案是：

> 兼有。它在物理上对应真实库房，在业务上默认代表这个库房里所有可用、可卖的库存。

为什么可以合在一起？

因为进销存场景足够简单：

- 多数情况下只有一个或少量仓库；
- 库存状态基本只有“可卖”这一种；
- 没有复杂在途；
- 没有多渠道库存拆分；
- 没有多组织、多货主归属。

用数据看更直观。

Phase 3 时，只有深圳总仓，所有货基本都可卖：

| 仓库 | SKU | 数量 | 能不能卖 |
| --- | --- | ---: | --- |
| 深圳总仓 | QC100 | 3000 | 能 |

这时候，“仓库”字段够用。

到了Phase 4，还是沿用进销存结构，就会变成打补丁：

| 仓库 | SKU | 数量 | 备注 |
| --- | --- | ---: | --- |
| 深圳总仓 | QC100 | 800 | 可售 |
| 东莞仓 | QC100 | 2000 | 其中150个残品 |
| 东莞仓 | QC100 | 1000 | FBA备货 |
| 南山门店 | QC100 | 500 | 可售 |
| 在途 | QC100 | 3000 | 供应商发货未到 |

你会发现：

- 同一个东莞仓要出现多行；
- “在途”被硬塞进仓库列；
- “备注”开始承担业务规则；
- 系统越来越依赖人工理解。

这个时候，临界点就到了。

> 当你开始觉得“这批货在哪”和“这批货能不能用”是两个不同问题时，就需要拆开实体仓和逻辑仓。

### 3.8 逻辑仓和实体仓的关系：可映射，也可以不映射

逻辑仓不是凭空存在的。

绝大多数逻辑仓最终要知道背后对应哪个实体仓。

因为ERP可以按逻辑仓管理库存，但真实收发货仍然要落到实体仓或WMS。

| 关系 | 说明 | 例子 |
| --- | --- | --- |
| 一个实体仓可以挂多个逻辑仓 | 一个真实仓库里的货，按不同业务口径拆成多个逻辑仓管理 | 东莞仓拆成电商可售仓、门店仓、FBA备货仓 |
| 一个逻辑仓要知道背后的实体仓 | 逻辑仓是管理维度，最终收发货要落到真实仓库 | 国内电商可售仓的货实际在东莞仓 |
| 逻辑仓可以和WMS库区映射 | 精细路径，WMS知道哪些库位放电商货、哪些放门店货 | WMS在库区层面做物理隔离 |
| 逻辑仓也可以不和WMS库区映射 | 简化路径，仓库只管总实物，ERP自己拆业务账 | WMS不感知逻辑仓，ERP按入库用途划分 |

这里的取舍很重要：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 逻辑仓和WMS区域有映射 | 精细、准确、好追溯 | 仓库作业复杂，同SKU可能分散存放 |
| 逻辑仓和WMS区域无映射 | 仓库效率高、操作简单 | ERP要自己分配和拆账，异常时规则复杂 |

课堂演示时，可以结合系统页面看两个地方：

| 页面 | 看点 |
| --- | --- |
| 仓库档案 | 一个实体仓下面是否配置多个逻辑仓 |
| 库存查询 | 同一个实体仓下，库存是否能按逻辑仓拆开查看 |

### 3.9 在途管控：在途仓是按过程状态拆出来的逻辑仓

在途仓是最适合课堂演示的逻辑仓案例。

强盛科技从深圳总仓发500个充电头到南山门店，物流要走3天。

这3天里，这批库存怎么记？

#### 错误方案一：发出就减深圳，门店收货再加

| 时间 | 深圳总仓 | 南山门店 | 总库存 |
| --- | ---: | ---: | ---: |
| 发出前 | 5000 | 800 | 5800 |
| 发出确认 | 4500 | 800 | 5300 |
| 收货确认 | 4500 | 1300 | 5800 |

问题：路上3天，总库存凭空少了500。

#### 错误方案二：发出不减，收货再处理

| 时间 | 深圳总仓 | 南山门店 | 总库存 |
| --- | ---: | ---: | ---: |
| 发出前 | 5000 | 800 | 5800 |
| 发出后 | 5000 | 800 | 5800 |
| 收货确认 | 4500 | 1300 | 5800 |

问题：深圳总仓一直显示5000，但其中500已经不在仓里，可能继续被订单承诺，导致超卖。

#### 正确方案：进入在途仓

| 节点 | 深圳总仓 | 门店在途仓 | 南山门店 | 总库存 |
| --- | ---: | ---: | ---: | ---: |
| 发出前 | 5000 | 0 | 800 | 5800 |
| 发出确认 | 4500 | 500 | 800 | 5800 |
| 收货确认 | 4500 | 0 | 1300 | 5800 |

在途仓的作用是：

> 让库存不凭空消失，也不提前进入接收方可用库存。

在途不只发生在门店补货。

采购在途也一样：供应商已发货，但企业仓库还没收货，这段时间也可以通过采购在途仓记录。

所以在途仓不是特殊的新概念。

它就是按“过程状态”拆出来的一种逻辑仓。

### 3.10 多仓库存如何汇总和统计

有了实体仓、逻辑仓、货主之后，库存查询就不能只给一个“总库存”。

同一批底层库存，按不同角色的问题，应该得到不同答案。

假设强盛科技有以下库存：

| 货主 | 实体仓 | 逻辑仓 | 拆分口径 | SKU | 数量 |
| --- | --- | --- | --- | --- | ---: |
| 强盛科技 | 深圳总仓 | 电商可售仓 | 用途 | QC100 | 800 |
| 强盛科技 | 深圳总仓 | 门店可售仓 | 用途 | QC100 | 400 |
| 强盛科技 | 深圳总仓 | FBA备货仓 | 用途 | QC100 | 600 |
| 强盛科技 | 东莞仓 | 电商可售仓 | 用途 | QC100 | 1000 |
| 强盛科技 | 东莞仓 | 门店可售仓 | 用途 | QC100 | 500 |
| 强盛科技 | 东莞仓 | 残品待处理仓 | 质量 | QC100 | 150 |
| 强盛数码 | 东莞仓 | 子公司可售仓 | 组织 | QC100 | 1500 |
| 强盛科技 | 南山门店 | 门店可售仓 | 用途 | QC100 | 750 |
| 强盛数码 | 南山门店 | 子公司可售仓 | 组织 | QC100 | 200 |
| - | 在途口径 | 采购在途仓 | 过程 | QC100 | 3000 |
| - | 在途口径 | 门店在途仓 | 过程 | QC100 | 500 |

不同人问“库存有多少”，系统不能给同一个答案。

| 问的人 | 口径 | 汇总逻辑 | 答案 |
| --- | --- | --- | ---: |
| 供应链总监 | 全公司总库存 | 所有行相加 | 9400 |
| 销售运营 | 可售库存 | 电商可售 + 门店可售 + 子公司可售 | 4150 |
| 仓库主管 | 东莞仓总实物 | 实体仓=东莞仓，所有逻辑仓相加 | 3150 |
| 品质管理 | 残品库存 | 逻辑仓=残品待处理仓 | 150 |
| 供应链计划 | 在途库存 | 采购在途 + 门店在途 | 3500 |
| 子公司财务 | 强盛数码库存 | 货主=强盛数码 | 1700 |

关键点是：

> 同一批底层库存，按不同维度汇总，会得到不同数字，而且这些数字都可能是正确的。

产品经理设计库存查询页时，不能只给一个“总库存”。

至少要考虑：

| 统计问题 | 汇总方式 |
| --- | --- |
| 全公司某SKU一共有多少 | 按SKU汇总 |
| 某个实体仓里有多少货 | 按实体仓汇总 |
| 某个业务用途还有多少 | 按逻辑仓用途口径汇总 |
| 正常品和残品分别多少 | 按逻辑仓质量口径汇总 |
| 在途还有多少 | 按逻辑仓过程状态汇总 |
| 某个货主/组织有多少 | 按货主/组织汇总 |

### 3.11 全渠道一盘货：逻辑仓口径继续扩展

全渠道一盘货是后面第6讲和第7讲的重点。

这一讲先讲它和逻辑仓模型的关系。

很多人以为全渠道一盘货就是：

```text
把所有仓库库存加起来，然后所有渠道一起卖
```

这个理解不对。

如果真的这么做：

- 天猫大促可能抢走门店开业备货；
- 京东订单可能抢走FBA备货；
- 批发大单可能把电商日常可售打穿；
- 总库存看起来很多，但每个渠道都觉得自己不够用。

所以，全渠道一盘货不是粗暴加总，而是要在统一库存模型上继续拆渠道口径。

| 全渠道场景下的逻辑仓 | 含义 |
| --- | --- |
| 全渠道共享池 | 多渠道共用的基础库存池，未被任何渠道预留 |
| 天猫可售仓 | 给天猫日常销售可承诺的库存 |
| 京东可售仓 | 给京东日常销售可承诺的库存 |
| 门店可售仓 | 门店可销售库存 |
| FBA备货仓 | 准备发往FBA的库存 |
| 批发业务仓 | 给大客户/经销商预留的库存 |

还是东莞仓10000个QC100。

如果不按渠道拆：

| 实体仓 | SKU | 数量 |
| --- | --- | ---: |
| 东莞仓 | QC100 | 10000 |

运营问：天猫能卖多少？京东能卖多少？门店留多少？

系统答不上来。

加上渠道逻辑仓后：

| 实体仓 | 逻辑仓（渠道口径） | SKU | 数量 | 说明 |
| --- | --- | --- | ---: | --- |
| 东莞仓 | 全渠道共享池 | QC100 | 3000 | 未被渠道预留，可弹性分配 |
| 东莞仓 | 天猫可售仓 | QC100 | 3000 | 天猫日常可卖 |
| 东莞仓 | 京东可售仓 | QC100 | 1000 | 京东日常可卖 |
| 东莞仓 | 门店可售仓 | QC100 | 1000 | 线下门店可卖 |
| 东莞仓 | FBA备货仓 | QC100 | 2000 | 准备发FBA，暂不参与国内销售 |
| **合计** | - | - | **10000** | - |

当运营决定给天猫大促再追加1000个库存，可以做库存口径调整：

| 操作 | 全渠道共享池 | 天猫可售仓 | 京东可售仓 | 门店可售仓 | FBA备货仓 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 调整前 | 3000 | 3000 | 1000 | 1000 | 2000 |
| 共享池调整到天猫1000 | 2000 | 4000 | 1000 | 1000 | 2000 |

这个动作不一定涉及真实仓库搬货。

它只是ERP库存口径发生变化。

第4讲到这里收住。

第6讲会先讲三层库存模型（实物层→调度层→销售层），理清ERP库存和渠道库存的关系。第7讲再深入讲：

- 渠道库存怎么分配（独占/共享/固定值）；
- 订单什么时候锁定库存、什么时候释放；
- 库存同步规则怎么配置；
- 平台库存同步怎么防超卖。

### 3.12 本讲小结：ERP库存模型的核心维度

这一讲可以收成一个公式：

```text
ERP库存 = 货主/组织 + SKU + 实体仓 + 逻辑仓 + 数量 + 可用规则
```

| 维度 | 作用 |
| --- | --- |
| 货主/组织 | 这批库存归谁，后续成本和结算归谁 |
| SKU | 管的是哪一个具体商品 |
| 实体仓 | 货真实在哪个仓库节点 |
| 逻辑仓 | 按什么业务口径统计和管理 |
| 数量 | 当前库存是多少 |
| 可用规则 | 能不能卖、能不能分配、能不能承诺 |

这不是为了把库存表设计得复杂。

而是因为ERP阶段的库存问题，本来就不是一个“仓库 + 数量”能讲清楚的。

第3讲讲的是单据分层。

第4讲讲的是库存分层。

单据分层解决“业务怎么一步步发生”；库存分层解决“每一步之后，库存按什么口径变化”。
