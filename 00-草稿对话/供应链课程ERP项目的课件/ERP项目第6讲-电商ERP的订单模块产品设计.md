## 1. 课程背景
第5讲我们讲了自研ERP里的B2B销售履约。B2B批发订单可以用三层单据理解：

```latex
销售订单 → 销售发货通知单 → 销售出库单
```

但如果强盛科技未来要自己做电商ERP，光理解B2B销售单据是不够的。所以这一讲，我们先做一个学习假设：

> 强盛科技准备自研一套电商ERP/OMS，用来承接天猫、京东、抖音、Amazon等平台订单。我们作为产品经理，要先理解成熟电商ERP大概怎么处理订单、怎么对接仓库、怎么管理库存，再参考聚水潭、领星这类系统，拆出自己要做的核心模块。
>

好消息是，市面上可以参考的产品很多。聚水潭、领星、万里牛、赛狐、马帮、店小秘——注册一个账号就能看订单模块长什么样、审核规则怎么配、库存从哪扣。竞品学习门槛远低于 B2B 三层单据的 ERP——后者大多是内部系统，你根本看不到。

:::info
本讲拆解 SaaS ERP 的内部机制，目的是建立竞品拆解能力和认知框架，**不代表强盛科技的自研 ERP 要重做一套聚水潭**。第 5 讲的结论依然成立——B2C 履约由 SaaS 主控，自研 ERP 接结果。

:::

## 2. 学习目标

+ 能看懂电商订单审核规则引擎（库存校验、地址校验、分仓/寻仓、物流匹配、拆合单、Hold 单、黑名单的用途和顺序）
+ 能说清寻仓和锁库的时序（先查库存→寻仓→锁库→锁失败后怎么处理）
+ 能区分本地仓和三方仓履约的两套逻辑（推单方式、库存校验次数、异常处理方式的本质差异）

+ 能产出订单管理产品设计稿（业务流程图、系统流程图、订单状态机、产品结构图、关键页面原型）

## 3. 课程内容
### 3.1 先看一条订单怎么流转
电商ERP的订单模块，核心不是"录入销售订单"。它要做的是：**把来自多个电商平台、多个店铺的订单，转换成仓库可以执行的发货任务，并把履约结果回传给平台。**

一条典型国内电商订单，大体会经过这些节点：

![](https://cdn.nlark.com/yuque/__mermaid_v3/e256bdf1eb310875bac6cfec0495230a.svg)

> 合单和 Hold 是进单后就能判断的规则，不需要等到寻仓或物流完成后才触发——合单要在分仓前做，合并后才知道整体要发多少货；Hold 随时可挂起。拆单则相反，通常在确仓之后才做，因为要先知道从哪几个仓发、有没有超出包裹限重，才能决定怎么拆。
>

这条链路和第5讲B2B销售三层单据不一样。

| 对比项 | B2B自研ERP销售 | B2C电商ERP订单 |
| --- | --- | --- |
| 订单来源 | 销售录单、客户订单、合同 | 平台订单、店铺订单、平台推送 |
| 核心压力 | 客户、价格、信用、账期、分批发货 | 高频、小单、平台规则、自动审单、时效 |
| 单据表达 | L1销售订单、L2发货通知、L3销售出库 | 平台订单、审核单、发货单、出库单、售后单等，命名因系统而异 |
| 库存判断 | L1审核时确定仓库并预占 | 审核、配货、打单前后都可能触发库存判断 |
| 结果回传 | 主要回写ERP内部和财务 | 必须回传平台物流单号和发货状态 |


我们并不需要复刻一个完整聚水潭或领星订单模块，重点是把订单、履约、库存等模块的精华知识提取出来，让大家"见多识广"，增加业务画面感。

### 3.2 平台订单如何进入 ERP
当消费者在电商平台购物下单之后，电商平台会先有一层自己的订单处理逻辑，例如消费者可能是在多个店铺内购买了多个商品，然后集中下单支付的，电商平台会根据店铺拆分订单，然后把订单推送给卖家的后台，**在电商卖家后台看到的订单已经是平台拆过一次单**了。（电商平台的OMS和电商ERP的OMS虽然都叫OMS，但是效果并不一样）

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692499951880-ce9ca64d-5d94-4b3d-9314-042dde408c58.png" width="4644" title="除了按商家拆分，还有按商品类型（实体货物/虚拟货物），订单类型（FBA订单/FBM订单）等" crop="0,0,1,1" id="PsufK" class="ne-image">

ERP需要获取电商平台的订单，就需要提前和电商平台进行API对接，对接的流程和细节就比较多了，这里不做详细的介绍，先了解大概的流程即可：

1. 申请成为电商平台的开发者；
2. 对接电商平台的业务接口，完成接口对接工作；
3. 在电商ERP上授权店铺，获得访问店铺数据的权限；
4. 在ERP上拉取已授权店铺的订单数据；

:::info
卖家将自己的店铺授权在ERP上之后，就可以通过ERP去拉取店铺中的订单信息，订单信息拉取一般有三种方式：

1. 电商平台通过消息推送的方式，通知给ERP，然后ERP接收到了通知之后再触发任务去拉取订单；
2. ERP自己设置定时任务，例如每10分钟拉取一次，从电商平台上拉取订单数据到ERP上；
3. 在ERP上做一个"手动拉取"的功能，当想要拉取新的信息的时候，点击一下"手动拉取"就会自动拉取最新的数据到ERP上；

:::

| 获取方式 | 怎么工作 | 适用场景 | 产品设计关注点 |
| --- | --- | --- | --- |
| 平台消息推送 | 平台有新订单后通知ERP，ERP再拉取订单详情 | 平台接口能力较完善，要求时效较高 | 消息丢失、重复推送、补偿拉取 |
| 定时任务拉取 | ERP每隔一段时间主动调用平台接口拉订单 | 大多数SaaS ERP常见做法 | 拉取频率、接口限流、增量游标 |
| 手动拉取 | 运营人工点击按钮补拉订单 | 异常兜底、历史订单补拉 | 权限、时间范围、重复订单校验 |


<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690294625127-971ccdf6-79d4-4742-bb76-86d9983b64a8.png" width="2324" title="" crop="0,0,1,1" id="NWKQr" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722242160123-e93c23d6-0e94-4a97-9375-0daadf148149.png" width="1482" title="速卖通订单同步到ERP的推荐方案" crop="0,0,1,1" id="PLluA" class="ne-image">

:::info
订单拉取到了ERP之后，一般订单中的信息会包含这些：

1. 平台订单的信息：平台名称，店铺名称、平台订单号、下单时间、买家留言/备注，订单状态……
2. 买家/用户的信息：用户ID，用户名称，用户等级，收件地址……
3. 订单的产品信息：平台SKU、商品编码、商品名称，数量，单价，总价，优惠金额……
4. 其他信息：卖家备注，业务人员，标签……

:::

订单进入ERP后，至少要保留这些信息：

| 信息类型 | 典型字段 | 为什么重要 |
| --- | --- | --- |
| 平台信息 | 平台、店铺、平台订单号、平台订单状态 | 区分来源、幂等校验（平台订单号+店铺+子单号）、状态回传 |
| 买家信息 | 买家账号、收货人、电话、地址、买家留言 | 物流匹配、地址校验、客服处理 |
| 商品信息 | 平台SKU、商品名称、数量、单价、优惠金额 | SKU映射、库存判断、应收计算 |
| 运营信息 | 卖家备注、客服备注、标签、业务员 | 审核规则、人工处理、异常识别 |
| 履约信息 | 仓库、物流公司、运费、期望发货时间 | 寻仓、物流匹配、履约时效 |


<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1685460870871-0edd6850-214a-4478-b9f0-5e807772434f.png" width="2194" title="聚水潭ERP订单" crop="0,0,1,1" id="oNUbN" class="ne-image">

这里要强调一个产品设计点：

> 平台订单号、店铺、平台子单号通常要进入幂等校验条件。否则平台重复推送、ERP重复拉取时，系统可能生成两张订单，导致重复锁库、重复发货。
>

#### SKU映射：先维护好，订单履约时再校验
当电商平台订单拉取到了ERP之后，还需要对平台SKU进行"商品配对"处理，也就是要用平台SKU去匹配一下本地的SKU，便于后续履约的时候判断库存相关的信息。

:::color1
为什么要做商品配对呢？

因为在电商平台上销售的商品，对应的SKU或者编码可能和实际仓库中（库存商品）定义的SKU并不太一样。

每个电商平台会有自己的商品上架要求，有些时候在平台上的商品SKU会有自己的定义规则，所以就会导致订单拉取到了本地之后，需要通过配对映射才知道具体仓库要发什么商品。

:::

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692508504787-e993b3a6-fa3f-42eb-a1e7-87e9d754cb44.png" width="2444" title="妙手ERP选择第三方仓库发货" crop="0,0,1,1" id="WUNMp" class="ne-image">

同一个实物商品，在不同系统里可能有不同编码——不止平台SKU和本地SKU两段，实际业务中可能存在四层：

| 层级 | 示例 | 谁维护 | 用途 |
| --- | --- | --- | --- |
| 平台SKU | TM-QC100-BLK-65W | 天猫/京东/抖音店铺运营 | 平台上架、展示、交易 |
| ERP本地SKU | QC100-BLK-65W | 企业商品主数据 | 采购、库存、成本、销售分析 |
| WMS仓库SKU | WH-QC100-BLK | 仓库/WMS | 拣货、复核、出库 |
| 三方仓SKU | 3PL-QC100-BLK | 第三方仓 | 外部仓履约 |


![](https://cdn.nlark.com/yuque/__mermaid_v3/d21640f9e3a97765e85c8c70aba9eb28.svg)

为什么要先映射？因为库存判断要看的是企业内部SKU或仓库SKU。如果平台订单只告诉ERP："平台SKU = TM-QC100-BLK-65W，购买数量 = 2"，但ERP不知道它对应哪个本地SKU，就无法回答：

+ 这个商品公司内部叫什么？
+ 哪些仓库有货？
+ 这个商品是否允许从当前渠道发？
+ WMS拣货时应该拣哪个仓库SKU？
+ 退货回来后应该回到哪个SKU库存？

所以，SKU映射通常应该在商品上架、店铺授权、系统初始化或仓库对接阶段提前维护好，而不是等订单来了才临时匹配。订单履约阶段要做的是校验映射是否完整、是否有效。

:::info
前置阶段：维护平台SKU、ERP本地SKU、WMS/三方仓SKU之间的映射关系

履约阶段：订单进入后校验映射是否完整，异常订单阻断审核

:::

### 3.3 审核规则引擎：先看库存和履约相关部分
#### 寻仓寻物流
订单要完成履约发货，首先需要确认从什么仓库发，用什么物流方式发，这两个是履约的核心信息，而电商平台拉下来的订单是没有指定仓库和物流的，所以在订单管理的界面需要有"设定仓库和物流"的功能。

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690357709884-3d8e0f91-2706-4f39-a63a-bc1afb9bc047.png" width="2070" title="" crop="0,0,1,1" id="vRD68" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722245084504-5fe95680-56ed-4d29-a741-248d0418605e.png" width="3830" title="" crop="0,0,1,1" id="ASExl" class="ne-image">

仓库和物流的信息需要提前在相关的模块维护好，例如仓库的创建和配置，对接物流商，创建物流渠道，完成货物的采购入库等。

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722246575161-24354410-9e24-4548-bdbf-dd8aa9cd7c0e.png" width="2434" title="" crop="0,0,1,1" id="PTUet" class="ne-image">

#### 拆单、合单、Hold单
平台的订单已经到了ERP后，ERP可以对订单再进行一次拆分处理，也可以不做拆分处理。ERP在审核处理订单的时候，拆合单是一个高频的动作，一般来说拆单是为了更好地履约，例如说仓库库存不够，某个订单中的商品缺货了部分商品要先发出，商品数量太多，体积太大等拆分。而合单则是为了减少履约成本，把相同客户，相同店铺，相同地址的订单合并为一个去履约，减少物流的成本。三者都属于审核规则引擎的一部分，但触发时机和依赖条件不同：

**合单**：在分配仓库之前触发。把同一客户、同一收货地址的多笔待处理订单合并为一笔，合并后再统一判断从哪个仓发、用什么物流，降低履约成本。如果等选完仓再合单，仓库可能已经分配不同，反而更麻烦。

**Hold单**：任何阶段都可以挂起。未到预售发货时间、平台要求延迟发货、客户留言待确认、风控标记等情况，都可以把订单挂起，暂停流入发货环节，等条件满足后再释放。

**拆单**：通常在确仓之后触发。常见触发条件：订单商品分布在不同仓库（多仓拆单）、单包裹超重超体积（按包裹拆单）、部分商品缺货先发可发部分（缺货拆单）。这些判断必须先知道从哪个仓发，才能知道要不要拆。

根据"珍珠奶茶学习法"，我建议大家在刚开始学习的时候先不要考虑拆单，合单，Hold单的问题，而是关注ERP的订单信息怎么流转，怎么处理，这些是主线的流程，也是更加适合新手学习的流程。

电商订单履约的核心：**就是把电商平台的订单转化为仓库可作业的发货单/出库单，当仓库发货之后再回传物流信息给ERP，ERP再推送给电商平台即算完成了订单履约的流程**。

#### 审核规则的完整体系
当这些"待审核"的内容都完成了之后，订单就可以进入履约状态（发货中）。对于ERP或者OMS来说，订单审核规则也可以称之为订单策略，订单规则，是非常重要的核心模块之一，因为强大的审核规则可以释放人力，减轻人工运营的成本，同时也能提升订单自动化处理的时效，尽快完成履约。

订单审核的作用一般有：

:::success
1. 检查仓库（该商品是否有库存）
2. 审核买家的需求（如物流公司、地址修改、包装要求、发票等）
3. 客户备注（是否有赠品，替换颜色尺码等）
4. 审查商品价格、运费设置等是否符合店铺要求（防止价格错误）
5. 检查是否有订单可以合并（未处理过的订单会自动合并，其他订单如果可以合并，会提示可合并）
6. 审核通过后才可以提交下一环节

:::

常见的订单审核规则有这么几个子项：

1. 分配仓库规则；
2. 分配物流规则；
3. 订单审核规则；
4. 拆合单规则；
5. 地址校验/修正规则；
6. 赠品规则；
7. 其他规则……

OMS/ERP的订单处理一般会包含以上内容，国内和跨境ERP基本上是类似的，少量的平台和业务要求不一样，所以功能上会有些微的差异。

<img src="https://cdn.nlark.com/yuque/0/2022/png/460219/1668660084912-2f960dd4-0bc8-4e37-8660-fb51cce5ac6f.png" width="422" title="" crop="0,0,1,1" id="CIpbM" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2022/png/460219/1665474714478-7340ec71-9072-43b2-a896-723b441007ca.png" width="3044" title="" crop="0,0,1,1" id="qbvP7" class="ne-image">

订单审核规则会很多，这里不全量展开。先聚焦和库存履约关系最强的几类：

| 规则 | 要解决什么 | 和库存/履约的关系 |
| --- | --- | --- |
| 地址校验 | 地址是否完整、是否可达 | 决定能否匹配物流，地址异常要阻断 |
| 库存校验 | 判断订单商品是否有货 | 没货不能进入正常发货 |
| 分仓/寻仓 | 决定从哪个仓发 | 决定锁哪一份库存 |
| 物流匹配 | 决定用哪个快递/物流服务 | 影响是否能按平台时效发货 |
| 拆单 | 一单多SKU或多仓发货 | 一笔平台订单可能拆成多个发货任务 |
| 合单 | 同收货人同地址多单合并 | 降低履约成本，但要保证库存和平台回传准确 |
| Hold单 | 延迟发货或异常挂起 | 暂不进入发货，但可能需要保留或释放库存 |
| 黑名单/风控 | 拦截高风险订单 | 避免欺诈、异常交易、平台处罚 |
| 赠品规则 | 自动添加或删除赠品 | 赠品也要占用库存 |
| 缺货处理 | 部分缺货或全部缺货 | 决定补货、换仓、拆发还是取消 |


审核规则的本质是把订单从"平台交易数据"变成"可履约任务"。

![](https://cdn.nlark.com/yuque/__mermaid_v3/078fb3bd6505fa52e740a525a36ee68e.svg)

:::info
审核规则引擎是电商 ERP 的灵魂。一个好的规则引擎能让 95% 的订单自动审核通过，只留下 5% 的异常需要人工处理。

:::

### 3.4 寻仓和锁库：订单履约的关键时序
在第5讲讲过，B2B销售订单可以在L1审核时确定仓库并预占库存。电商订单也要解决同一个问题：**这笔订单到底从哪一份库存里发？**

只是电商订单的处理更自动化。

**常见寻仓规则：**

| 寻仓规则 | 示例 | 风险点 |
| --- | --- | --- |
| 店铺默认仓 | 天猫旗舰店默认深圳仓 | 默认仓缺货时要有兜底 |
| 区域就近 | 华东订单优先上海仓 | 最近不等于有货，需结合库存判断 |
| 库存可用量 | 哪个仓能满足SKU数量就选哪个 | 要区分实物库存、锁定库存、可售库存 |
| 渠道专用仓 | Amazon订单只能走FBA/海外仓 | 配错会占用其他渠道资源 |
| 物流服务能力 | 偏远地区只能走指定仓和物流 | 仓库有货但物流不可达，仍无法发货 |
| 人工指定 | 大促、异常订单人工指定仓 | 需记录覆盖规则的原因 |


**寻仓和锁库的时序：**

![](https://cdn.nlark.com/yuque/__mermaid_v3/6437dae192b1a9097df6f7f0685616e1.svg)

**锁库时机对比：**

| 锁库节点 | 逻辑 | 优点 | 风险 |
| --- | --- | --- | --- |
| 订单审核通过时锁库 | 审核成功后占用库存 | 防止后续被其他订单抢走 | 审核阶段要处理大量锁定和释放 |
| 待配货时锁库 | 进入仓库发货前占用 | 减少无效占用 | 审核到配货之间可能被抢货 |
| 申请运单号前锁库 | 打单前确认库存 | 和物流流程结合紧密 | 节点偏晚，超卖风险较高 |
| 发货终态扣减 | 发货后扣减实物库存 | 和实际履约结果一致 | 不能替代前置锁库 |


### 3.5 本地仓履约 vs 三方仓履约
对于ERP的订单履约来说，根据履约仓库的不同，大致可以分成这么2种履约方式：

1. ERP的本地仓履约，即履约的仓库是通过ERP直接管理的这些仓库，所以在ERP上可以直接查看到仓库的信息，可以执行履约的操作，比较适用于仓库不大，也不是很精细化管理的那种，一套ERP软件就搞定了各种业务；仓库管理使用的是ERP的不同功能模块，所以ERP的订单模块和仓库模块可以共用一套库存体系，共享很多数据。
2. 第三方仓的履约，即履约的仓库不是ERP直接管理的仓库，例如跨境ERP一般对接的就是第三方海外仓，需要将订单信息推送给第三方海外仓去完成履约，也就是我们之前讲过的海外仓OMS→WMS的玩法；

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690358951535-e3a17749-c7e9-4fb2-8685-cf201e0eb7fc.png" width="3008" title="ERP的订单履约方式" crop="0,0,1,1" id="v1oaj" class="ne-image">

审核通过、找到仓库、锁了库存。下一步是把订单推给仓库执行。但"推给仓库"这件事，推给本地仓和推给三方仓，是完全不同的两套逻辑。

![](https://cdn.nlark.com/yuque/__mermaid_v3/5649d106b1a6080553872d66575306d8.svg)

| 对比维度 | 本地仓履约 | 三方仓履约 |
| --- | --- | --- |
| **仓库归属** | 企业自有仓库，使用ERP的仓储管理模块来处理仓库的日常业务 | 第三方仓（海外仓、平台仓、云仓），外部系统 |
| **推单方式** | 内部系统调用，同步/准同步 | API 调用外部系统，异步等结果 |
| **库存校验** | ERP 锁库 = 实物可用（同一套库存体系） | ERP 锁库 ≠ 三方仓一定认（三方仓有自己的库存账） |
| **执行过程** | 可实时跟踪拣货/复核/称重状态 | 只能等三方仓回传结果，中间状态不可见 |
| **异常处理** | 缺量直接回传，ERP 即时感知 | 推单被拒后才知道库存不够；发货超时可能完全无反馈 |
| **取消难度** | 拣货前可取消，拣货后需判断 | 推单成功后取消，需要调三方仓接口确认，可能已发货无法拦截 |
| **对账** | 内部系统，库存账天然一致 | ERP 账面和三方仓账面是两套账，需要定期对账 |


#### 本地仓履约详细流程
如果通过ERP的本地仓库进行履约，那么就要在ERP中对本地仓库的实物进行管理，和WMS的一样的玩法，需要有入库，质检，上架，出库，波次，拣货，复核，称重等功能模块，一般来说出库履约的功能ERP会放在"仓储"，"仓库"，"销售-发货履约"，"订单-发货"等位置。

本地仓履约的大致流程：

![](https://cdn.nlark.com/yuque/__mermaid_v3/96ee7c19f0d769b0e4c9a31a23a06cd7.svg)

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690359432795-fac74af5-08a2-46b7-9308-34dd482c45ec.png" width="818" title="" crop="0,0,1,1" id="KwCxv" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690359452389-10b64895-c96b-458e-ab47-9faec5ad5d07.png" width="1170" title="" crop="0,0,1,1" id="ZkucA" class="ne-image">

订单申请了运单号之后，会在ERP的发货模块生成一个"发货单"或者"出库单"，使用这个模块的人一般是仓库的操作员，这个仓库是电商卖家自己经营的仓库，例如深圳的一些电商卖家的自有仓一般会设立在深圳或者东莞。ERP可以开设不同的子账号，通过权限控制的方式让仓库人员只能登录ERP的发货模块，然后去完成这些待处理的发货单。

ERP的发货也会涉及到库存的锁定和扣减，具体锁定的节点可以根据业务不一样而调整：

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722248446493-5995d585-6cca-4429-9dfd-8cd3e78db9b5.png" width="1909" title="" crop="0,0,1,1" id="iKo8B" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690360053870-abb242a9-9ea3-4e1b-b8ad-c109c50683e9.png" width="3764" title="" crop="0,0,1,1" id="H80pr" class="ne-image">

赛狐ERP会有一个"待配货"的状态，如果分配库存成功，则会进入到"待打单"的状态，如果分配库存失败，则会提示"缺货"。领星ERP则是在【审核】订单的时候去判断库存是否足够，只有库存足够了之后，才可以进行下一步申请运单号。

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722249156424-8422e509-5892-4dc6-81c5-8456b2ee1fd4.png" width="3690" title="" crop="0,0,1,1" id="LcaKl" class="ne-image">

<img src="https://cdn.nlark.com/yuque/0/2024/png/460219/1722249453194-a104ad97-ab43-4635-99d9-cf496f224e9e.png" width="3764" title="" crop="0,0,1,1" id="NfDRu" class="ne-image">

:::info
这两种方式都可以，取决于产品方案怎么设计，一般来说锁库的节点都会有多个，因为需要支持不同的业务场景，有一些场景是先锁定库存再去申请运单号，有一些场景则是先申请运单号再去锁定库存，还有一些可能是虚拟出库或者不需要严格的实体库存管理，那么就不用锁库了。

:::

ERP发货的库存扣减一般来说就是发货单流入终态的时候扣减，例如说"已出库"，"已发货"，"已交运"等。

#### 三方仓履约详细流程
如果是采用第三方仓库来履约，那么对于ERP来说就只需要将审核后的订单数据推送给第三方仓，然后接收第三方仓作业之后的结果数据即可。

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692542412412-767d9076-4c46-45f6-9cd8-6f7a5a30f320.png" width="4676" title="" crop="0,0,1,1" id="oE4s8" class="ne-image">

ERP需要提前和第三方仓库进行对接，这个一般是一个大工程，因为第三方海外仓有很多，需要逐个去对接，然后一些业务流转需要加上配置化的东西，所以对接、调试、跑通的周期可能还比较长。

ERP推送单据到第三方仓库之前，也会先锁定库存，因为ERP需要统计第三方仓有多少库存，是否可以推送订单给第三方仓。虽然ERP自己推送订单之前会做一次库存的校验和锁定，但是实际单据推送到了下游的海外仓OMS之后可能也会失败，因为海外仓OMS的库存可能是不足的。

:::color4
ERP能否推送到第三方仓库，即要看ERP自己的一些规则条件校验是否通过，也要看三方仓是否校验通过，两者都没问题的情况下，单据才可以正常流转。

:::

ERP订单推送给第三方海外仓的时候也需要注意SKU的映射和转化，在ERP的系统中SKU可能叫做"苹果"，但是在海外仓的系统中SKU可能叫做"Apple"，所以ERP推送单据给海外仓的时候需要将自己本地的SKU映射为对方的SKU，这里的关系是这样的：

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1690361334026-6567c5b1-7466-45c5-8cb5-d08ecc9cdf53.png" width="2168" title="" crop="0,0,1,1" id="MRLtb" class="ne-image">

**三方仓履约完整时序：**

![](https://cdn.nlark.com/yuque/__mermaid_v3/20a3fb825e14670da542a20c9c41b546.svg)

三方仓履约最核心的产品风险就一个：**你锁了库存，推给三方仓，三方仓说没货。** 这在跨境场景里非常常见——三方仓的库存账更新有延迟、或者实物已经破损/丢失但账面没减。产品设计上必须兜住这个场景：推单被拒后自动释放锁定、触发重新寻仓，而不是让订单卡在中间状态无人处理。

:::info
本地仓和三方仓不是"同一个流程，仓库地址不同"，而是两套履约模式。产品设计上，发货单的数据模型要能区分 `fulfillment_type`（本地/三方），状态机也要分别覆盖各自的异常分支。

:::

### 3.6 库存扣减时机：系统性对比
前面 3.4 和 3.5 分别提到了不同的锁库节点。这里做一个系统性总结，并把 B2B 三层单据的扣减逻辑也放进来对照。

**电商 ERP 常见的四种库存扣减时机：**

| 锁库节点 | 典型系统/做法 | 逻辑 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| 订单审核通过时 | 领星ERP | 审核成功后占用库存 | 防超卖最安全 | 审核阶段处理大量锁定/释放 |
| 待配货时 | 赛狐ERP | 进入仓库发货前占用 | 减少无效占用 | 审核到配货之间可能被抢货 |
| 申请运单号前 | 部分ERP | 打单前确认库存 | 和物流流程结合紧密 | 节点偏晚，超卖风险较高 |
| 发货终态扣减 | 通用做法 | 发货后扣减实物库存 | 和实际履约结果一致 | 必须搭配前置锁库使用 |


**与 B2B 三层单据对照：**

| 阶段 | B2C 电商 ERP | B2B 自研 ERP |
| --- | --- | --- |
| 承诺 | 审核锁库存 / 配货锁库存 | L1 销售订单审核 → 预占库存 |
| 执行 | 推送 WMS 发货 | L2 发货通知单 → 推 WMS |
| 结果 | WMS 发货回传 → 实物 -1 | L3 销售出库单 → 实扣 + 应收确认 |


**锁库、扣减、释放三个概念要分开：**

| 概念 | 含义 | 典型节点 |
| --- | --- | --- |
| 锁库 | 系统承诺这份库存给某张订单，防止被其他订单占用 | 审核通过、待配货、待打单 |
| 扣减 | 实物已经发出或出库结果确认，库存账正式减少 | 已出库、已发货、已交运 |
| 释放 | 订单取消、锁库失败、换仓、超时未处理时释放占用 | 取消订单、换仓、人工释放 |


### 3.7 国内电商 vs 跨境电商：订单履约差异
前面讲的是通用型的电商ERP处理逻辑，但是在实际的业务场景中，不同的电商平台会有不同的履约方式。例如说亚马逊就会有FBA和FBM的发货模式，然后FBM（意为卖家自配送）也可以拆分成从海外仓发货，或者是从国内仓直发。所以这里也会有一些订单处理上的差异，我们做一个简单对比，如果想要了解更详细的订单履约的处理逻辑，可以去做竞品调研，做相关的分析。

**差异一：履约路径从一条变成三条**

国内电商 ERP 只有一种履约方式——从国内仓发货。跨境 ERP 的订单进来后，先要判断走哪条路：

![](https://cdn.nlark.com/yuque/__mermaid_v3/a41750c4356d340aa939a7ebea5c74c8.svg)

| 履约路径 | 发货主体 | ERP 做什么 | 典型时效 | 适用场景 |
| --- | --- | --- | --- | --- |
| FBA 履约 | Amazon 官方 | 仅同步订单和库存数据，不操作发货 | 1-2 天（Prime） | 追求时效、FBA 仓有货 |
| 海外仓履约 | 第三方海外仓 + 本地快递 | 推单到海外仓，跟踪发货状态 | 2-5 天（本土配送） | 兼顾时效和成本、多平台运营 |
| 国内直发 | 卖家自己 | 完整履约链路（审单→打单→拣货→跨境物流→标发） | 7-20 天（跨境运输） | 小件低客单价、新品测试、库存灵活 |


**差异二：审核环节多了"物流比价"**

国内 ERP 物流匹配相对简单——通常是签约快递，按地址匹配就行。跨境直发订单，物流渠道差异巨大：云途、燕文、4PX 等 400+ 物流商，不同渠道的价格、时效、覆盖区域差异显著。领星的审核环节支持物流比价——系统列出不同物流方式的预估运费，运营选择最优方案后再审核通过。

**差异三：发货后多了"标发"环节**

国内 ERP 发货后自动回传物流单号到平台。跨境平台（Amazon、eBay 等）对此有严格时效要求——订单必须在规定时间内上传物流单号（标发），超时可能罚款或影响账号绩效。所以跨境 ERP 的履约链路末尾多了一个关键动作：**标发 = 把物流单号上传到平台后台**，这不是"顺便做一下"，是有 SLA 压力的。

**差异四：售后处理的"钱货分离"更极端**

国内电商的售后一般是退货退款或换货，实物和钱款基本同步回流。跨境场景下退货成本极高（国际运费可能超过货值本身），所以存在大量"仅退款不退货"的情况——平台已退款，但实物不回来。ERP 的售后模块需要处理"应收冲减了但库存不变"这种场景。

**差异五：在途库存对履约的影响更大**

国内 ERP 的采购在途通常 1-3 天，对订单履约判断影响有限。跨境的 FBA 头程（国内 → FBA 仓）可能走 10-20 天，这段时间的"在途库存"既不能卖、又影响补货决策——ERP 需要明确区分：FBA 在售（可卖）、FBA 在途（不能卖但要被计划感知）、海外仓在库（可卖）、国内直发仓（可卖但时效长）。

**一张表总结：**

| 履约环节 | 国内电商 ERP（聚水潭） | 跨境电商 ERP（领星） |
| --- | --- | --- |
| 履约路径 | 1 条（国内仓发货） | 3 条（FBA / 海外仓 / 国内直发），订单进来先判断走哪条 |
| 审核环节 | 仓库分配 + 物流匹配 | 仓库分配 + **物流比价**（400+ 物流商，价格/时效差异大） |
| 发货操作 | ERP 全链路主控（打单→拣货→发货） | FBA 不操作、海外仓推单、国内直发全链路 |
| 发货后 | 自动回传物流单号 | **标发**到平台（有 SLA 压力，超时罚款/影响账号绩效） |
| 售后处理 | 退货退款/换货，钱货基本同步 | 大量仅退款不退货（退货成本 > 货值），钱货分离更极端 |
| 在途库存影响 | 采购在途 1-3 天，影响小 | FBA 头程 10-20 天，在途库存直接影响补货决策 |


### 3.8 B2C 订单处理 vs B2B 三层销售单据
第 5 讲和第 6 讲分别讲了 B2B 和 B2C 的订单/库存处理。这里我们用一张表来做一个总结，让大家有一个更直观的差异性的对比：

| 维度 | B2C 电商（SaaS ERP） | B2B 批发（自研 ERP） |
| --- | --- | --- |
| **订单来源** | 电商平台 API 拉单（推送/定时/手动） | 销售人工录入 / Excel 批量导入 |
| **审核方式** | 规则引擎自动审单（95% 自动通过） | 人工审核（客户信用/价格/库存） |
| **仓库确定时机** | 审核时规则自动匹配 | L1 创建/审核时确定 |
| **库存锁定/扣减** | 审核锁库 → 发货回传实扣 | L1 预占 → L3 实扣 |
| **单据结构** | 平台订单 → 审核 → 发货单 → 结果归集 | 销售订单 L1 → 发货通知单 L2 → 销售出库单 L3 |
| **退货处理** | 平台售后单（钱货可能不同步） | 三层退货单据（钱货必须同步） |
| **主控系统** | SaaS ERP 主控履约 | 自研 ERP 主控完整链路 |
| **ERP 角色** | 理解、接收、对账、归集 | 创建、审核、执行、入账 |


## 4. 产品设计实战：从知识科普到方案产出
前面 3.1–3.8 是对电商 ERP 订单处理链路和库存模型的快速科普。如果真要去做产品设计，不能把这些知识点简单堆成页面，而是要产出一组产品设计交付物。

| 交付物 | 回答的问题 | 常见产出 |
| --- | --- | --- |
| 业务流程图 | 业务对象在平台、ERP、仓库、物流之间怎么流转？ | 角色泳道图、单据关系图 |
| 系统流程图 | 系统内部如何判断、分支、自动处理和异常回退？ | 流程图、决策树、时序图 |
| 状态机 | 订单有哪些状态，哪些状态可逆，哪些状态影响库存？ | 状态流转图、状态表 |
| 产品结构图 | 订单模块由哪些子模块组成？ | 功能结构图、模块清单 |
| 页面原型 | 用户在哪里查看、处理、配置和追踪订单？ | 列表页、详情页、规则配置页、异常处理页 |


### 4.1 先画业务流程图：把平台、ERP、仓储关系讲清楚
业务流程图不是页面流程图，它先回答"业务对象之间怎么流转"。

看图时不要背单据名称，而是抓住三个关系：平台订单怎么进入 ERP，ERP 怎么转成仓储作业，仓储结果怎么回传平台。

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692502098700-38cf9102-4689-443d-8d5c-1d1d1f53ca6f.png" width="2968" title="平台、ERP、仓储的主要单据关系图" crop="0,0,1,1" id="qdlSe" class="ne-image">

拆业务流程图时，建议确认这五个问题：

| 步骤 | 产品经理要确认什么 |
| --- | --- |
| 1. 订单来源 | 来自哪些平台、店铺、线下渠道？订单号如何唯一？ |
| 2. 主控系统 | 是 ERP 主控，还是外部 SaaS/OMS 主控？ |
| 3. 履约对象 | 最终生成的是发货单、出库单、三方仓推单，还是平台仓履约结果？ |
| 4. 结果回写 | 发货结果回写给谁？库存、物流、售后、财务分别怎么同步？ |
| 5. 异常闭环 | 缺货、推单失败、取消、退款、地址异常有没有回路？ |


> 业务流程图不要一上来就画页面按钮。先把平台、ERP、仓库、物流、财务几个角色之间的单据关系画清楚，页面设计才不会飘。

### 4.2 再画系统流程图：把订单处理规则拆出来
系统流程图比业务流程图更细，它要表达系统内部怎么判断、怎么分支、怎么自动处理。

以下是四家竞品的系统流程图，每家适合观察的角度不一样：

| 竞品图 | 适合观察什么 |

| 聚水潭订单处理流程 | 国内电商审单、分仓、打单、发货链路 |
| 赛狐订单处理流程 | 待配货、缺货、锁库、待打单之间的状态关系 |
| 领星订单处理流程 | 跨境订单在 FBA、海外仓、国内直发之间的履约分支 |
| 商派 OMS 订单处理流程 | 全渠道订单中台如何统一接单、路由、履约分发 |


参考竞品不是为了复刻某一家，而是抽出自己的系统流程：哪些节点必须有，哪些节点可以简化，哪些异常在当前业务里必须闭环。

看系统流程图时，不要只看箭头顺序，要问这五个问题：

| 问题 | 对应产品设计动作 |
| --- | --- |
| 哪些节点能自动通过？ | 设计自动审核规则、任务调度和批处理 |
| 哪些节点必须人工处理？ | 设计异常队列、人工审核入口和处理记录 |
| 哪些节点会锁库存？ | 设计库存占用、释放、换仓、缺货处理 |
| 哪些节点要调用外部系统？ | 设计接口、重试、幂等、失败补偿 |
| 哪些节点会改变订单状态？ | 设计状态机、操作权限和日志 |


### 4.3 单独画状态机：不要只写"待处理/已完成"
订单模块很容易被做成一堆列表页：待审核、待配货、待打单、已发货、已取消。真正的产品设计要回答的是：这些状态之间怎么流转，谁可以操作，操作失败怎么办。

不同的ERP会采用不同的订单状态机进行处理，这里以**店小秘和妙手ERP**的状态机作为参考对象：

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692512064075-304c37b1-4510-48da-9f5a-8fbc42b379d2.png" width="5176" title="ERP订单处理的状态机" crop="0,0,1,1" id="wAscr" class="ne-image">

状态机至少要拆四类状态：

| 状态类型 | 例子 | 设计重点 |
| --- | --- | --- |
| 前置处理状态 | 待拉取、待匹配、待审核 | 是否自动流转，异常是否阻断 |
| 履约承诺状态 | 待配货、已锁库、缺货、Hold | 库存占用、释放、换仓逻辑 |
| 作业执行状态 | 待打单、待拣货、已出库、已发货 | 和 WMS/三方仓的接口边界 |
| 终态/异常状态 | 已完成、已取消、退款中、推单失败 | 是否可逆，是否影响库存和应收 |


状态机设计最容易出错的地方，是只写正向流程，不写异常回路。比如：锁库成功后订单取消，库存是否释放？三方仓推单失败，订单回到哪里？已发货后退款不退货，库存要不要动？这些才是产品设计的关键。

### 4.4 决定订单处理和仓库作业是否解耦
产品设计时还要判断一个问题：订单模块要不要直接做仓库作业？

<img src="https://cdn.nlark.com/yuque/0/2023/png/460219/1692513163188-ef052230-938b-48b6-b383-6d5d34bf6d4b.png" width="2808" title="" crop="0,0,1,1" id="RCcAm" class="ne-image">

大多数的ERP都支持自有仓库发货和第三方仓库发货。对第三方仓库来说，只需将订单推送到三方仓系统，后续详细操作由三方仓负责；对自有仓库发货来说，有一些ERP的仓库发货模块和订单处理模块解耦，有一些则不解耦。

| 方案 | 适用场景 | 产品设计影响 |
| --- | --- | --- |
| 不解耦：订单模块直接打单发货 | 仓库小、流程简单、ERP 一体化作业 | 页面简单，但仓库精细化能力弱 |
| 半解耦：订单生成发货任务，仓库模块处理 | 中小型自有仓，作业复杂度中等 | 要设计发货单、拣货、复核、回传 |
| 完全解耦：订单模块只推送 WMS/三方仓 | 自研 WMS、三方仓、海外仓、多仓履约 | 要设计接口、状态同步、异常补偿 |


这个判断会影响菜单结构、权限设计、状态机、接口文档和测试用例。不要等画页面时才临时决定。

| 我能区分电商 ERP 库存扣减的三种时机吗？ | 能说清审核锁库（领星主流）、打单锁库、待配货锁库的差异和超卖风险权衡 |
| 我能说清三方仓履约的库存扣减链路比本地仓多了哪个环节吗？ | 能说清三方仓有两次校验（ERP侧+三方仓侧），推单被拒后要释放锁定 |
| 我能区分锁库、扣减、释放三个概念吗？ | 能说出锁库是承诺、扣减是结果、释放是撤回承诺 |
| 我能用一张表说清 B2C 和 B2B 在库存管理上的 8 个维度差异吗？ | 覆盖订单来源、审核方式、仓库确定时机、锁库扣减、单据结构、退货、主控系统、ERP角色 |
| 我能画订单管理业务流程图吗？ | 能画清平台、ERP/OMS、WMS/三方仓、物流、平台回传之间的关系 |
| 我能画订单管理系统流程图吗？ | 能把 SKU 映射、审核、寻仓、锁库、履约、异常分支放进流程，且有异常回路 |
| 我能画订单状态机吗？ | 能说明哪些状态会影响库存、哪些状态是终态、哪些状态可回退 |
| 我能拆出订单模块产品结构吗？ | 能覆盖订单获取、订单列表、详情、规则、履约、异常、售后、日志 |


**应用判断（进阶）：**

| 场景 | 判断要点 |
| --- | --- |
| 运营反馈"聚水潭显示可售 500，ERP 显示可用 300" | 差异可能来自：调度层锁定/预留、安全库存设置、销售层运营手动调整 |
| 仓库说"ERP 锁了 100 个但我只拣到 95 个" | 问题在实物层（账实不符），ERP 要释放 5 个锁定并触发重新寻仓或缺货告警 |
| 运营想把天猫展示库存设得比调度层算出来的可售库存更高 | 技术上可以（销售层是运营决策层），但要评估超卖风险，加强审核规则兜底 |
| 公司要从纯 B2C 扩展到 B2B+门店 | 实体仓级调度层不够，需要升级到实体仓+逻辑仓级，区分电商/批发/门店口径 |

## 7. 补充知识
### 7.1 面试考点
| 面试问题 | 回答方向 |
| --- | --- |
| 电商 ERP 订单处理的核心链路是什么？ | 平台拉单 → SKU 映射 → 审核规则 → 分仓分物流 → 打单发货 → 平台回传。每个环节都要说清和库存的关系 |
| SKU 映射为什么重要？ | 多平台 SKU 各不相同，映射不对 → 仓库分配和库存判断全错 → 超卖或无法履约。跨境还有第三段三方仓映射 |
| 审核规则引擎决定什么？ | 决定订单能不能发、从哪个仓发、用什么物流发、是否需要人工处理——仓库分配和库存校验直接决定库存从哪个仓扣、扣多少 |
| 库存扣减时机有哪几种？ | 审核锁库（领星主流）、打单锁库（部分 ERP）、待配货锁库（赛狐）——锁太早浪费库存利用率，锁太晚有超卖风险 |
| 为什么需要分三层？ | 仓库、供应链、运营三个角色的决策权分离，互不干扰。合成一层则运营改不了展示库存、计划看不到全局可售 |
| 自研 ERP 要不要重做一套聚水潭？ | 通常不需要。成熟 SaaS 主控 B2C 拉单、审单、打单、发货；自研 ERP 的价值在接履约结果、形成库存/财务口径、做深度定制。重做等于重造轮子 |
| 订单管理产品设计要交付哪些图？ | 业务流程图、系统流程图、状态机、产品结构图、关键页面原型，五类缺一不可 |


### 7.2 常见坑与误区
| 坑 | 为什么是坑 | 正确理解 |
| --- | --- | --- |
| 以为 SKU 映射是"一次性配置好就不用管了" | 新品上架、平台规则变更、三方仓 SKU 变更都需要持续维护 | SKU 映射是持续运维过程，不是一次性项目 |
| 以为所有 ERP 都有逻辑仓 | 很多 B2C SaaS ERP 调度层以实体仓为主粒度，纯 B2C 场景不需要区分同仓不同用途 | 逻辑仓是全渠道 OMS 的高配需求，不是所有 ERP 的标配 |
| 以为库存扣减时机有"最佳实践" | 审核锁库/打单锁库/待配货锁库各有利弊，取决于业务对超卖容忍度和库存利用率的权衡 | 没有完美方案，只有适合业务的方案 |
| 把锁库当成扣减 | 订单取消、换仓、缺货时库存处理会乱——以为发出订单就扣了库存 | 锁库是承诺，发货/出库后才扣减，期间还有释放的可能 |
| 三方仓推单只看 ERP 库存 | 外部仓可能 SKU 不存在或库存不足，ERP 账面有货≠三方仓一定接单成功 | ERP 校验和三方仓校验都要通过，推单被拒后必须释放锁定 |
| 一上来就画页面原型 | 页面有了，但业务流程、系统分支和状态流转讲不清 | 先画业务流程图和系统流程图，状态机和产品结构清楚后再落页面 |
| 只画正向流程，不画异常回路 | 缺货、取消、推单失败、退款不退货等场景不闭环，实际落地会漏洞百出 | 系统流程图和状态机必须覆盖异常回路，异常处理才是产品设计的难点 |
